## 二、风险分析（限定措辞）

### 2.1 已证明的潜在写入路径

- 文件 0666 + 祖先目录 0777：当前 Unix 权限位下，本地用户可写/替换 `main.py`；
- bind RW + 容器 root：存在“容器内 root → 宿主文件”的写路径。

### 2.2 尚未核实、不能直接断言的部分

- **user namespace**：未启用（UsernsMode 空），但未验证宿主是否有其它 namespace 限制；
- **capabilities**：CapEff 为 Docker 默认集（含 DAC_OVERRIDE 等），未逐一映射到“能否写该文件”；
- **AppArmor**：`docker-default (enforce)` 已启用，但其 profile 是否限制该路径写入未逐条验证；
- **SELinux**：`getenforce` 不可得，未确认；
- **ACL**：未检查。

因此，正确表述是：**存在潜在写入路径；不能断言“任意容器 root 进程均可写宿主”**。

### 2.3 本地用户风险

基于当前 Unix 权限位判断；若 ACL 或其它访问控制存在，实际可利用性可能不同。需要 ACL 核实后才能下最终结论。

## 三、升级流程对权限的影响

- AstrBot 升级后需把 `core_patches/` 四个文件放回（`运维与备份.md`）；
- 插件升级会覆盖源码（`HANDOFF` 坑：改过第三方的地方要登记）；
- 未发现统一的“部署后 chmod”流程；
- 因此权限可能在升级/复制过程中被重新设置，**基线需要与升级流程一起定**。

## 四、权限基线建议（待主人决定，未执行）

### 4.1 目标

- 文件：`0644`（root 写、其他只读）；
- 目录：`0755`（root 写、其他进入/读）；
- 若 AstrBot 以非 root 运行且需写插件目录：专用组 + `0664`/`2775`，不要 world-writable。

### 4.2 前置确认

1. AstrBot 实际运行用户（容器内 root；宿主是否 root 启动）；
2. 插件升级/重载是否会重写权限；
3. 宿主是否有其他可登录用户/服务；
4. ACL 是否存在；
5. 收紧目录 0777 是否影响现有部署/备份脚本。

### 4.3 分步建议

1. 先只读确认 ACL/运行用户/升级流程；
2. 在隔离副本验证 0644/0755 不影响 AstrBot 加载；
3. 选维护窗口，先改插件文件/目录，再改上层目录；

5. 单独立项，不与 P3 修复混在一起。
