## 二、0666 的写权限风险（分析，未修改）

### 2.1 已验证事实

```text
namei -l:
drwxr-xr-x root root /
drwxr-xr-x root root opt
drwxrwxrwx root root astrbot
drwxrwxrwx root root data
drwxrwxrwx root root plugins
drwxrwxrwx root root astrbot_plugin_tool_xml_guard
-rw-rw-rw- root root main.py
```

- 文件 0666：任何本地用户可写；
- 祖先目录 `/opt/astrbot`、`data`、`plugins`、插件目录均 0777：任何本地用户可创建/替换文件；
- bind RW + 容器 root：容器内被攻破的 root 进程可写宿主文件。

### 2.2 风险依据

- 0666 意味着 world-writable：任何能登录宿主或在该主机上有代码执行的本地用户，都可以替换 `main.py`；AstrBot 下次重启/重载即执行；
- 目录 0777 放大风险：即使文件改成 0644，普通用户仍可删除/替换文件（目录可写）；
- 容器 root + RW bind：容器内任意 root 进程可改写宿主插件，形成“容器 → 宿主”持久化面；
- 这是**既有状态**（v6/v14 部署前线上文件即 0666），不是本次部署引入；本次按部署准备“保持原权限”执行。

### 2.3 建议（未执行）

1. 文件建议 `0644`（root 写、其他只读）；目录建议 `0755`；
2. 若 AstrBot 以非 root 运行且需要写插件目录，改用专用组 + `0664`/`2775`，不要 world-writable；
3. 修改前先确认：AstrBot 运行用户、升级/重载流程、备份与回滚；单独立项，不在本轮改；
4. 由于目录 0777，只改文件权限不够，需同时收紧目录；
5. 备份目录 `备份_20261122_p1a1_v14_failclosed_pre/` 当前也是 0777/文件 0666，同上风险，建议一并评估。

### 4.3 为什么校验失败后仍启动

脚本把“备份校验失败”设计成“恢复服务”分支，但实现是**裸 `docker start`**，没有先做任何磁盘 `main.py` 核验。它不是“验证后启动”，而是“失败即启动”。

### 4.4 是否违反部署前置条件

- **违反流程要求**：部署准备 v5 的 3.3.1 要求“任何 `docker start`/`restart` 前必须核验磁盘 `main.py` 的 SHA、属主、权限”；该分支没有核验。
- **未造成未验证文件上线**：该次启动前 `main.py` 未被修改，仍是部署前的 v14 `2f180cf0…`；所以启动的文件本身是已知的 v14，不是候选、也不是未知文件。
- 结论：**过程违规，结果未引入未验证文件**；不能因为结果安全就认为流程正确。

### 4.5 根因

1. **预期值硬编码错误**：`V14` 写成了 v6 `c4497e04…`，与实际 v14 `2f180cf0…` 不符；
2. **启动动作没有统一入口**：备份失败/校验失败分支直接 `docker start`，未调用 3.3.1 的“启动前核验”；
3. **脚本把“备份校验失败”与“恢复服务”混在一个分支**：没有区分“备份内容错误”和“是否需要启动/启动什么版本”。

### 4.6 修复设计（未执行）

1. 封装唯一启动函数 `start_verified(expected_sha)`：
   - 读取当前磁盘 `main.py`；
   - 核验 SHA == expected_sha、属主 == root:root、权限 == 部署前记录值；
   - 三项通过才 `docker start`；任一失败不启动、记录、报告；
2. 所有分支（正常部署、备份失败、校验失败、回滚、恢复）都调用 `start_verified`，禁止裸 `docker start`；
3. 预期 SHA 从**单一来源**读取（部署准备报告/常量文件），并在执行前打印 `expected`；避免手写；
4. 备份校验失败分支：先确认/恢复原文件，再 `start_verified(V14)`；不把“备份校验”与“启动”合并；

## 六、结论汇总

### 已验证事实

1. 线上 `main.py` 路径 `/opt/astrbot/data/plugins/astrbot_plugin_tool_xml_guard/main.py`，SHA `bba95b71…`，root:root 0666，inode 661568；

4. 第一次脚本 `V14` 误写 v6，`BACKUP_MISMATCH` 分支裸 `docker start`，未执行 3.3.1 核验；

### 推断

1. 0666 + 目录 0777 + bind RW + 容器 root 构成“本地用户或容器内 root 可替换插件”的写权限风险；实际可利用性取决于宿主其他用户/服务，未做渗透验证；

2. 目录 0777 的历史来源与是否可安全收紧；
