# 部署脚本整改设计（start_verified 统一入口）v4

- **文档类型**：整改设计（不施工、不动线上）
- **任务**：解决部署脚本所有分支绕过 `start_verified()` 的问题
- **版本**：v4（v3 复审返修；补配置保护边界、状态统一、invoked 时序与命名、备份分支）
- **日期**：2026-11-22
- **更新时间**：2026-11-22 15:25（Asia/Shanghai）
- **当前状态**：**修订完成，待复审；未修改脚本、未改线上**

## 〇、v4 返修点

1. `deploy.env` 保护不能只靠文件属主/mode：补**完整路径、父目录权限、符号链接检查、读取与使用之间竞态**；权限基线未完成前不宣称可靠防篡改。
2. 统一 `RUNNING_UNVERIFIED`：保持运行，**不自动 stop/restart/回滚**；是否停止由主人决定；删除 3.7 中“自动停止”的歧义。
3. `invoked` 写入时序：**先持久化 `invoked` 并确认写入成功，再调用 `docker start`**；结果独立追加，不覆盖原记录。
4. 废弃 `recovered_success`，改为 `running_disk_match` / `running_disk_mismatch` / `stopped_unknown`：只证明“巡检时磁盘相符”，不证明容器已加载代码字节。
5. “备份校验不一致”分支：**不自动启动、不自动回滚**；只有确认可信 v14 文件并恢复后，才允许 `start_verified(v14)`；无法确认则保持停止、报告。

## 一、现状缺陷（已证实）

1. `p3_deploy_stepA.sh` 的 `BACKUP_MISMATCH` 分支裸 `sudo docker start astrbot`，未执行 3.3.1 三项核验；
2. 备份失败、复制失败、`mv` 失败等分支也有裸 `docker start`；
3. 预期 SHA 硬编码，且误写为 v6（`c4497e04…`），实际 v14（`2f180cf0…`）；
4. “启动完整性核验”与“权限安全基线”未分开；
5. 无统一启动日志（expected/actual）。

## 二、目标

1. **所有** `docker start` / `docker restart` 只能通过统一入口；
2. 启动前实际读取磁盘 `main.py`，核验 SHA、属主、权限；
3. 目标与 SHA 绑定，不接受任意组合；
4. 失败不启动、报告、人工恢复；
5. 启动尝试两阶段留痕；
6. 明确竞态未根治，依赖权限基线整改。

## 三、设计

### 3.1 配置来源与保护

#### 3.1.1 唯一来源与严格解析

`deploy.env` 是**唯一来源**；不保留脚本顶部常量、不读 shell 环境变量覆盖。

- 只接受 `KEY=VALUE`，一行一对；忽略空行与整行 `#` 注释；
- **白名单键**：`TARGET_CANDIDATE_SHA`、`TARGET_V14_SHA`、`EXPECTED_OWNER`、`EXPECTED_MODE`；
- 未知键、重复键、缺键 → 失败；
- 不允许引号、空格、续行、变量展开、`export`；
- 值类型校验：
  - SHA：`^[0-9a-f]{64}$`；
  - OWNER：必须为 `root:root`（或与部署前记录一致）；
  - MODE：`^0?[0-7]{3,4}$`，且必须与部署前记录一致；
- 解析失败 → 不启动、记录、报告。

#### 3.1.2 路径与父目录保护（v4 新增）

不能只 `stat` 最终文件。启动前检查：

1. `deploy.env` 的**完整绝对路径**，拒绝相对路径；
2. **父目录链**（`/opt/astrbot`、`.../shared`、`.../记忆`、`.../部署`）逐级权限：任一级允许 world-writable（others 有 `w`）→ 判定“配置可被替换”，不启动；
3. 文件本身：属主 `root`、mode 不宽于 `0640`、**非符号链接**（`lstat` 检查，拒绝 symlink）；
4. 路径中任一段是符号链接 → 失败；
5. 上述检查不能消除“检查后被替换”的竞态；在权限基线完成前，**不宣称 `deploy.env` 已获得可靠防篡改保护**。

#### 3.1.3 读取与使用竞态（v4 新增）

- 读取 `deploy.env` 后，到实际使用（构造 `TARGETS`、启动）之间，配置仍可能被替换；
- 缓解：读取后记录文件 `inode/mtime/SHA`，使用前再次核验；不一致 → 中止；
- 仍不能根治：0777 父目录下，其他写入者可在两次检查之间替换；与权限基线整改建立依赖；
- 不能把“两次 stat 一致”写成“配置文件安全”。

#### 3.1.4 交叉核对

- `TARGET_V14_SHA` 必须等于备份实际 SHA 与部署准备报告基线；
- `TARGET_CANDIDATE_SHA` 必须等于候选 snapshot SHA；
- 不一致 → 中止，不启动。

### 3.2 目标与 SHA 绑定

```text
TARGETS = {
  "candidate": TARGET_CANDIDATE_SHA,
  "v14":       TARGET_V14_SHA,
  "recovered-v14": TARGET_V14_SHA,
}

start_verified(target):
  expected_sha = TARGETS[target]        # target 未知 → 立即失败，不启动
  读取磁盘 main.py 的 SHA/属主/权限
  核验 SHA == expected_sha
  核验 属主 == EXPECTED_OWNER
  核验 权限 == EXPECTED_MODE
  写 precheck 日志（target/expected/actual/result）
  三项全过 → 调用受控启动（见 3.5.1 时序）
  任一项失败 → 不启动；写 precheck fail；返回非零
```

- `start_verified` 只接受 target，不接受调用方传 SHA；
- `TARGETS` 由 `deploy.env` 构建；未知 target 直接失败；
- 目标与 SHA 映射在启动前打印一次，供人工核对。

### 3.3 分支矩阵（v4 修订）

| 分支 | 启动调用 |
|---|---|
| 正常部署（替换后） | `start_verified(candidate)` |
| 备份失败 | 不自动启动；保留现场、报告；确认可信 v14 后才 `start_verified(v14)` |
| **备份校验不一致** | **不自动启动、不自动回滚**；保留现场、报告；只有找到来源可信、SHA 符合 `TARGET_V14_SHA` 的 v14 文件并完成恢复后，才允许 `start_verified(v14)`；无法确认则保持停止 |
| 临时文件复制/校验失败 | 删临时文件；确认原文件可信后 `start_verified(v14)`；无法确认则停止、报告 |
| `mv` 失败 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败则停止、报告 |
| 回滚 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败则停止、报告 |
| 启动失败后重试 | 仍调用 `start_verified(当前 target)`，禁止裸 start/restart |
| 验证失败（测试 FAIL） | 不自动启动/回滚；报告，由主人决定；回滚走 v14 分支 |

要点：**“备份校验失败”不等于“可以启动 v14”**；只有可信恢复来源才允许启动。

### 3.4 restart 语义

- **禁止裸 `docker restart`**；静态检查同时禁止统一入口外的 `docker (start|restart)`；
- `restart_verified(target)`：
  1. `docker stop`（失败/仍运行 → 不继续，报告）；
  2. 核验磁盘 `main.py` 三项；
  3. 三项通过才按 3.5.1 时序启动；
  4. 写 precheck/start 两阶段日志；
- 不接受“跳过核验直接 restart”。

#### 3.4.1 重启后核验失败：统一状态（v4 修订）

- `STOPPED_UNVERIFIED`：容器停止且磁盘文件未通过核验；**保持停止，不自动启动**；保留现场；写日志；报告。
- `RUNNING_UNVERIFIED`：容器已运行但复核失败；**保持当前运行状态，不自动 stop/restart/回滚**；保留现场；写日志；报告；是否停止由主人明确决定。
- 两种状态都只读记录；dsh 不自动执行恢复动作。

> 删除 v3 中“启动后核验不一致 → 记录并停止/告警”的歧义；统一为“记录并告警，保持运行，不自动停止”。

### 3.5 启动日志

路径：`/opt/astrbot/shared/记忆/部署日志/start-attempt-<timestamp>.json`（每次尝试一个文件）。

```json
{
  "time": "...",
  "target": "candidate",
  "expected_sha": "...",
  "actual_sha": "...",
  "owner": "root:root",
  "mode": "666",
  "precheck": "pass | fail",
  "start": "not_invoked | invoked | success | failed | interrupted",
  "resolution": "（仅 invoked 遗留时追加）"
}
```

#### 3.5.1 `invoked` 写入时序（v4 修订）

1. 三项核验通过后，**先持久化 `start=invoked`**；
2. **确认日志写入成功**（fsync/rename 或可验证的写返回）；
3. 再调用 `docker start`；
4. 根据 Docker 命令明确返回结果，**独立追加**最终状态（success/failed）；
5. 若进程中断，保留 `invoked`，交给后续只读取证；
6. 原始记录不被覆盖；结果以追加记录/字段形式保留。

#### 3.5.2 `invoked` 遗留与 `resolution`（v4 修订）

发现 `invoked` 遗留时，读容器状态与磁盘三项，追加：

- 容器 Running 且磁盘三项符合预期 → `resolution=running_disk_match`；
- 容器 Running 但磁盘三项不一致 → `resolution=running_disk_mismatch`；
- 容器 Stopped → `resolution=stopped_unknown`；
- **不使用 `recovered_success`**：只证明“巡检时运行且磁盘相符”，不证明容器实际加载的代码字节；
- 原记录保留，`resolution` 独立追加；不把 `invoked` 当 success。

### 3.6 静态检查 + 分支测试

- 静态检查：`grep -nE 'docker (start|restart)' deploy.sh`，统一入口外出现即失败；
- 分支测试：备份失败、备份校验不一致、复制失败、`mv` 失败、回滚、启动失败重试，断言“只走统一入口、失败不启动、两阶段日志、非零退出”；
- dry-run + 故障注入；
- 补充测试：
  1. `deploy.env` 解析（缺/多/重复/非法值/权限宽/父目录 world-writable/symlink）；
  2. 读取与使用间替换（模拟两次 inode/mtime 不一致）；
  3. 重启后失败：`STOPPED_UNVERIFIED` / `RUNNING_UNVERIFIED`，断言不自动 stop/restart/回滚；
  4. `invoked` 时序：在 start 前中断，确认 invoked 已持久化；resume 追加 `running_disk_match` 等；
  5. 备份校验不一致：断言不自动启动、不自动回滚；
  6. target/SHA 映射：未知 target/不匹配 → 失败。

### 3.7 校验与启动之间的竞态（v4 补充配置）

- 目录 0777、文件 0666；`start_verified` 检查完到 Docker 加载文件之间，文件仍可能被替换；
- `deploy.env` 自身也有“读取→使用”竞态，父目录 0777 时同样可被替换；
- 部署脚本内部 `flock` 只能防并发部署，不能阻止其他写入者；
- 缓解：窗口最小化、启动后复核 inode/mtime/SHA、配置读取两次核验；
- **不能宣称竞态已消除**；权限基线整改是根治前提。

## 四、风险

1. 竞态未根治（依赖权限基线）；
2. `start_verified` 只保证“启动字节与目标一致”，权限 0666 下核验一致不代表权限安全；
3. 启动日志/配置目录权限也需评估；
4. 分支测试若只 dry-run，可能与真实 Docker 行为有差异；
5. 配置与启动文件均可能被 0777 环境下替换。
