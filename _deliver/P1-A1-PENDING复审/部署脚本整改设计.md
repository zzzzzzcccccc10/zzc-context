- **文档类型**：整改设计（不施工、不动线上）
- **任务**：解决部署脚本所有分支绕过 `start_verified()` 的问题
- **版本**：v8（v7 返修；JSON 行合法性、三态映射、不可记录状态、非 root 判据、锁文件安全）
- **日期**：2026-11-22
- **更新时间**：2026-11-22 16:05（Asia/Shanghai）
- **当前状态**：**修订完成，待复审；未修改脚本、未改线上**

## 〇、v8 返修点

1. **完整 JSON 行合法性**：不只检查“行是否有换行”，还逐行 `json.loads` 校验；区分“缺行结束符”“有换行但 JSON 损坏”“中间行损坏”。
2. **三态映射**：`RUNNING_UNVERIFIED` / `STOPPED_UNVERIFIED` / `STATE_UNKNOWN_UNVERIFIED` 固定映射，删除歧义。
3. **不可记录状态**：`start_result` 或 `resolution` 写入失败 → 进入 `UNRECORDED`，不得推断启动成功/失败；容器状态不可读 → `STATE_UNKNOWN_UNVERIFIED`。
4. **非 root 目录属主判据**：白名单 + 系统账号 + 不可交互登录 + 无提权组；无法验证 → 失败关闭。
5. **锁文件安全**：受保护目录、`O_CREAT|O_EXCL`/`flock`、拒绝 symlink、root:0600、父目录检查；锁失败不启动；锁不阻止其他写入者。

## 一、现状缺陷（已证实）

1. `p3_deploy_stepA.sh` 的 `BACKUP_MISMATCH` 分支裸 `sudo docker start astrbot`；
2. 备份失败、复制失败、`mv` 失败等分支也有裸 `docker start`；
3. 预期 SHA 硬编码，且误写为 v6（`c4497e04…`），实际 v14（`2f180cf0…`）；
4. “启动完整性核验”与“权限安全基线”未分开；
5. 无统一启动日志。

## 二、目标

1. 所有 `docker start` / `docker restart` 只能通过统一入口；
2. 启动前核验 SHA、属主、权限；
3. 目标与 SHA 绑定；
4. 日志可靠、不可覆盖、可解析、无损坏行歧义；
5. 状态机覆盖“成功/不匹配/无法读取/不可记录”；
6. 失败不启动、报告、人工恢复；
7. 竞态未根治，依赖权限基线。

## 三、设计

### 3.1 配置来源与保护

#### 3.1.1 唯一来源与严格解析

`deploy.env` 是唯一来源；不保留脚本顶部常量、不读 shell 环境变量覆盖。

- 只接受 `KEY=VALUE`，一行一对；忽略空行与整行 `#` 注释；
- 白名单键：`TARGET_CANDIDATE_SHA`、`TARGET_V14_SHA`、`EXPECTED_OWNER`、`EXPECTED_MODE`；
- 未知键、重复键、缺键 → 失败；
- 不允许引号、空格、续行、变量展开、`export`；
- SHA：`^[0-9a-f]{64}$`；
- OWNER：唯一判定来源 `root:root`；部署前记录仅核对；
- MODE：`^(?:[0-7]{3}|0[0-7]{3})$`；
- 解析失败 → 不启动、记录、报告。

#### 3.1.2 路径、父目录与属主

1. 绝对路径，拒绝相对路径；
2. 从 `/` 到直接父目录逐级 `lstat`（拒绝 symlink）；
3. **属主判定**：
   - 允许 `root`；
   - 非 root 必须**同时**满足：
     a. 在预声明 `TRUSTED_OWNERS` 白名单内；
     b. 系统/服务账号（非普通交互用户），shell 为 `/usr/sbin/nologin` 或 `/bin/false`；
     c. 不属于 `sudo` / `wheel` / `adm` 等提权组；
     d. 能只读核对 `/etc/passwd`、组信息；
   - 任一无法验证 → **失败关闭**；
   - 权限位符合 ≠ 目录可信；
4. 任一级 world-writable → 不启动；
5. group-writable：仅当组内仅 root/可信主体才可接受，否则失败；
6. 文件 root、mode ≤0640、非 symlink；
7. 检查不能消除替换竞态；不宣称可靠防篡改。

#### 3.1.3 读取与使用竞态

- 读取后记录 `inode/mtime/SHA`，使用前再核验；
- 不能根治；依赖权限基线；
- 两次 stat 一致 ≠ 配置安全。

#### 3.1.4 交叉核对

- `TARGET_V14_SHA` = 备份实际 SHA = 部署准备报告基线；
- `TARGET_CANDIDATE_SHA` = 候选 snapshot SHA；
- 不一致 → 中止。

### 3.2 唯一启动入口与状态机

```text
TARGETS = {
  "candidate": TARGET_CANDIDATE_SHA,
  "v14":       TARGET_V14_SHA,
  "recovered-v14": TARGET_V14_SHA,
}

start_verified(target):
  expected_sha = TARGETS[target]        # 未知 target → 立即失败
  读取磁盘 main.py 的 SHA/属主/权限
  核验三项
  追加 precheck（pass/fail）
  fail → 不启动（不写 start_invoked）
  持久化 start_invoked → 失败则不启动
  docker start
  追加 start_result（exit_0/exit_nonzero）；写入失败 → UNRECORDED
  读取容器实际状态；失败/无法识别 → STATE_UNKNOWN
  再次读取磁盘 inode/mtime/SHA；失败 → disk_check_failed
  追加 resolution；写入失败 → UNRECORDED
```

- **只有 `start_verified()` 内部允许 `docker start`**；
- `restart_verified(target)` 只 `docker stop` + 状态检查 + 委托 `start_verified(target)`；
- `running_disk_match` 只证明“巡检时 Running 且磁盘相符”，不证明已加载目标代码。

#### 3.2.1 resolution 判定

| 容器状态 | 磁盘核验 | resolution |
|---|---|---|
| Running | 三项符合 | `running_disk_match` |
| Running | 三项不符 | `running_disk_mismatch` |
| Running | 读取失败/inode/mtime/SHA 不可得 | `disk_check_failed` |
| Docker 状态查询失败/无法识别 | 任意 | `container_state_unknown` |
| Stopped | 任意（未验证） | `stopped_unknown` |
| 任意 | resolution 写入失败 | `resolution_unrecorded` |
| 任意 | start_result 写入失败 | `start_result_unrecorded` |

规则：不得把“无法读取/查询失败/写入失败”转成 `running_disk_match`。

#### 3.2.2 三态映射（v8 固定）

| 对外状态 | 内部 resolution | 含义 |
|---|---|---|
| `RUNNING_UNVERIFIED` | `running_disk_mismatch` / `disk_check_failed` / `resolution_unrecorded`（且容器 Running） | 容器在运行，但磁盘不一致或核验/记录未完成 |
| `STOPPED_UNVERIFIED` | `stopped_unknown`（且容器 Stopped） | 容器停止，无法确认启动结果 |
| `STATE_UNKNOWN_UNVERIFIED` | `container_state_unknown` / `start_result_unrecorded` | 容器状态未知，或无法记录 Docker 是否执行 |

- `start_result_unrecorded` 时，**不得推断 Docker 已执行或未执行**；按 `STATE_UNKNOWN_UNVERIFIED` 处理；
- `resolution_unrecorded` 若容器 Running → `RUNNING_UNVERIFIED`，若 Stopped → `STOPPED_UNVERIFIED`，若容器状态不可读 → `STATE_UNKNOWN_UNVERIFIED`；
- 三种对外状态都只读记录、保留现场、报告；不自动 stop/restart/回滚。

### 3.3 分支矩阵

| 分支 | 启动调用 |
|---|---|
| 正常部署（替换后） | `start_verified(candidate)` |
| 备份失败 | 不自动启动；确认可信 v14 后才 `start_verified(v14)` |
| 备份校验不一致 | 不自动启动、不自动回滚；只有可信 v14 恢复后才 `start_verified(v14)`；否则停止 |
| 临时文件复制/校验失败 | 删临时文件；确认原文件可信后 `start_verified(v14)`；否则停止 |
| `mv` 失败 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败停止 |
| 回滚 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败停止 |
| 启动失败后重试 | 仍 `start_verified(当前 target)` |
| 验证失败（测试 FAIL） | 不自动启动/回滚；报告，由主人决定 |

### 3.4 restart 语义

```text
restart_verified(target):
  docker stop
  检查容器实际状态（失败/仍运行 → 不继续，报告）
  start_verified(target)      # 唯一启动入口
```

禁止裸 `docker restart`。

### 3.5 启动日志（JSONL 事件流）

路径：`/opt/astrbot/shared/记忆/部署日志/start-attempt-<attempt_id>.jsonl`。

#### 3.5.1 日志目录安全前置条件

1. 从 `/` 到日志目录逐级 `lstat`，拒绝 symlink；
2. 属主 root（非 root 按 3.1.2 判据）；
3. 不 world-writable；group-writable 需证明组内仅 root/可信；
4. 日志文件（存在时）非 symlink、root、mode ≤0640；
5. 检查/创建/持久化失败 → 不启动；
6. 权限基线纳入单独评估。

#### 3.5.2 事件模型

```text
{"event":"attempt_created","attempt_id":"...","time":"...","target":"candidate"}
{"event":"precheck","attempt_id":"...","result":"pass|fail",...}
{"event":"start_invoked","attempt_id":"...","time":"..."}
{"event":"start_result","attempt_id":"...","result":"docker_start_exit_0|docker_start_exit_nonzero|start_result_unrecorded","time":"..."}
{"event":"resolution","attempt_id":"...","result":"running_disk_match|running_disk_mismatch|container_state_unknown|disk_check_failed|stopped_unknown|resolution_unrecorded","time":"..."}
{"event":"corrupt_line","attempt_id":"...","line":N,"reason":"missing_newline|invalid_json","time":"..."}
{"event":"recovery","attempt_id":"...","action":"added_line_terminator|isolated_corrupt_line","time":"..."}
```

- 每个事件独立追加；`attempt_id` 关联；每行完整合法 JSON；
- **单写者**：同一 attempt 只允许一个写入者，追加前获取尝试级锁；锁失败 → 不写、不启动。

#### 3.5.3 创建与追加

**A. 首次创建**

1. 受保护目录 `O_CREAT|O_EXCL` 临时文件（拒绝 symlink）；
2. 写 `attempt_created`、`precheck`；precheck fail 只写 fail，不写 `start_invoked`；
3. precheck pass 写 `start_invoked`；
4. 临时文件 `fsync`；
5. 用不覆盖目标的原子创建（`link` 或 `renameat2(RENAME_NOREPLACE)`）生成正式文件；目标已存在 → 失败；
6. 删临时文件；父目录 `fsync`；
7. 全成功才允许 `docker start`。

**B. 已有文件追加**

1. 获取尝试级锁；
2. **逐行 JSON 合法性校验**（见 C）；
3. 以 append 写一条完整事件（一次写完整行）；
4. 校验写入完整；
5. 文件 `fsync`；
6. 任一步失败 → 不启动。

**C. JSON 行合法性检测（v8 新增）**

- 读取文件全部行，逐行 `json.loads`：
  - 每行必须是合法 JSON 对象，且含 `event`、`attempt_id`；
  - 不存在“有换行但 JSON 损坏”的中间行；
- 分类：
  1. **缺行结束符**（最后一行无 `\n`）：原字节保留，追加 `\n` 建立边界，追加 `corrupt_line(reason=missing_newline)` + `recovery(added_line_terminator)`；
  2. **有换行但 JSON 损坏**（解析失败）：原字节保留，不覆盖/不截断；追加 `corrupt_line(line=N, reason=invalid_json)` + `recovery(isolated_corrupt_line)`；
  3. **中间行损坏且后续还有合法行**：说明历史已损坏；**停止写入、报告、不启动**，不尝试修复；
  4. **连续损坏/无法定位边界**：停止写入、报告、不启动；
- 只有确认“最后一条完整合法行”之后，才允许追加新事件；
- 不得覆盖/截断/重写历史字节。

**D. 目录 fsync 失败**

- 正式文件已创建，但父目录 `fsync` 失败：可能留下含 `start_invoked` 的文件；
- 不启动；标记 `state_uncertain`；不假设 Docker 已执行；交只读取证/人工处理。

#### 3.5.4 `invoked` 遗留与 resolution

- 发现 `start_invoked` 遗留：读容器状态与磁盘三项，按 3.2.1 追加 `resolution`；
- 无法完成 → `container_state_unknown` / `disk_check_failed` / `resolution_unrecorded`；
- 原事件保留；不把 `invoked` 当 success。

#### 3.5.5 锁文件安全（v8 新增）

- 锁文件位于受保护日志目录；父目录通过 3.5.1 检查；
- 用 `O_CREAT|O_EXCL` 创建或 `flock` 打开；拒绝 symlink；
- 属主 root、mode `0600`；
- 获取失败 → 不写、不启动；
- 锁只防并发部署，**不阻止不遵守锁的其他写入者**；不能替代权限基线。

### 3.6 静态检查与完整调用链

`grep` 只是基础检查：

1. 审查所有部署脚本及辅助脚本；
2. 检查所有实际执行 Docker 命令的路径（子进程、Python、其它脚本）；
3. 负向测试统一入口外的启动调用；
4. 人工调用链复核；
5. grep 无命中不能宣称无绕过。

### 3.7 测试矩阵

1. deploy.env 解析（缺/多/重复/非法值/权限宽/父目录 world-writable/group-writable/非 root 属主/symlink）；
2. 父目录从 `/` 逐级；非 root 判据（白名单/系统账号/nologin/无提权组）；
3. 读取与使用间替换；
4. 三态映射：RUNNING/STOPPED/STATE_UNKNOWN；
5. resolution：match/mismatch/container_state_unknown/disk_check_failed/stopped_unknown/resolution_unrecorded/start_result_unrecorded；
6. JSONL 首建：O_EXCL、不覆盖原子创建、目标已存在失败、目录 fsync 失败 state_uncertain；
7. JSONL 追加：完整行/缺换行/有换行但 JSON 损坏/中间损坏/连续损坏；
8. 单写者锁：并发拒绝；锁文件 symlink/权限失败；
9. precheck fail 不写 start_invoked；
10. 日志目录/创建/持久化失败 → 不启动；
11. 备份校验不一致：不自动启动/回滚；
12. Docker 非零但容器异常；
13. 负向测试：统一入口外启动被捕获；
14. target/SHA 映射。

### 3.8 竞态

- 0777/0666 下检查到 Docker 加载之间文件可能被替换；
- 配置读取→使用竞态；日志文件/目录可被替换；
- `flock` 不阻止外部写入者；
- 不能宣称竞态消除；权限基线是根治前提。

## 四、现实约束

当前 0777 环境可能无法通过日志/配置路径检查；设计通过后也不能直接施工/部署；先完成权限基线评估与整改；不得为让脚本跑起来放宽 fail-closed。

## 五、风险

1. 竞态未根治（依赖权限基线）；
2. 启动字节一致 ≠ 权限安全；
3. 日志目录可能不满足前置条件，届时 fail-closed 不启动；
4. dry-run 与真实 Docker 差异；
5. grep 不能单独证明无绕过。
