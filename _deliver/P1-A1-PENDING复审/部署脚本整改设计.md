## 〇、v5 返修点

1. `restart_verified` 明确**只调用 `start_verified(target)`**，自身不实现 `docker start`；唯一启动入口仍是 `start_verified`。
2. **日志目录成为启动前置条件**：目录/父目录属主、权限、symlink 检查；检查失败、创建失败、持久化失败 → **不启动**。
3. 日志改为**不可变 JSON Lines 事件流**（`attempt_created` / `start_invoked` / `start_result` / `resolution`），明确持久化语义；`success/failed` 改为 `docker_start_exit_0` / `docker_start_exit_nonzero`，不代表应用就绪或已加载目标代码。
4. 配置解析收紧：父目录从 `/` 逐级检查；group-writable 处理；`MODE` 严格三位/四位；`EXPECTED_OWNER` 单一判定来源。
5. 测试矩阵补日志失败、目录权限、symlink、group-writable、Docker 非零但状态异常。

## 一、现状缺陷（已证实）

1. `p3_deploy_stepA.sh` 的 `BACKUP_MISMATCH` 分支裸 `sudo docker start astrbot`，未执行三项核验；
2. 备份失败、复制失败、`mv` 失败等分支也有裸 `docker start`；
3. 预期 SHA 硬编码，且误写为 v6（`c4497e04…`），实际 v14（`2f180cf0…`）；
4. “启动完整性核验”与“权限安全基线”未分开；
5. 无统一启动日志（expected/actual）。

## 二、目标

1. **所有** `docker start` / `docker restart` 只能通过统一入口；
2. 启动前实际读取磁盘 `main.py`，核验 SHA、属主、权限；
3. 目标与 SHA 绑定，不接受任意组合；
4. 启动日志必须可靠落盘，否则不启动；
5. 失败不启动、报告、人工恢复；
6. 明确竞态未根治，依赖权限基线整改。

## 三、设计

### 3.1 配置来源与保护

#### 3.1.1 唯一来源与严格解析

`deploy.env` 是**唯一来源**；不保留脚本顶部常量、不读 shell 环境变量覆盖。

- 只接受 `KEY=VALUE`，一行一对；忽略空行与整行 `#` 注释；
- **白名单键**：`TARGET_CANDIDATE_SHA`、`TARGET_V14_SHA`、`EXPECTED_OWNER`、`EXPECTED_MODE`；
- 未知键、重复键、缺键 → 失败；
- 不允许引号、空格、续行、变量展开、`export`；
- 值类型校验：
  - SHA：`^[0-9a-f]{64}$`；
  - OWNER：**唯一判定来源是 `root:root`**；部署前记录仅用于核对，不一致即失败（不再保留“或与记录一致”的双标准）；
  - MODE：`^(?:[0-7]{3}|0[0-7]{3})$`（严格三位或四位八进制；拒绝 `06666` 这类五位）；
- 解析失败 → 不启动、记录、报告。

#### 3.1.2 路径与父目录保护

不能只 `stat` 最终文件。启动前检查：

1. `deploy.env` 使用**绝对路径**，拒绝相对路径；
2. **从 `/` 到直接父目录逐级检查**，不能只检查列举的目录：每级 `lstat`（拒绝 symlink），核验属主、权限；
3. **world-writable**：任一级 others 有 `w` → 判定“配置可被替换”，不启动；
4. **group-writable**：任一级 group 有 `w` 时，仅当该组可证明只含 root/可信主体才可接受；无法证明 → 判定不可信，不启动（不能默认 group-writable 安全）；
5. 文件本身：属主 `root`、mode 不宽于 `0640`、非符号链接；
6. 上述检查不能消除“检查后被替换”的竞态；权限基线完成前，**不宣称 `deploy.env` 已获得可靠防篡改保护**。

#### 3.1.3 读取与使用竞态

- 读取后记录文件 `inode/mtime/SHA`，使用前再次核验；不一致 → 中止；
- 仍不能根治：0777 父目录下，其他写入者可在两次检查之间替换；与权限基线整改建立依赖；
- 不能把“两次 stat 一致”写成“配置文件安全”。

#### 3.1.4 交叉核对

- `TARGET_V14_SHA` 必须等于备份实际 SHA 与部署准备报告基线；
- `TARGET_CANDIDATE_SHA` 必须等于候选 snapshot SHA；
- 不一致 → 中止，不启动。

### 3.2 唯一启动入口

```text
TARGETS = {
  "candidate": TARGET_CANDIDATE_SHA,
  "v14":       TARGET_V14_SHA,
  "recovered-v14": TARGET_V14_SHA,
}

start_verified(target):
  expected_sha = TARGETS[target]        # target 未知 → 立即失败，不启动
  读取磁盘 main.py 的 SHA/属主/权限
  核验 SHA == expected_sha
  核验 属主 == EXPECTED_OWNER
  核验 权限 == EXPECTED_MODE
  写 precheck 事件
  三项全过 → 调用受控启动（见 3.5.1 时序）
  任一项失败 → 不启动；写 precheck fail；返回非零
```

- **只有 `start_verified()` 内部允许实际执行 `docker start`**；
- 其它函数（含 `restart_verified`）不得自行调用 `docker start`；
- `start_verified` 只接受 target，不接受调用方传 SHA；
- `TARGETS` 由 `deploy.env` 构建；未知 target 直接失败。

### 3.3 分支矩阵（v5）

| 分支 | 启动调用 |
|---|---|
| 正常部署（替换后） | `start_verified(candidate)` |
| 备份失败 | 不自动启动；保留现场、报告；确认可信 v14 后才 `start_verified(v14)` |
| 备份校验不一致 | **不自动启动、不自动回滚**；只有找到来源可信、SHA 符合 `TARGET_V14_SHA` 的 v14 文件并完成恢复后，才允许 `start_verified(v14)`；无法确认则保持停止 |
| 临时文件复制/校验失败 | 删临时文件；确认原文件可信后 `start_verified(v14)`；无法确认则停止、报告 |
| `mv` 失败 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败则停止、报告 |
| 回滚 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败则停止、报告 |
| 启动失败后重试 | 仍调用 `start_verified(当前 target)`，禁止裸 start/restart |
| 验证失败（测试 FAIL） | 不自动启动/回滚；报告，由主人决定；回滚走 v14 分支 |

### 3.4 restart 语义

- **禁止裸 `docker restart`**；静态检查同时禁止统一入口外的 `docker (start|restart)`；
- `restart_verified(target)` **只做停止与交接，启动必须委托 `start_verified(target)`**：

```text
restart_verified(target):
  docker stop
  检查容器实际状态（失败/仍运行 → 不继续，报告）
  start_verified(target)      # 唯一启动入口；不在本函数内再写 docker start
```

- 不接受“跳过核验直接 restart”。

#### 3.4.1 重启后核验失败：统一状态

- `STOPPED_UNVERIFIED`：容器停止且磁盘文件未通过核验；**保持停止，不自动启动**；保留现场；写日志；报告。
- `RUNNING_UNVERIFIED`：容器已运行但复核失败；**保持当前运行状态，不自动 stop/restart/回滚**；保留现场；写日志；报告；是否停止由主人明确决定。
- 两种状态都只读记录；dsh 不自动执行恢复动作。
- **删除 v3 中“记录并停止/告警”的歧义**：统一为“记录并告警，保持运行，不自动停止”。

### 3.5 启动日志（事件流）

路径：`/opt/astrbot/shared/记忆/部署日志/start-attempt-<attempt_id>.jsonl`。

#### 3.5.1 日志目录安全前置条件（v5 新增）

启动前必须检查日志目录及父目录：

1. 从 `/` 到日志目录逐级 `lstat`，拒绝 symlink；
2. 属主为 `root`；
3. 不 world-writable；group-writable 需证明组内仅 root/可信主体，否则失败；
4. 日志文件（若已存在）不得为 symlink，属主 `root`，mode 不宽于 `0640`；
5. 目录可写由 root 执行；**检查失败、创建失败、持久化失败 → 不得执行 `docker start`**；
6. 日志路径权限基线纳入单独的权限安全评估（当前 0777 目录环境可能不满足，届时保持停止、报告）。

#### 3.5.2 不可变事件流

每次尝试一个 `attempt_id`，JSON Lines 追加事件：

```text
{"event":"attempt_created","attempt_id":"...","time":"...","target":"candidate",...}
{"event":"precheck","attempt_id":"...","result":"pass|fail","expected_sha":"...","actual_sha":"...","owner":"...","mode":"..."}
{"event":"start_invoked","attempt_id":"...","time":"..."}
{"event":"start_result","attempt_id":"...","result":"docker_start_exit_0|docker_start_exit_nonzero","time":"..."}
{"event":"resolution","attempt_id":"...","result":"running_disk_match|running_disk_mismatch|stopped_unknown","time":"..."}
```

- 每个事件独立追加；**不重写已有事件**；同一 attempt 通过 `attempt_id` 关联；
- `start_result` 的 `docker_start_exit_0` 只代表 Docker 命令返回 0，**不代表应用就绪，也不代表已加载目标代码**；
- `docker_start_exit_nonzero` 只代表命令非零，容器实际状态需另行记录；
- JSONL 每行必须是完整合法 JSON。

#### 3.5.3 `invoked` 写入时序（v5 强化）

1. 三项核验通过后，先追加 `start_invoked`；
2. **确认持久化成功**：
   - 文件内容 `fsync`；
   - 若新建文件，使用原子 rename，并对目录执行 `fsync`（确保目录项持久化）；
   - 写入返回可验证；
3. 持久化失败 → **不启动**、报告；
4. 再调用 `docker start`；
5. 根据 Docker 返回追加 `start_result`；
6. 中断则保留 `start_invoked`，后续只读取证。

#### 3.5.4 `invoked` 遗留与 `resolution`

发现 `start_invoked` 遗留时，读容器状态与磁盘三项，追加 `resolution`：

- Running 且磁盘三项符合预期 → `running_disk_match`；
- Running 但磁盘三项不一致 → `running_disk_mismatch`；
- Stopped → `stopped_unknown`；
- **不使用 `recovered_success`**；只证明“巡检时运行且磁盘相符”，不证明容器实际加载的代码字节；
- 原事件保留，`resolution` 独立追加；不把 `invoked` 当 success。

### 3.6 静态检查 + 分支测试

- 静态检查：`grep -nE 'docker (start|restart)' deploy.sh`，统一入口外出现即失败；
- 分支测试：备份失败、备份校验不一致、复制失败、`mv` 失败、回滚、启动失败重试，断言“只走统一入口、失败不启动、事件流完整、非零退出”；
- dry-run + 故障注入；
- 补充测试：
  1. `deploy.env` 解析（缺/多/重复/非法值/权限宽/父目录 world-writable/group-writable/symlink）；
  2. 父目录从 `/` 逐级检查；
  3. 读取与使用间替换（两次 inode/mtime 不一致）；
  4. 重启后失败：`STOPPED_UNVERIFIED` / `RUNNING_UNVERIFIED`，断言不自动 stop/restart/回滚；
  5. `start_invoked` 时序：在 docker start 前中断，确认已持久化；resume 追加 `running_disk_match` 等；
  6. 日志目录权限不合格 / 文件创建失败 / 持久化失败 → 断言不启动；
  7. 备份校验不一致：断言不自动启动、不自动回滚；
  8. Docker 非零返回但容器状态异常（如 Running）→ 记录 `docker_start_exit_nonzero` + 实际状态，不自动处理；
  9. target/SHA 映射：未知 target/不匹配 → 失败。

### 3.7 校验与启动之间的竞态

- 目录 0777、文件 0666；`start_verified` 检查完到 Docker 加载文件之间，文件仍可能被替换；
- `deploy.env` 自身也有“读取→使用”竞态，父目录 0777 时同样可被替换；
- 部署脚本内部 `flock` 只能防并发部署，不能阻止其他写入者；
- 缓解：窗口最小化、启动后复核 inode/mtime/SHA、配置读取两次核验；
- **不能宣称竞态已消除**；权限基线整改是根治前提。

## 四、风险

1. 竞态未根治（依赖权限基线）；
2. `start_verified` 只保证“启动字节与目标一致”，权限 0666 下核验一致不代表权限安全；
3. 日志目录当前可能不满足安全前置条件（0777 环境），届时按 fail-closed 不启动；
4. 分支测试若只 dry-run，可能与真实 Docker 行为有差异；
5. 配置与启动文件均可能被 0777 环境下替换。
