# 部署脚本整改设计（顶层事务 + 统一启动入口）v19

- **文档类型**：整改设计（不施工、不动线上）
- **任务**：解决部署脚本所有分支绕过 `start_verified()` 的问题
- **版本**：v19（v18 返修；威胁模型、迁移失败回收、cgroup 失败事件、锁 fd 验证、释放顺序）
- **日期**：2026-11-22
- **更新时间**：2026-11-22 18:15（Asia/Shanghai）
- **当前状态**：**修订完成，待复审；未修改脚本、未改线上**

## 〇、v19 返修点

1. **威胁模型**：明确保护范围排除拥有 root/Docker socket/等效系统权限的主体；不再笼统声称“禁止外部迁入”；supervisor 只迁入目标 CLI、不迁出（程序约束）。
2. **迁移失败回收**：CLI 子进程在迁移确认前阻塞、不 execve；迁移失败 → 终止 + `waitpid` 确认退出 → 才记 `not_sent`；C 空不足以证明 C 外子进程已清理。
3. **cgroup 创建失败事件**：新增 `cgroup_create_failed` / `cgroup_verify_failed`，在 supervisor 启动前，确定未发送。
4. **锁 fd 验证**：不把 `FD_CLOEXEC=false` 当证明；supervisor 通过 `/proc/<pid>/fd` 只读核验 CLI 持有 L；明确残余风险。
5. **释放顺序**：C 空 → 回收 → 写并持久化 start_result → resolution → supervisor 关 L → 退出 → 主进程确认后关 L；日志失败不提前释放。

## 一、威胁模型与生命周期

### 1.1 威胁模型

**保护目标**：防止项目内部脚本/普通本地用户绕过顶层事务，制造并发部署或绕过启动核验。

**明确不防御**：

- 拥有 `root`、Docker socket 写权限、或等效系统管理权限的主体；
- 这类主体可以直接操作 Docker/cgroup，脚本无法阻止；
- 本文中“禁止迁出/外部迁入”是**程序行为约束**，不是内核强制；root 仍可迁移；
- 不能把脚本内部约束夸大为系统级隔离。

### 1.2 边界图

```text
C 外（持锁 fd L）：
  主进程 deploy.sh        （持 L；等待 supervisor）
  supervisor              （持 L；只迁入目标 CLI，不迁出）

C 内（Docker 操作）：
  Docker CLI              （继承 L；属于 C）
  CLI 受控后代            （继承 L；属于 C）
```

| 进程 | 在 C 内 | 持 L | 创建者 | 退出条件 |
|---|---|---|---|---|
| 主进程 | 否 | 是 | 入口 | 事务结束、supervisor 退出 |
| supervisor | 否 | 是 | 主进程 | C 空、结果持久化后 |
| Docker CLI | 是 | 是（继承） | supervisor | CLI 退出 |
| CLI 后代 | 是 | 是（默认） | CLI | 各自退出 |

- 主进程/supervisor 不在 C 内：C 空可达；
- 只有 CLI 及受控后代在 C 内；
- 锁 fd `L` 由主进程、supervisor、CLI 及后代持有；`FD_CLOEXEC=false`；
- CLI 持 L 通过 `/proc/<pid>/fd` 核验，不靠“默认继承”假设。

## 二、现状缺陷（已证实）

1. `p3_deploy_stepA.sh` 的 `BACKUP_MISMATCH` 分支裸 `sudo docker start astrbot`；
2. 备份失败、复制失败、`mv` 失败等分支也有裸 `docker start`；
3. 预期 SHA 硬编码，且误写为 v6（`c4497e04…`），实际 v14（`2f180cf0…`）；
4. “启动完整性核验”与“权限安全基线”未分开；
5. 无统一启动日志。

## 三、目标

1. 所有部署动作只经唯一顶层事务；
2. 全局锁覆盖完整事务，包括父进程崩溃与 supervisor 崩溃；
3. 启动前核验 SHA、属主、权限；
4. 日志与锁目录使用安全目录 fd，日志文件本身做身份核验；
5. 启动意图、调用开始、命令结果、记录结果四层分开；
6. 崩溃窗口中的状态不被错误解释；
7. 不自动重试；未知结果停止自动操作；
8. 竞态未根治，依赖权限基线。

## 四、设计

### 4.1 配置来源与保护

#### 4.1.1 唯一来源与初始信任根

`deploy.env` 是唯一来源；不保留脚本顶部常量、不读 shell 环境变量覆盖。

**初始信任根**：

1. `deploy.env` 必须 `root:root`、mode `0640`、非 symlink；
2. 从 `/` 到直接父目录逐级 `lstat`：每级 `root` 属主、非 symlink、不含 world/group write；
3. 任一级不满足 → 失败，**不读取配置内容**；
4. 通过后才读取 `TRUSTED_OWNERS`、`PRIVILEGED_GROUPS`；
5. 不得用配置内白名单证明配置自身路径可信。

**解析**：

- `KEY=VALUE` 一行一对；忽略空行/整行 `#`；
- 白名单键：`TARGET_CANDIDATE_SHA`、`TARGET_V14_SHA`、`EXPECTED_OWNER`、`EXPECTED_MODE`、`TRUSTED_OWNERS`、`PRIVILEGED_GROUPS`；
- 未知/重复/缺键 → 失败；不允许引号/空格/续行/变量展开/`export`；
- SHA `^[0-9a-f]{64}$`；OWNER `root:root`；MODE `^(?:[0-7]{3}|0[0-7]{3})$`；
- `TRUSTED_OWNERS`：`name:uid:gid` 逗号分隔，含 `root:0:0`；
- `PRIVILEGED_GROUPS`：组名逗号分隔，至少 `sudo,wheel,adm`；
- 解析失败 → 不启动、记录、报告。

#### 4.1.2 路径、父目录与属主

1. 绝对路径；
2. 配置路径按 4.1.1（仅 root）；
3. 其它路径允许：`root:0:0`；或白名单内且 passwd `name/uid/gid` 一致、系统账号（`100<=uid<=999` 或显式标注）、`nologin`/`false`、主 GID 与附加组均不在 `PRIVILEGED_GROUPS`；组来源可读；否则失败；
4. 任一级 world-writable → 不启动；
5. group-writable：主 GID 成员 + `getent group` 附加成员，存在非白名单 → 失败；组信息不完整 → 失败；
6. 文件 root、mode ≤0640、非 symlink；
7. 不宣称防篡改。

#### 4.1.3 读取与使用竞态

- 读取后记录 `inode/mtime/SHA`，使用前再核验；
- 不能根治；依赖权限基线。

#### 4.1.4 交叉核对

- `TARGET_V14_SHA` = 备份实际 SHA = 部署准备报告基线；
- `TARGET_CANDIDATE_SHA` = 候选 snapshot SHA；
- 不一致 → 中止。

### 4.2 唯一顶层事务与入口边界

```text
deploy.sh <action> [target]        # 唯一项目入口
  deploy_transaction(action, target):
    acquire_global_lock()          # 失败 → 零改动、退出
    try:
      ... 备份 / 替换 / 恢复 / stop / start_verified / resolution ...
    finally:
      release_attempt_lock()
      close(L)                     # 仅当 C 空、supervisor 已退出
```

- 项目内部：所有项目自有脚本只经 `deploy.sh`；`lib/` 禁止独立执行；`start_verified` 不导出；
- 系统级：sudoers、Docker socket 权限、ACL 决定外部主体能否直接调用 Docker；**不通过 sudo 传递 fd**；
- 未实现系统级控制时，明确：**不保证拥有 Docker 权限的外部主体无法绕过 `deploy.sh`**；
- 负向测试：内部辅助脚本、内部调用链、系统外部直接 Docker（第三类不能仅靠脚本测试证明）。

#### 4.2.1 `start_verified`（内部）与启动事件

```text
start_verified(target):
  expected_sha = TARGETS[target]
  读取磁盘 main.py 的 SHA/属主/权限
  核验三项
  追加 precheck（pass/fail）
  fail → 不启动（不写 start_invoked）
  持久化 start_invoked          # 仅“意图”
  持久化 start_call_begin       # “即将调用”；失败 → 不调用、不启动
  创建并验证 cgroup C（叶节点）
    失败 → start_not_sent(cgroup_create_failed/cgroup_verify_failed) → resolution(not_sent,no)
  spawn supervisor（在 C 外；继承 L；核验 fd 继承）
    失败 → start_not_sent(supervisor_spawn_failed) → resolution
  supervisor fork CLI（阻塞在 pipe，未 execve）
  supervisor 将 CLI 写入 C
    失败 → 终止+waitpid 确认 → start_not_sent(cli_cgroup_enter_failed) → resolution
  放行 execve；exec 失败 → start_not_sent(cli_exec_failed) → resolution
  C 空 → 回收子进程 → 写 start_result（exit_0/exit_nonzero/result_unknown）
  写 resolution
```

- `start_invoked`：意图；`start_call_begin`：即将调用；都不是“命令已发出”；
- 明确未发送时写 `start_not_sent`；
- 崩溃规则：有 `start_result` → 用结果；有 `start_not_sent` → `not_sent`；只有 invoked/call_begin → `result_unknown`；
- **`result_unknown` 停止自动操作**；重试需独立人工授权事务。

#### 4.2.2 三维状态与对外映射

| 维度 | 取值 |
|---|---|
| `attempt_result` | `exit_0` / `exit_nonzero` / `not_sent` / `result_unknown` / `unrecorded` |
| `command_sent` | `yes` / `no` / `unknown`（仅事后） |
| `container_state` | `running` / `stopped` / `unknown` |
| `disk_verification` | `match` / `mismatch` / `check_failed` |

| container_state | disk_verification | 对外状态 |
|---|---|---|
| running | match | `RUNNING_DISK_MATCH` |
| running | mismatch | `RUNNING_DISK_MISMATCH` |
| running | check_failed | `RUNNING_DISK_UNVERIFIED` |
| stopped | 任意 | `STOPPED_UNVERIFIED` |
| unknown | 任意 | `STATE_UNKNOWN_UNVERIFIED` |

- `RUNNING_DISK_MATCH` 不代表已加载目标代码；
- 只读记录、保留现场、报告；不自动 stop/restart/回滚。

#### 4.2.3 UNRECORDED 边界

- `start_result` 只表示实际成功持久化的结果：`exit_0`/`exit_nonzero`/`result_unknown`；
- 写入失败 → 进程内 `attempt_result=unrecorded`；
- 后续 resolution 可带 `attempt_result=unrecorded`；
- resolution 也失败 → 保留现场与已有日志，不声称完整；
- 四个事实分开：启动意图、调用开始、命令结果、记录是否成功。

### 4.3 分支矩阵（全部经顶层事务，无自动重试）

| 分支 | 事务内动作 |
|---|---|
| 正常部署 | 备份 → 替换 → `start_verified(candidate)` |
| 备份失败 | 不启动；报告；可信 v14 恢复后才 `start_verified(v14)` |
| 备份校验不一致 | 不自动启动、不自动回滚；可信 v14 恢复后才 `start_verified(v14)`；否则停止 |
| 临时文件复制/校验失败 | 删临时文件；确认原文件可信后 `start_verified(v14)`；否则停止 |
| `mv` 失败 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败停止 |
| 回滚 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败停止 |
| 启动结果未知/非零 | 停止自动操作；不自动重试；报告主人；重试需独立人工授权事务 |
| 验证失败（测试 FAIL） | 不自动启动/回滚；报告，由主人决定 |

### 4.4 restart 语义

```text
deploy_transaction("restart", target):
  ...（全局锁已持有）...
  docker stop（supervisor/cgroup 管理，同 4.5.7）
  检查容器实际状态
  start_verified(target)
```

禁止裸 `docker restart`。

### 4.5 启动日志（JSONL）

路径：`/opt/astrbot/shared/记忆/部署日志/start-attempt-<attempt_id>.jsonl`。

#### 4.5.1 日志目录与日志文件 fd 核验

**目录**：从 `/` 逐级 `openat` + `O_NOFOLLOW` + `fstat`；保持 dirfd 链；创建/正式化/追加只用 dirfd。

**创建**：`openat(logdir_fd, "....tmp", O_CREAT|O_EXCL|O_NOFOLLOW, 0600)`；`fstat` 核验 regular/root/0600；记录 `dev/ino`。

**正式化**：`linkat`/`renameat2(RENAME_NOREPLACE)`；`fstatat` 核验目录项；与临时文件 `dev/ino` 一致。

**追加**：`openat(logdir_fd, name, O_RDWR|O_APPEND|O_NOFOLLOW)`；`fstat` 核验 regular/属主/权限；`fstatat` 比较 `dev/ino`；不一致失败。

#### 4.5.2 事件 Schema（闭合）

**通用规则**：所有字段值为 JSON 字符串；`additionalProperties=false`；未知字段拒绝。

**字段类型**：

| 字段 | JSON 类型 | 格式/枚举 |
|---|---|---|
| `event` | string | 枚举 |
| `attempt_id` | string | `^[a-f0-9]{32}$` |
| `time` | string | `YYYY-MM-DDTHH:MM:SSZ`，日历有效 |
| `target` | string | candidate/v14/recovered-v14 |
| `result` | string | precheck: pass/fail；start_result: exit_0/exit_nonzero/result_unknown |
| `reason` | string | call_declined/cgroup_create_failed/cgroup_verify_failed/supervisor_spawn_failed/cli_cgroup_enter_failed/cli_exec_failed/operator_cancel/precondition_changed |
| `attempt_result` | string | exit_0/exit_nonzero/not_sent/result_unknown/unrecorded |
| `command_sent` | string | yes/no/unknown |
| `container_state` | string | running/stopped/unknown |
| `disk_verification` | string | match/mismatch/check_failed |
| `source` | string | normal/recovery（resolution 可选） |
| `expected_sha`/`actual_sha` | string | `^[0-9a-f]{64}$` |
| `owner` | string | `^[a-z_][a-z0-9_-]{0,31}:[a-z_][a-z0-9_-]{0,31}$` |
| `mode` | string | `^0?[0-7]{3}$` |
| `action` | string | added_line_terminator |

**逐事件允许字段（闭合）**：

| 事件 | 允许字段（无其它） | 必需 |
|---|---|---|
| attempt_created | event, attempt_id, time, target | 全部 |
| precheck | event, attempt_id, time, result, expected_sha?, actual_sha?, owner?, mode? | event, attempt_id, time, result |
| start_invoked | event, attempt_id, time | 全部 |
| start_not_sent | event, attempt_id, time, reason | 全部 |
| start_call_begin | event, attempt_id, time | 全部 |
| start_result | event, attempt_id, time, result, command_sent | 全部 |
| resolution | event, attempt_id, time, attempt_result, command_sent, container_state, disk_verification, source? | 除 source 外全部 |
| recovery | event, attempt_id, time, action | 全部 |

**状态机**：

```text
attempt_created → precheck
  precheck=fail → 结束（终止）
  precheck=pass → start_invoked → start_call_begin
    → start_not_sent（cgroup/supervisor/CLI 失败，确定未发送）→ resolution（终止）
    → start_result → resolution（终止）
recovery：仅非终止事件缺换行时追加；最多一次
```

**交叉约束**：

- `precheck=fail` 不产生 `start_invoked`/`resolution`；
- `start_not_sent` 允许在 `start_call_begin` 之后；后必须 `resolution`；
- `start_not_sent.reason` ∈ `cgroup_create_failed/cgroup_verify_failed/supervisor_spawn_failed/cli_cgroup_enter_failed/cli_exec_failed/call_declined/operator_cancel/precondition_changed`；
- `start_result.command_sent`：`exit_0`/`exit_nonzero` → `yes`；`result_unknown` → `unknown`；
- `resolution.command_sent`：`exit_0`/`exit_nonzero` → `yes`；`not_sent` → `no`；`result_unknown`/`unrecorded` → `unknown`；
- `resolution.source=recovery` 仅用于 supervisor 崩溃恢复；不伪造 `start_result`；
- `container_state`/`disk_verification` 独立；
- `recovery` 不改变业务状态。

#### 4.5.3 严格 JSON 校验

对象、拒绝重复键/`NaN`/`Infinity`、按 4.5.2 校验；非法行按 4.5.4。

#### 4.5.4 JSON 合法性处理（含终止事件）

| 情况 | 处理 |
|---|---|
| 合法 + 有换行 | 可追加 |
| 合法 + 无换行，终止事件 | 只补 `\n` + `fsync`；不追加 `recovery` |
| 合法 + 无换行，非终止事件 | 补 `\n` + `fsync` → `recovery` + `fsync`；最多一次 |
| 非法 + 无/有换行 | 停止追加、只读取证、不启动 |
| 中间行非法 | 停止追加、只读取证、不启动 |
| 连续非法/无法定位 | 停止追加、只读取证、不启动 |

#### 4.5.5 首次创建与追加（含创建失败事件）

**锁顺序**：全局锁 → attempt 锁；释放 attempt → 全局。

**A. 首次创建（precheck=pass）**

1. 全局锁已持有；获取 attempt 锁；
2. 创建临时文件（`O_CREAT|O_EXCL|O_NOFOLLOW`）；
3. 写 `attempt_created`；
4. 写 `precheck`；
5. 写 `start_invoked`；
6. 写 `start_call_begin`（失败 → 不调用、不启动）；
7. 临时文件 `fsync`；
8. 不覆盖原子创建正式文件；目标已存在失败；
9. 删除临时文件；
10. 目录 `fsync`；
11. 全部成功才允许创建 C/spawn supervisor；
12. 释放 attempt 锁。

**B. 首次创建（precheck=fail）**

1. 写 `attempt_created`；
2. 写一条 `precheck(fail)`；
3. 临时文件 `fsync`；
4. 原子创建正式文件；
5. 删除临时文件；
6. 目录 `fsync`；
7. 直接返回，绝不 spawn；不产生 `resolution`。

**C. 失败矩阵（含 cgroup 与迁移回收）**

| 失败步骤 | 可能状态 | 继续？ | 启动？ | 现场 |
|---|---|---|---|---|
| 临时文件创建失败 | 无文件 | 否 | 否 | 报告 |
| 临时文件 `fstat` 失败 | 身份未证 | 否 | 否 | 保留，只读取证 |
| 事件写入失败 | 临时文件残缺 | 否 | 否 | 保留临时文件 |
| `start_call_begin` 写入失败 | invoked 存在、无 call_begin | 否 | 否 | 保留，只读取证 |
| 临时文件 `fsync` 失败 | 临时文件存在 | 否 | 否 | 保留 |
| 正式文件创建失败 | 临时文件存在、目标无 | 否 | 否 | 保留临时文件 |
| 正式化 `fstatat` 失败 | 目录项未证 | 否 | 否 | 保留，只读取证 |
| 正式化 `dev/ino` 不一致 | 身份不匹配 | 否 | 否 | 保留，只读取证 |
| 临时文件删除失败 | 正式文件存在、临时残留 | 否 | 否 | 保留残留，报告 |
| 目录 `fsync` 失败 | 正式文件可能已存在 | 否 | 否 | 标记 `state_uncertain` |
| **cgroup 创建失败** | 无 C | 否 | 否 | `start_not_sent(cgroup_create_failed)` |
| **cgroup 验证失败** | C 不可用 | 否 | 否 | `start_not_sent(cgroup_verify_failed)` |
| **supervisor spawn 失败** | 无 supervisor | 否 | 否 | `start_not_sent(supervisor_spawn_failed)` |
| **CLI 进入 C 失败** | CLI 未 exec | 否 | 否 | 终止+waitpid 确认 → `start_not_sent(cli_cgroup_enter_failed)` |
| **CLI exec 失败** | CLI 未执行 | 否 | 否 | `start_not_sent(cli_exec_failed)` |

**D. 追加（含身份核验）**

1. 全局锁已持有；获取 attempt 锁；
2. 日志文件 `fstat`/`fstatat` 身份核验；
3. 严格 JSON 校验；
4. append 一条完整事件；
5. 校验完整；`fsync`；
6. 任一步失败 → 不追加、不启动、保留现场、只读取证；
7. 释放 attempt 锁。

#### 4.5.6 锁设计

**全局部署互斥锁**：

- 路径固定；目录链从 `/` 逐级 `openat` + `fstat`；
- `openat(lockdir_fd, "deploy.lock", O_RDWR|O_CREAT|O_NOFOLLOW, 0600)`；
- `fstat` 核验 regular/root/0600；`fstatat` 比较 `dev/ino`；
- `flock(LOCK_EX|LOCK_NB)`；
- 锁目录必须 root 且不可被外部替换；
- 获取失败 → 零改动、退出。

**attempt 日志锁**：同目录、同一套 fd/fstat/flock 规则。

#### 4.5.7 监督进程、cgroup 与 Docker 子进程

**威胁模型边界**：

- 保护对象：项目内部脚本/普通本地用户；
- 不防御：root、Docker socket 写权限、等效系统管理权限的主体；其可直接操作 Docker/cgroup；
- “禁止迁出/外部迁入”是程序约束，不是内核强制。

**cgroup C**：

- 叶节点：不创建子 cgroup，不写 `subtree_control`；
- 属主 root、mode `0700`（cgroup 文件通常 root 可写；不依赖 mode 阻止 root）；
- supervisor 只执行“将目标 CLI 迁入 C”，不执行迁出；
- 外部迁入由系统权限决定；超范围不宣称防御。

**启动顺序**：

1. 主进程打开锁 fd `L`（`CLOEXEC=false`）；
2. 创建 cgroup C（叶节点）；验证无子 cgroup、`cgroup.procs` 可读写、权限；
3. 失败 → `start_not_sent(cgroup_create_failed/cgroup_verify_failed)`；此时 supervisor/CLI 未启动，确定未发送；
4. `fork/exec` supervisor（C 外；继承 L；核验 fd 继承）；
5. supervisor `fork` CLI 子进程；子进程**阻塞在 pipe**，不 execve；
6. supervisor 将 CLI 写入 `C/cgroup.procs`；
7. 迁移失败 → 关闭 pipe/终止子进程 → `waitpid` 确认退出 → `start_not_sent(cli_cgroup_enter_failed)`；**C 空不能证明 C 外子进程已清理**；
8. 迁移成功 → 通过 pipe 放行 `execve`；
9. exec 成功/失败用 pipe（CLOEXEC 于 exec 成功）区分；失败 → `start_not_sent(cli_exec_failed)`；
10. CLI 执行；supervisor 轮询 `C/cgroup.procs` 为空；
11. C 空 → 回收子进程（`waitpid`）→ 写并持久化 `start_result` → 写并持久化 `resolution`；
12. 结果持久化后 → supervisor 关闭自己的 L → 退出；
13. 主进程等待 supervisor 退出 → 关闭自己的 L。

- 进入 C 成功 ≠ exec 成功；
- 无 docker socket 权限 → fail-closed，不通过 sudo；
- 调用链不得包含 `sudo` 或关闭 fd 的中间程序。

**锁 fd 验证**：

- 主进程/supervisor 持 L 是主要保证；
- CLI 继承 L（`FD_CLOEXEC=false`）是附加保证；
- supervisor 通过 `/proc/<cli_pid>/fd` 只读检查是否含 L（inode 匹配）；
- 若 CLI 未持有 L → 记录、停止/报告；**不宣称锁绝对安全**；
- 残余风险：主进程+supervisor 同时崩溃且 CLI 关闭 L → 锁可能提前释放；文档明确该风险，不能写成“已证明”。

**结果与释放顺序（唯一）**：

1. C 内操作全部结束（`cgroup.procs` 空）；
2. 回收 CLI/子进程（`waitpid`）；
3. 写并持久化 `start_result`；
4. 写并持久化 `resolution`；
5. 日志失败 → `unrecorded`/`result_unknown`，保留现场；
6. supervisor 关闭自己的 L；
7. supervisor 退出；
8. 主进程确认退出后关闭 L；
9. **不得为尽快释放锁而提前结束事务**。

**信号**：

- 主进程 SIGINT/SIGTERM → 转事务中断，通知 supervisor；
- supervisor 向 C 内进程 SIGTERM，超时 SIGKILL；
- 清理中再次信号 → 不再嵌套清理，保留现场。

**父进程/supervisor 崩溃**：

- 主进程 SIGKILL：L 仍由 supervisor + CLI 持有 → 锁不释放；
- supervisor 崩溃：L 仍由 CLI 持有；主进程检测退出，检查 C：
  - 非空 → 等待/报告，不补事件；
  - 空 → 只读核查，追加 `resolution(source=recovery)`；不补 `start_result`；
- CLI 崩溃：C 空 → supervisor 回收并释放；
- 所有持有者崩溃：L 全部关闭 → 锁释放；此时 C 无成员（残余风险已声明）。

### 4.6 入口边界（内部/系统分层）

- 项目内部：`deploy.sh` 唯一入口；`lib/` 禁止独立执行；`start_verified` 不导出；
- 系统级：sudoers、Docker socket 权限、ACL 决定外部主体能否直接调用 Docker；
- 未实现系统级控制时，明确：**不保证拥有 Docker 权限的外部主体无法绕过 `deploy.sh`**；
- 负向测试：内部辅助脚本、内部调用链、系统外部直接 Docker（第三类不能仅靠脚本测试证明）。

### 4.8 竞态

- 0777/0666 下检查到 Docker 加载之间文件可能被替换；
- 配置读取→使用竞态；日志/锁目录可被替换；
- `flock` 不阻止外部写入者；
- 不能宣称竞态消除；权限基线是根治前提。

## 五、现实约束

当前 0777 环境可能无法通过配置/日志/锁目录检查；cgroup v2 可能不可用；设计通过后也不能直接施工/部署；先完成权限基线评估与整改；不得为让脚本跑起来放宽 fail-closed。

## 六、风险

1. 竞态未根治（依赖权限基线）；
2. 启动字节一致 ≠ 权限安全；
3. 日志/锁目录可能不满足前置条件，届时 fail-closed 不启动；
4. cgroup 不可用/权限不足 → fail-closed；
5. 系统级 Docker 权限无法由脚本保证；
6. 残余风险：主进程+supervisor 同时崩溃且 CLI 关闭 L → 锁可能提前释放（已声明，不宣称绝对）。
