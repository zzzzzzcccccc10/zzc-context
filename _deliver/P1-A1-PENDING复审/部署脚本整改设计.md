# 部署脚本整改设计（start_verified 统一入口）

- **文档类型**：整改设计（不施工、不动线上）
- **任务**：解决部署脚本所有分支绕过 `start_verified()` 的问题
- **版本**：v1
- **日期**：2026-11-22
- **更新时间**：2026-11-22 15:00（Asia/Shanghai）
- **当前状态**：**设计完成，待复审；未修改脚本、未改线上**

## 一、现状缺陷（已证实）

1. 第一次备份脚本 `p3_deploy_stepA.sh` 的 `BACKUP_MISMATCH` 分支直接 `sudo docker start astrbot`，没有执行 3.3.1 三项核验；
2. 备份失败、复制失败、`mv` 失败等分支也存在裸 `docker start`；
3. 预期 SHA 硬编码在脚本里，且写成了 v6（`c4497e04…`），与实际 v14（`2f180cf0…`）不符；
4. “启动完整性核验”与“权限安全基线”没有分开；
5. 没有统一的启动日志（expected/actual 三项）。

## 二、目标

1. **所有** `docker start` / `docker restart` 只能通过 `start_verified()`；
2. 启动前实际读取磁盘 `main.py`，核验 SHA、属主、权限；
3. 预期值单一来源，执行前打印；
4. 失败不启动、报告、人工恢复；
5. 启动尝试留痕（JSON 日志），可审计。

## 三、设计

### 3.1 单一配置

`deploy.env`（或脚本顶部常量，唯一来源）：

```text
V14_SHA=2f180cf0be727671a08ad98a5a15fd764bdc1bfe7867c939f6feeb12185550f0
CAND_SHA=bba95b712d6d0708ed23c34a97f55c2375ea66b4e2bab3b8995bd2fb26de627f
OWNER=root:root
MODE=666          # 当前既有权限；权限基线另议（见权限专项评估）
```

- 执行前打印 `V14_SHA`/`CAND_SHA`/`OWNER`/`MODE`，并与部署准备报告交叉核对；
- 若配置缺失或格式不符，直接中止，不启动。

### 3.2 `start_verified()` 契约

```text
start_verified(target_label, expected_sha):
  1. 读取磁盘 main.py 的 SHA/属主/权限
  2. 核验 SHA == expected_sha
  3. 核验 属主 == OWNER
  4. 核验 权限 == MODE
  5. 写启动尝试日志（time/target/expected/actual/result）
  6. 三项全过 → docker start
  7. 任一项失败 → 不启动；输出 expected/actual；返回非零
```

- `target_label` 只能是 `candidate` / `v14` / `recovered-v14` 等枚举；
- 启动失败后需要再次 `start`/`restart` 时，仍必须调用 `start_verified`（不允许裸 start）；
- **边界**：`start_verified` 只证明“启动的字节与目标版本一致”；权限若本身是 0666，核验一致**不代表权限安全**（见权限专项评估）。

### 3.3 分支矩阵

| 分支 | 启动目标 | 调用 |
|---|---|---|
| 正常部署（替换后） | candidate | `start_verified(candidate, CAND_SHA)` |
| 备份失败 | 原 v14 | `start_verified(v14, V14_SHA)` |
| 备份校验不一致 | 原 v14 | 先确认/恢复原文件，再 `start_verified(v14, V14_SHA)` |
| 临时文件复制/校验失败 | 原 v14 | 删临时文件，`start_verified(v14, V14_SHA)` |
| `mv` 失败 | v14 恢复 | 恢复备份，`start_verified(recovered-v14, V14_SHA)` |
| 回滚 | v14 | 恢复备份，`start_verified(recovered-v14, V14_SHA)` |
| 启动失败再 start | 当前目标 | `start_verified(当前目标, 对应 SHA)` |
| 验证失败（测试 FAIL） | 不自动启动/不自动回滚 | 报告，由主人决定；回滚时走 v14 分支 |

### 3.4 禁止裸启动

- 脚本静态检查：`grep -nE 'docker (start|restart)' deploy.sh`，除 `start_verified` 内部外出现即失败；
- CI/本地测试用 `shellcheck` + 自定义 grep；
- 代码评审检查该 grep 结果。

### 3.5 启动日志

- 路径：`/opt/astrbot/shared/记忆/部署日志/start-attempt-<timestamp>.json`；
- 字段：`time/target/expected_sha/actual_sha/owner/mode/result`；
- 失败也写日志（result=fail），便于复盘；
- 日志不写正文/敏感内容。

### 3.6 测试计划（不执行）

1. **dry-run**：`START_VERIFIED_DRY_RUN=1`，只核验不启动，覆盖正常/备份失败/校验失败/回滚/启动失败重试；
2. **故障注入（隔离环境）**：模拟 SHA 不符、属主不符、权限不符、`docker start` 失败，断言“不启动 + 日志 + 非零退出”；
3. **静态检查**：grep 裸 start/restart；
4. **交叉核对**：`deploy.env` 与部署准备报告 SHA 一致。

### 3.7 迁移步骤

1. 评审本设计；
2. 在 `zzc` 新分支实现脚本（不改线上）；
3. 隔离环境跑 dry-run + 故障注入；
4. 提交 diff/日志，复审；
5. 部署脚本本身不部署到线上，仅在部署时由 dsh 执行。

## 四、风险

- `start_verified` 只保证“启动字节一致”，不保证权限安全；
- 权限基线若未定，`MODE` 只能是“当前既有值”，属于“一致性核验”而非“安全基线”；
- 启动日志目录本身权限也需评估（0666/0777 风险）；
- 分支矩阵需与部署准备报告同步，避免再次出现预期值错写。
