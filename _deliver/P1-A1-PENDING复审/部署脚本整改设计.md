- **版本**：v9（v8 返修；JSON 损坏隔离、三维状态、非 root 判据、全局/attempt 锁、UNRECORDED 边界）
- **日期**：2026-11-22
- **更新时间**：2026-11-22 16:15（Asia/Shanghai）
- **当前状态**：**修订完成，待复审；未修改脚本、未改线上**

## 〇、v9 返修点

1. **JSON 损坏不再“原地恢复”**：先判换行、再独立判 JSON；只有“JSON 合法但缺换行”可补 `\n` 继续；任何非法 JSON 行（末尾/中间）→ 停止追加、转只读取证、不启动，不声称已恢复。
2. **三维状态**：`attempt_result`（本次启动调用结果）、`container_state`（实际容器状态）、`disk_verification`（磁盘核验）分别记录；删除“一个 STATE_UNKNOWN 承担多种含义”。
3. **非 root 判据可执行**：`TRUSTED_OWNERS`、`PRIVILEGED_GROUPS` 纳入 `deploy.env` 白名单；组成员来源限定；无法判定 → 失败关闭。
4. **两级锁**：全局部署互斥锁（覆盖完整 stop→核验→start 临界区）+ attempt 日志锁；明确首次创建/后续打开/生命周期/异常释放。
5. **UNRECORDED 边界**：它是进程内故障结果，不是持久化事件；Docker 返回、命令异常、是否发出、日志失败四种事实分开；不根据未记录结果推断。

## 一、现状缺陷（已证实）

1. `p3_deploy_stepA.sh` 的 `BACKUP_MISMATCH` 分支裸 `sudo docker start astrbot`；
2. 备份失败、复制失败、`mv` 失败等分支也有裸 `docker start`；
3. 预期 SHA 硬编码，且误写为 v6（`c4497e04…`），实际 v14（`2f180cf0…`）；
4. “启动完整性核验”与“权限安全基线”未分开；
5. 无统一启动日志。

## 二、目标

1. 所有 `docker start` / `docker restart` 只能通过统一入口；
2. 启动前核验 SHA、属主、权限；
3. 目标与 SHA 绑定；
4. 日志可靠、不可覆盖、无“已恢复但仍有非法行”的假象；
5. 状态记录拆成三个维度，不互相替代；
6. 失败不启动、报告、人工恢复；
7. 竞态未根治，依赖权限基线。

## 三、设计

### 3.1 配置来源与保护

#### 3.1.1 唯一来源与严格解析

`deploy.env` 是唯一来源；不保留脚本顶部常量、不读 shell 环境变量覆盖。

- 只接受 `KEY=VALUE`，一行一对；忽略空行与整行 `#` 注释；
- **白名单键**：`TARGET_CANDIDATE_SHA`、`TARGET_V14_SHA`、`EXPECTED_OWNER`、`EXPECTED_MODE`、`TRUSTED_OWNERS`、`PRIVILEGED_GROUPS`；
- 未知键、重复键、缺键 → 失败；
- 不允许引号、空格、续行、变量展开、`export`；
- 值格式：
  - SHA：`^[0-9a-f]{64}$`；
  - OWNER：`root:root`；
  - MODE：`^(?:[0-7]{3}|0[0-7]{3})$`；
  - TRUSTED_OWNERS：`name:uid:gid` 逗号分隔列表；必须含 `root:0:0`；
  - PRIVILEGED_GROUPS：组名逗号分隔（至少 `sudo,wheel,adm`）；
- `TRUSTED_OWNERS`、`PRIVILEGED_GROUPS` 本身由 `deploy.env` 维护，文件 root:0640；不接受运行时注入；
- 解析失败 → 不启动、记录、报告。

#### 3.1.2 路径、父目录与属主（可执行判据）

1. 绝对路径，拒绝相对路径；
2. 从 `/` 到直接父目录逐级 `lstat`（拒绝 symlink）；
3. **允许属主**：
   - `root:0:0`；或
   - 在 `TRUSTED_OWNERS` 白名单内，**且同时满足**：
     a. 系统/服务账号（`uid < 1000` 或专用服务账号）；
     b. shell 为 `/usr/sbin/nologin` / `/bin/false`（只读 `/etc/passwd` 可核对）；
     c. 不属于 `PRIVILEGED_GROUPS` 中任何组；
     d. 可只读读取 `/etc/passwd`、`/etc/group`、`getent group`；来源不完整/不可读 → 失败关闭；
   - 任一无法证明 → 失败关闭；权限位符合 ≠ 目录可信；
4. 任一级 world-writable → 不启动；
5. **group-writable**：读该目录 gid → `getent group` 成员 → 若成员中存在不在 `TRUSTED_OWNERS` 的账号 → 失败；无法读取组信息 → 失败；
6. 文件 root、mode ≤0640、非 symlink；
7. 检查不能消除替换竞态；不宣称可靠防篡改。

#### 3.1.3 读取与使用竞态

- 读取后记录 `inode/mtime/SHA`，使用前再核验；
- 不能根治；依赖权限基线；
- 两次 stat 一致 ≠ 配置安全。

#### 3.1.4 交叉核对

- `TARGET_V14_SHA` = 备份实际 SHA = 部署准备报告基线；
- `TARGET_CANDIDATE_SHA` = 候选 snapshot SHA；
- 不一致 → 中止。

### 3.2 唯一启动入口与三维状态

```text
TARGETS = {
  "candidate": TARGET_CANDIDATE_SHA,
  "v14":       TARGET_V14_SHA,
  "recovered-v14": TARGET_V14_SHA,
}

start_verified(target):
  expected_sha = TARGETS[target]        # 未知 target → 立即失败
  读取磁盘 main.py 的 SHA/属主/权限
  核验三项
  追加 precheck（pass/fail）
  fail → 不启动（不写 start_invoked）
  持久化 start_invoked → 失败则不启动
  docker start
  attempt_result = exit_0 | exit_nonzero | unrecorded   # 记录失败即 unrecorded
  container_state = query() → running | stopped | unknown
  disk_verification = check() → match | mismatch | check_failed
  追加 resolution（若记录失败 → resolution=unrecorded，进程内）
```

- 只有 `start_verified()` 内部允许 `docker start`；
- `restart_verified(target)` 只 `docker stop` + 状态检查 + 委托 `start_verified(target)`；
- 三个维度**分别记录**，不互相推断。

#### 3.2.1 三个维度

| 维度 | 取值 | 含义 |
|---|---|---|
| `attempt_result` | `exit_0` / `exit_nonzero` / `unrecorded` | 本次 `docker start` 命令结果；`unrecorded` 表示日志写入失败，不能推断命令是否发出/执行 |
| `container_state` | `running` / `stopped` / `unknown` | 实际查询到的容器状态；查询失败=unknown |
| `disk_verification` | `match` / `mismatch` / `check_failed` | 磁盘三项核验；读取失败=check_failed |

#### 3.2.2 对外映射（只依据实际观测）

| container_state | disk_verification | 对外状态 |
|---|---|---|
| running | match | `RUNNING_VERIFIED` |
| running | mismatch / check_failed | `RUNNING_UNVERIFIED` |
| stopped | 任意（无法验证启动结果） | `STOPPED_UNVERIFIED` |
| unknown | 任意 | `STATE_UNKNOWN_UNVERIFIED` |

- `attempt_result = unrecorded` 不改变 `container_state` 的观测值；它只表示“本次调用结果未记录”；
- 不根据 `unrecorded` 推断容器未运行/已运行；
- `RUNNING_UNVERIFIED` / `STOPPED_UNVERIFIED` / `STATE_UNKNOWN_UNVERIFIED` 都只读记录、保留现场、报告；不自动 stop/restart/回滚。

#### 3.2.3 UNRECORDED 边界

- `unrecorded` 是**进程内故障结果**，不是已持久化事件；
- `start_result` 写失败：`attempt_result=unrecorded`；仍继续只读查询 `container_state`、`disk_verification`（若可读）；
- `resolution` 也写失败：保留已有日志与现场，**不声称完整记录成功**；
- 区分四个事实：Docker 返回码、命令执行异常、命令是否真正发出、日志是否写入成功；不能互相替代。

### 3.3 分支矩阵

| 分支 | 启动调用 |
|---|---|
| 正常部署（替换后） | `start_verified(candidate)` |
| 备份失败 | 不自动启动；确认可信 v14 后才 `start_verified(v14)` |
| 备份校验不一致 | 不自动启动、不自动回滚；只有可信 v14 恢复后才 `start_verified(v14)`；否则停止 |
| 临时文件复制/校验失败 | 删临时文件；确认原文件可信后 `start_verified(v14)`；否则停止 |
| `mv` 失败 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败停止 |
| 回滚 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败停止 |
| 启动失败后重试 | 仍 `start_verified(当前 target)` |
| 验证失败（测试 FAIL） | 不自动启动/回滚；报告，由主人决定 |

### 3.4 restart 语义（全局锁覆盖）

```text
restart_verified(target):
  acquire_global_deploy_lock()      # 覆盖整个临界区
  docker stop
  检查容器实际状态（失败/仍运行 → 不继续，报告）
  start_verified(target)            # 唯一启动入口
  release_global_deploy_lock()
```

- 禁止裸 `docker restart`；
- 全局锁必须在 `docker stop` **之前**获取，覆盖 stop→核验→start→resolution；否则不能防止并发部署交叉。

### 3.5 启动日志（JSONL）

路径：`/opt/astrbot/shared/记忆/部署日志/start-attempt-<attempt_id>.jsonl`。

#### 3.5.1 日志目录前置条件

1. 从 `/` 到日志目录逐级 `lstat`，拒绝 symlink；
2. 属主按 3.1.2 判据；
3. 不 world-writable；group-writable 按 3.1.2 验证；
4. 日志文件（存在时）非 symlink、root、mode ≤0640；
5. 检查/创建/持久化失败 → 不启动。

#### 3.5.2 事件模型

```text
{"event":"attempt_created","attempt_id":"...","time":"...","target":"candidate"}
{"event":"precheck","attempt_id":"...","result":"pass|fail",...}
{"event":"start_invoked","attempt_id":"...","time":"..."}
{"event":"start_result","attempt_id":"...","result":"exit_0|exit_nonzero|unrecorded","time":"..."}
{"event":"resolution","attempt_id":"...","attempt_result":"...","container_state":"...","disk_verification":"...","time":"..."}
```

- 不再使用单一 `resolution` 字符串承担三件事；三维分别记录；
- 单写者：同一 attempt 一个写入者；追加前获取 attempt 锁。

#### 3.5.3 首次创建与追加

**A. 首次创建**

1. 受保护目录 `O_CREAT|O_EXCL` 临时文件（拒绝 symlink）；
2. 写 `attempt_created`、`precheck`；precheck fail 只写 fail，不写 `start_invoked`；
3. precheck pass 写 `start_invoked`；
4. 临时文件 `fsync`；
5. 不覆盖目标的原子创建（`link` / `renameat2(RENAME_NOREPLACE)`）；目标已存在 → 失败；
6. 删临时文件；父目录 `fsync`；
7. 全成功才允许 `docker start`。

**B. 已有文件追加**

1. 获取 attempt 锁；
2. 逐行 JSON 合法性检测（C）；
3. append 一条完整事件；
4. 校验写入完整；
5. 文件 `fsync`；
6. 任一步失败 → 不启动。

**C. JSON 合法性（v9 保守规则）**

先判末行是否有换行，再**独立**判 JSON 是否合法：

| 情况 | 处理 |
|---|---|
| JSON 合法 + 末行有换行 | 正常，可追加 |
| **JSON 合法 + 末行无换行** | 补 `\n`（仅行结束符）→ `recovery(added_line_terminator)` → 可继续；不称“损坏” |
| **JSON 非法 + 末行无换行** | 原字节保留；**停止追加、转只读取证、不启动**；不声称已恢复 |
| **JSON 非法 + 末行有换行** | 原字节保留；**停止追加、转只读取证、不启动**；不声称已恢复 |
| **中间行非法** | 停止追加、转只读取证、不启动；不尝试修复 |
| **连续非法/无法定位边界** | 停止追加、转只读取证、不启动 |

- 关键：不再“追加 corrupt_line 后继续”，因为后续读取仍会 `json.loads` 失败；**非法行只做只读取证，不做原地隔离**；
- 只有“合法但缺换行”可补 `\n` 继续；
- 读取者遇到非法行：停止解析、报告，不跳过、不猜测。

#### 3.5.4 锁设计（两级）

**全局部署互斥锁**：

- 路径固定：`/opt/astrbot/shared/记忆/部署锁/deploy.lock`；
- 首次创建：`O_CREAT|O_EXCL`，root:0600；
- 后续打开：`open` 后用 `lstat` 核验非 symlink、root、0600、记录 inode；再 `flock(LOCK_EX|LOCK_NB)`；
- 锁文件长期保留；进程异常退出由 `flock` 自动释放；
- 获取失败 → 不继续、不启动、报告；
- 覆盖完整临界区（stop→核验→start→resolution），`restart_verified` 在 stop 前获取；
- 只防并发部署，**不阻止不遵守锁的其他写入者**；不能替代权限基线。

**attempt 日志锁**：

- 每 attempt 一个锁文件（同目录），只防同一 attempt 并发写；
- 首次 `O_CREAT|O_EXCL`；后续 `open` + `lstat` + `flock`；
- 锁失败 → 不写、不启动。

#### 3.5.5 `invoked` 遗留

- 发现 `start_invoked` 遗留：读 `container_state`、`disk_verification`，按 3.2.2 记录；
- 无法完成 → 对应 unknown/check_failed/unrecorded；
- 原事件保留；不把 invoked 当 success。

### 3.6 静态检查与完整调用链

`grep` 只是基础检查：审查所有脚本/辅助脚本/实际 Docker 调用路径；负向测试；人工调用链复核；grep 无命中不能宣称无绕过。

### 3.7 测试矩阵

1. deploy.env 解析（含 TRUSTED_OWNERS/PRIVILEGED_GROUPS 缺/非法）；
2. 父目录逐级；非 root 判据（白名单/nologin/提权组/组来源不可读）；
3. 读取与使用间替换；
4. 三维状态组合（attempt_result × container_state × disk_verification）；
5. JSON 合法性：合法有换行/合法无换行/非法无换行/非法有换行/中间非法/连续非法；
6. 首建：O_EXCL、不覆盖原子创建、目标已存在失败、目录 fsync 失败；
7. 追加：完整行/部分写入/中断；
8. 全局锁：两个部署尝试互斥；attempt 锁：同 attempt 并发拒绝；锁文件 symlink/权限/inode 失败；
9. precheck fail 不写 invoked；
10. 日志目录/创建/持久化失败 → 不启动；
11. 备份校验不一致不自动启动/回滚；
12. Docker 非零但容器异常；
13. 负向测试：统一入口外启动被捕获；
14. target/SHA 映射。

### 3.8 竞态

- 0777/0666 下检查到 Docker 加载之间文件可能被替换；
- 配置读取→使用竞态；日志文件/目录可被替换；
- `flock` 不阻止外部写入者；
- 不能宣称竞态消除；权限基线是根治前提。

## 四、现实约束

当前 0777 环境可能无法通过日志/配置路径检查；设计通过后也不能直接施工/部署；先完成权限基线评估与整改；不得为让脚本跑起来放宽 fail-closed。

## 五、风险

1. 竞态未根治（依赖权限基线）；
2. 启动字节一致 ≠ 权限安全；
3. 日志目录可能不满足前置条件，届时 fail-closed 不启动；
4. dry-run 与真实 Docker 差异；
5. grep 不能单独证明无绕过。
