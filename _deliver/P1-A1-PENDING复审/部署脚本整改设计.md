## 〇、v11 返修点

1. **precheck=fail 绝不启动**：首次创建即使日志/fsync 全部成功，`precheck=fail` 也直接返回、不执行 `docker start`；只有 pass + `start_invoked` 持久化 + 原子创建 + 目录 fsync 全成功才启动；补负向测试。
2. **初始信任根**：验证 `deploy.env` 路径链时**只接受 root 属主与固定权限**，不引用其内部的 `TRUSTED_OWNERS`；通过初始验证后才允许使用配置中的非 root 白名单，打破循环。
3. **锁目录完整路径链**：从 `/` 逐级 `openat` 目录 fd，逐级 `O_NOFOLLOW` + `fstat`；锁 inode 一致性用 `fstatat` 与 `fstat` 比较 dev/ino；锁目录必须 root、不可被替换，否则两进程可能锁不同 inode。
4. **锁顺序统一**：全局锁 → attempt 锁；释放 attempt → 全局；首次创建与追加都必须先 attempt 锁；并发首次创建失败即不创建。
5. **唯一入口可验证边界**：明确唯一可执行入口、辅助脚本禁止清单、外部入口负向测试；grep/调用链/负向测试结合。
6. 事件 schema 具体化：字段类型、允许值、是否允许额外字段、时间与 attempt_id 格式。

## 一、现状缺陷（已证实）

1. `p3_deploy_stepA.sh` 的 `BACKUP_MISMATCH` 分支裸 `sudo docker start astrbot`；
2. 备份失败、复制失败、`mv` 失败等分支也有裸 `docker start`；
3. 预期 SHA 硬编码，且误写为 v6（`c4497e04…`），实际 v14（`2f180cf0…`）；
4. “启动完整性核验”与“权限安全基线”未分开；
5. 无统一启动日志。

## 二、目标

1. 所有部署动作只经唯一顶层事务；
2. 全局锁覆盖完整事务，锁失败零改动；
3. 启动前核验 SHA、属主、权限；
4. 目标与 SHA 绑定；
5. 日志严格可解析、不可覆盖；
6. 状态三维记录，不互相推断；
7. 失败不启动、报告、人工恢复；
8. 竞态未根治，依赖权限基线。

## 三、设计

### 3.1 配置来源与保护

#### 3.1.1 唯一来源与初始信任根

`deploy.env` 是唯一来源；不保留脚本顶部常量、不读 shell 环境变量覆盖。

**初始信任根（不依赖配置内容）**：

1. `deploy.env` 必须是 `root:root`、mode `0640`、非 symlink；
2. 从 `/` 到直接父目录逐级 `lstat`：每级必须 `root` 属主、非 symlink、不含 world/group write；
3. 任一级不满足 → 失败，**不读取配置内容**；
4. 通过以上验证后，才允许读取 `TRUSTED_OWNERS`、`PRIVILEGED_GROUPS` 用于后续检查；
5. **不得用配置里的白名单证明配置自身路径可信**（打破循环）。

**解析**：

- 只接受 `KEY=VALUE`，一行一对；忽略空行与整行 `#` 注释；
- 白名单键：`TARGET_CANDIDATE_SHA`、`TARGET_V14_SHA`、`EXPECTED_OWNER`、`EXPECTED_MODE`、`TRUSTED_OWNERS`、`PRIVILEGED_GROUPS`；
- 未知键、重复键、缺键 → 失败；
- 不允许引号、空格、续行、变量展开、`export`；
- SHA：`^[0-9a-f]{64}$`；OWNER：`root:root`；MODE：`^(?:[0-7]{3}|0[0-7]{3})$`；
- `TRUSTED_OWNERS`：`name:uid:gid` 逗号分隔；必须含 `root:0:0`；
- `PRIVILEGED_GROUPS`：组名逗号分隔；至少 `sudo,wheel,adm`；
- 解析失败 → 不启动、记录、报告。

#### 3.1.2 路径、父目录与属主

1. 绝对路径，拒绝相对路径；
2. 配置路径按 3.1.1 初始信任根验证（仅 root）；
3. 其它路径（日志、锁等）允许属主：
   - `root:0:0`；或
   - 在 `TRUSTED_OWNERS` 内且：passwd `name/uid/gid` 三者一致；系统/服务账号（`100<=uid<=999` 或显式标注）、shell 为 `nologin`/`false`；主 GID 与附加组均不属于 `PRIVILEGED_GROUPS`；组信息来源可读；否则失败；
4. 任一级 world-writable → 不启动；
5. group-writable：同时核对主 GID 成员与 `getent group` 附加成员；存在非白名单账号 → 失败；组信息不完整 → 失败；
6. 文件 root、mode ≤0640、非 symlink；
7. 检查不能消除替换竞态；不宣称可靠防篡改。

#### 3.1.3 读取与使用竞态

- 读取后记录 `inode/mtime/SHA`，使用前再核验；
- 不能根治；依赖权限基线；
- 两次 stat 一致 ≠ 配置安全。

#### 3.1.4 交叉核对

- `TARGET_V14_SHA` = 备份实际 SHA = 部署准备报告基线；
- `TARGET_CANDIDATE_SHA` = 候选 snapshot SHA；
- 不一致 → 中止。

### 3.2 唯一顶层部署事务与唯一入口

```text
deploy.sh <action> [target]        # 唯一可执行入口
  deploy_transaction(action, target):
    acquire_global_lock()          # 失败 → 零改动、退出
    ... 备份 / 替换 / 恢复 / stop / start_verified / resolution ...
    release_global_lock()
```

- 唯一可执行入口：`deploy.sh`（或等价的单一主程序）；
- 辅助脚本（`lib/` 下）不得作为独立入口执行；`start_verified` 不导出、不提供 CLI；
- 外部不得直接 `docker start/restart`；所有动作经 `deploy.sh`；
- `start_verified(target)` 是内部函数，只能在 `deploy_transaction` 内调用；
- 锁获取失败：不备份、不替换、不 stop、不 start、不改线上。

#### 3.2.1 `start_verified`（内部）

```text
start_verified(target):
  expected_sha = TARGETS[target]
  读取磁盘 main.py 的 SHA/属主/权限
  核验三项
  追加 precheck（pass/fail）
  fail → 不启动（不写 start_invoked）
  持久化 start_invoked → 失败则不启动
  docker start
  attempt_result = exit_0 | exit_nonzero | unrecorded
  container_state = query() → running | stopped | unknown
  disk_verification = check() → match | mismatch | check_failed
```

### 3.2.2 三维状态与对外映射

| 维度 | 取值 |
|---|---|
| `attempt_result` | `exit_0` / `exit_nonzero` / `unrecorded` |
| `container_state` | `running` / `stopped` / `unknown` |
| `disk_verification` | `match` / `mismatch` / `check_failed` |

| container_state | disk_verification | 对外状态 |
|---|---|---|
| running | match | `RUNNING_DISK_MATCH` |
| running | mismatch | `RUNNING_DISK_MISMATCH` |
| running | check_failed | `RUNNING_DISK_UNVERIFIED` |
| stopped | 任意 | `STOPPED_UNVERIFIED` |
| unknown | 任意 | `STATE_UNKNOWN_UNVERIFIED` |

- `RUNNING_DISK_MATCH` 不代表已加载目标代码；
- `attempt_result` 独立保留，不被容器/磁盘状态掩盖；
- 只读记录、保留现场、报告；不自动 stop/restart/回滚。

#### 3.2.3 UNRECORDED 与事件模型

- `start_result` 只表示实际成功持久化的命令结果：`exit_0` / `exit_nonzero`；
- 写入失败 → 进程内 `attempt_result=unrecorded`，不写“unrecorded 的 start_result”；
- 后续 resolution 可带 `attempt_result=unrecorded`，表示“此前记录失败”，不声称原始事件已写；
- resolution 也失败 → 保留现场与已有日志，不声称完整持久化；
- 区分：Docker 返回码、命令异常、是否真正发出、日志是否写入成功。

### 3.3 分支矩阵（全部经顶层事务）

| 分支 | 事务内动作 |
|---|---|
| 正常部署 | 备份 → 替换 → `start_verified(candidate)` |
| 备份失败 | 不启动；报告；可信 v14 恢复后才 `start_verified(v14)` |
| 备份校验不一致 | 不自动启动、不自动回滚；可信 v14 恢复后才 `start_verified(v14)`；否则停止 |
| 临时文件复制/校验失败 | 删临时文件；确认原文件可信后 `start_verified(v14)`；否则停止 |
| `mv` 失败 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败停止 |
| 回滚 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败停止 |
| 启动失败后重试 | 仍 `start_verified(当前 target)`（事务内） |
| 验证失败（测试 FAIL） | 不自动启动/回滚；报告，由主人决定 |

### 3.4 restart 语义

```text
deploy_transaction("restart", target):
  ...（全局锁已持有）...
  docker stop
  检查容器实际状态
  start_verified(target)
```

禁止裸 `docker restart`。

### 3.5 启动日志（JSONL）

路径：`/opt/astrbot/shared/记忆/部署日志/start-attempt-<attempt_id>.jsonl`。

#### 3.5.1 日志目录前置条件

1. 从 `/` 到日志目录逐级 `lstat`，拒绝 symlink；
2. 属主按 3.1.2（初始 root 或已验证白名单）；
3. 不 world-writable；group-writable 按 3.1.2 验证；
4. 日志文件（存在时）非 symlink、root、mode ≤0640；
5. 检查/创建/持久化失败 → 不启动。

#### 3.5.2 事件 schema（具体化）

| 字段 | 类型/允许值 | 说明 |
|---|---|---|
| `event` | 枚举：`attempt_created/precheck/start_invoked/start_result/resolution/recovery` | 必需 |
| `attempt_id` | `^[a-f0-9]{32}$` | 必需 |
| `time` | ISO-8601 UTC（`YYYY-MM-DDTHH:MM:SSZ`） | 必需 |
| `target` | 枚举：`candidate/v14/recovered-v14` | attempt_created 必需 |
| `result` | 按事件类型枚举 | precheck: pass/fail；start_result: exit_0/exit_nonzero |
| `attempt_result` | 枚举：exit_0/exit_nonzero/unrecorded | resolution |
| `container_state` | 枚举：running/stopped/unknown | resolution |
| `disk_verification` | 枚举：match/mismatch/check_failed | resolution |
| `action` | 枚举：added_line_terminator | recovery |

- 拒绝未知字段（`additional_properties=false`）；
- 字段类型不符、枚举外值、缺必需字段 → 非法行。

#### 3.5.3 严格 JSON 校验

- 只接受 JSON **对象**；拒绝数组/标量；
- 拒绝重复键；
- 拒绝 `NaN`/`Infinity`；
- 按 3.5.2 schema 校验字段与类型；
- 任一行不满足 → 非法行，按 3.5.4 处理。

#### 3.5.4 JSON 合法性处理

先判末行换行，再独立判 JSON：

| 情况 | 处理 |
|---|---|
| 合法 + 有换行 | 可追加 |
| **合法 + 无换行** | 锁内：append `\n` → `fsync` → append `recovery(added_line_terminator)` → `fsync` → 才允许后续事件 |
| 非法 + 无换行 | 原字节保留；停止追加、只读取证、不启动 |
| 非法 + 有换行 | 原字节保留；停止追加、只读取证、不启动 |
| 中间行非法 | 停止追加、只读取证、不启动 |
| 连续非法/无法定位 | 停止追加、只读取证、不启动 |

- 恢复任一步失败 → 停止后续追加与启动；
- 不覆盖/截断/重写历史。

#### 3.5.5 首次创建与追加（锁顺序统一）

**锁顺序（所有路径统一）**：全局锁 → attempt 锁；释放 attempt → 全局。固定顺序避免死锁。

**A. 首次创建**

1. 全局锁已持有；
2. 获取 attempt 锁；并发首建失败 → 不创建、报告；
3. 受保护目录 `O_CREAT|O_EXCL|O_NOFOLLOW` 临时文件；
4. 写 `attempt_created`、`precheck`；
5. **若 precheck=fail**：写 fail 事件 → `fsync` → 原子创建正式文件 → 目录 `fsync` → **直接返回，绝不 `docker start`**；
6. 若 pass：写 `start_invoked` → 临时文件 `fsync` → 不覆盖目标的原子创建（`link`/`renameat2(RENAME_NOREPLACE)`）→ 目标已存在失败 → 删临时文件 → 目录 `fsync`；
7. 只有 pass + `start_invoked` 已持久化 + 原子创建 + 目录 fsync 全成功，才允许 `docker start`；
8. 释放 attempt 锁，再由事务释放全局锁。

**B. 已有文件追加**

1. 全局锁已持有；获取 attempt 锁；
2. 严格 JSON 校验（3.5.3/3.5.4）；
3. append 一条完整事件；
4. 校验写入完整；
5. 文件 `fsync`；
6. 任一步失败 → 不启动；
7. 释放 attempt 锁。

**C. 目录 fsync 失败**

- 正式文件已创建但目录 fsync 失败：可能留下含 `start_invoked` 的文件；
- 不启动；标记 `state_uncertain`；不假设 Docker 已执行。

#### 3.5.6 锁设计（两级，目录链安全）

**全局部署互斥锁**：

- 路径固定：`/opt/astrbot/shared/记忆/部署锁/deploy.lock`；
- **目录链**：从 `/` 开始逐级 `openat(parent_fd, name, O_DIRECTORY|O_NOFOLLOW)`；每级 `fstat` 核验：目录类型、root 属主、不含 world/group write；任一级失败 → 不获取锁；
- 取得锁目录 fd 后，`openat(lockdir_fd, "deploy.lock", O_RDWR|O_CREAT|O_NOFOLLOW, 0600)`；
- `fstat(fd)` 核验 regular file、root、0600；
- **一致性**：`fstatat(lockdir_fd, "deploy.lock", AT_SYMLINK_NOFOLLOW)` 与 `fstat(fd)` 比较 `dev/ino`；不一致 → 失败；
- `flock(fd, LOCK_EX|LOCK_NB)`；
- 目录 fd 与锁 fd 持有到事务结束；释放锁后关闭 fd；
- 锁目录必须 root 且不可被外部替换；否则两进程可能锁不同 inode，互斥失效；
- 获取失败 → 零改动、退出。

**attempt 日志锁**：

- 每 attempt 一个锁文件，位于同一受保护目录；
- 同一套目录链/`O_NOFOLLOW`/`fstat`/`fstatat` 一致性规则；
- 只防同一 attempt 并发写；
- 失败 → 不写、不启动。

### 3.6 唯一入口的可验证边界

- 唯一可执行入口：`deploy.sh`；
- 辅助脚本清单：`lib/` 下脚本禁止独立执行（无 main 或入口检查拒绝）；
- `start_verified` 不导出、不提供 CLI；
- 外部入口不得直接调用 Docker；
- 检查手段：`grep` + 全脚本调用链人工复核 + 对每个实际入口做负向测试（直接执行辅助脚本/直接 Docker 调用应被拒绝）；
- 不能单凭函数命名或代码组织认定“外部无法绕过”。

### 3.7 测试矩阵

1. deploy.env 初始信任根（配置路径非 root/权限宽/symlink → 不读取内容）；解析（白名单键、缺/非法）；
2. 父目录逐级；非 root 判据（name/uid/gid、主 GID+附加组、提权组、组来源不可读）；
3. 读取与使用间替换；
4. 三维状态组合与对外映射；
5. JSON schema：未知字段/类型错/枚举外/缺字段/重复键/NaN/Infinity/非对象；
6. JSON 合法性：合法无换行恢复、非法（无/有换行/中间/连续）；
7. 首建：precheck=fail 即使日志全成功也不启动；pass 才启动；并发首建失败；
8. 首建/追加锁顺序：全局→attempt，释放 attempt→全局；无死锁；
9. 锁目录链：逐级 openat/fstat；symlink/非 root/权限宽失败；锁 inode 一致性（fstatat vs fstat）；
10. 全局锁覆盖所有分支；锁失败零改动；
11. attempt 锁并发拒绝；
12. 日志目录/创建/持久化失败 → 不启动；
13. 备份校验不一致不自动启动/回滚；
14. Docker 非零但容器异常；
15. 唯一入口负向测试：辅助脚本/直接 Docker 调用被拒绝；
16. target/SHA 映射。

### 3.8 竞态

- 0777/0666 下检查到 Docker 加载之间文件可能被替换；
- 配置读取→使用竞态；日志/锁目录可被替换；
- `flock` 不阻止外部写入者；
- 不能宣称竞态消除；权限基线是根治前提。

## 四、现实约束

当前 0777 环境可能无法通过配置/日志/锁目录检查；设计通过后也不能直接施工/部署；先完成权限基线评估与整改；不得为让脚本跑起来放宽 fail-closed。

4. dry-run 与真实 Docker 差异；
5. grep 不能单独证明无绕过。
