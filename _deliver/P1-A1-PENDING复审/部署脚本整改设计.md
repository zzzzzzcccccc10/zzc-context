# 部署脚本整改设计（顶层事务 + 统一启动入口）v14

- **文档类型**：整改设计（不施工、不动线上）
- **任务**：解决部署脚本所有分支绕过 `start_verified()` 的问题
- **版本**：v14（v13 返修；删除自动重试、完整事件状态机、身份核验失败矩阵）
- **日期**：2026-11-22
- **更新时间**：2026-11-22 17:30（Asia/Shanghai）
- **当前状态**：**修订完成，待复审；未修改脚本、未改线上**

## 〇、v14 返修点

1. **删除自动重试**：移除“启动失败后重试”分支；`result_unknown` 停止自动操作；重试只能是独立人工授权事务，先核实容器状态/前次结果/磁盘；不得以“仍经 `start_verified`”作为自动重试依据。
2. **事件状态机闭合**：逐事件定义必需/可选/禁止字段、前置/后继、是否重复、交叉约束；`start_not_sent` 必带 reason；`start_result` 与 `resolution` 的 `command_sent` 有合法组合；`recovery` 纳入状态机位置；`owner`/`time` 的格式与有效性收紧。
3. **身份核验失败矩阵**：临时文件 `fstat`、正式化 `fstatat`、`dev/ino` 不一致、追加 `fstat`/`fstatat`、追加身份不匹配，全部列入失败矩阵：不追加、不启动、保留现场、只读取证。

## 一、现状缺陷（已证实）

1. `p3_deploy_stepA.sh` 的 `BACKUP_MISMATCH` 分支裸 `sudo docker start astrbot`；
2. 备份失败、复制失败、`mv` 失败等分支也有裸 `docker start`；
3. 预期 SHA 硬编码，且误写为 v6（`c4497e04…`），实际 v14（`2f180cf0…`）；
4. “启动完整性核验”与“权限安全基线”未分开；
5. 无统一启动日志。

## 二、目标

1. 所有部署动作只经唯一顶层事务；
2. 全局锁覆盖完整事务，锁失败零改动；
3. 启动前核验 SHA、属主、权限；
4. 日志与锁目录使用安全目录 fd，日志文件本身做身份核验；
5. 启动意图、调用开始、命令结果、记录结果四层分开；
6. 崩溃窗口中的状态不被错误解释；
7. **不自动重试**；未知结果停止自动操作；
8. 竞态未根治，依赖权限基线。

## 三、设计

### 3.1 配置来源与保护

#### 3.1.1 唯一来源与初始信任根

`deploy.env` 是唯一来源；不保留脚本顶部常量、不读 shell 环境变量覆盖。

**初始信任根**：

1. `deploy.env` 必须 `root:root`、mode `0640`、非 symlink；
2. 从 `/` 到直接父目录逐级 `lstat`：每级 `root` 属主、非 symlink、不含 world/group write；
3. 任一级不满足 → 失败，**不读取配置内容**；
4. 通过后才读取 `TRUSTED_OWNERS`、`PRIVILEGED_GROUPS`；
5. 不得用配置内白名单证明配置自身路径可信。

**解析**：

- `KEY=VALUE` 一行一对；忽略空行/整行 `#`；
- 白名单键：`TARGET_CANDIDATE_SHA`、`TARGET_V14_SHA`、`EXPECTED_OWNER`、`EXPECTED_MODE`、`TRUSTED_OWNERS`、`PRIVILEGED_GROUPS`；
- 未知/重复/缺键 → 失败；不允许引号/空格/续行/变量展开/`export`；
- SHA `^[0-9a-f]{64}$`；OWNER `root:root`；MODE `^(?:[0-7]{3}|0[0-7]{3})$`；
- `TRUSTED_OWNERS`：`name:uid:gid` 逗号分隔，含 `root:0:0`；
- `PRIVILEGED_GROUPS`：组名逗号分隔，至少 `sudo,wheel,adm`；
- 解析失败 → 不启动、记录、报告。

#### 3.1.2 路径、父目录与属主

1. 绝对路径；
2. 配置路径按 3.1.1（仅 root）；
3. 其它路径允许：`root:0:0`；或白名单内且 passwd `name/uid/gid` 一致、系统账号（`100<=uid<=999` 或显式标注）、`nologin`/`false`、主 GID 与附加组均不在 `PRIVILEGED_GROUPS`；组来源可读；否则失败；
4. 任一级 world-writable → 不启动；
5. group-writable：主 GID 成员 + `getent group` 附加成员，存在非白名单 → 失败；组信息不完整 → 失败；
6. 文件 root、mode ≤0640、非 symlink；
7. 不宣称防篡改。

#### 3.1.3 读取与使用竞态

- 读取后记录 `inode/mtime/SHA`，使用前再核验；
- 不能根治；依赖权限基线。

#### 3.1.4 交叉核对

- `TARGET_V14_SHA` = 备份实际 SHA = 部署准备报告基线；
- `TARGET_CANDIDATE_SHA` = 候选 snapshot SHA；
- 不一致 → 中止。

### 3.2 唯一顶层事务与入口边界

```text
deploy.sh <action> [target]        # 唯一项目入口
  deploy_transaction(action, target):
    acquire_global_lock()          # 失败 → 零改动、退出
    try:
      ... 备份 / 替换 / 恢复 / stop / start_verified / resolution ...
    finally:
      release_attempt_lock()       # 若持有
      release_global_lock()
```

- 项目内部：所有项目自有脚本只经 `deploy.sh`；`lib/` 禁止独立执行；`start_verified` 不导出；
- 系统级：能否阻止拥有 Docker socket/sudo 权限的外部主体直接调用 Docker，由 sudoers、socket 权限等系统控制决定；本项目未提供这些控制时，**不保证外部主体无法绕过 `deploy.sh`**；
- 负向测试分三类：内部辅助脚本直接执行；内部调用链绕过事务；系统外部直接 Docker（第三类不能仅靠脚本测试证明）。

#### 3.2.1 `start_verified`（内部）与启动事件

```text
start_verified(target):
  expected_sha = TARGETS[target]
  读取磁盘 main.py 的 SHA/属主/权限
  核验三项
  追加 precheck（pass/fail）
  fail → 不启动（不写 start_invoked）
  持久化 start_invoked          # 仅“意图”
  （尚未调用 Docker）
  持久化 start_call_begin       # “即将调用”；失败 → 不调用、不启动
  docker start
  追加 start_result（exit_0/exit_nonzero/result_unknown）
  追加 resolution
```

- `start_invoked`：启动意图；不承载最终命令发送状态；
- `start_call_begin`：即将调用；不代表命令已发出；
- 若明确决定不调用，写 `start_not_sent`（必带 reason）；
- **崩溃规则**：
  - 有 `start_result` → 用其结果；
  - 有 `start_not_sent` → `not_sent`；
  - 只有 `start_invoked`/`start_call_begin`，无 `start_result`/`start_not_sent` → **`result_unknown`**；不得推断命令未发送；
- **`result_unknown` 必须停止自动操作**：不自动重试、不自动 start/restart、不自动回滚；报告主人；
- 重试只能作为**独立人工授权事务**，先核实容器状态、前次命令结果、磁盘状态；
- 不得以“仍经 `start_verified`”作为自动重试的安全依据。

#### 3.2.2 三维状态与对外映射

| 维度 | 取值 |
|---|---|
| `attempt_result` | `exit_0` / `exit_nonzero` / `not_sent` / `result_unknown` / `unrecorded` |
| `command_sent` | `yes` / `no` / `unknown`（仅事后） |
| `container_state` | `running` / `stopped` / `unknown` |
| `disk_verification` | `match` / `mismatch` / `check_failed` |

| container_state | disk_verification | 对外状态 |
|---|---|---|
| running | match | `RUNNING_DISK_MATCH` |
| running | mismatch | `RUNNING_DISK_MISMATCH` |
| running | check_failed | `RUNNING_DISK_UNVERIFIED` |
| stopped | 任意 | `STOPPED_UNVERIFIED` |
| unknown | 任意 | `STATE_UNKNOWN_UNVERIFIED` |

- `RUNNING_DISK_MATCH` 不代表已加载目标代码；
- `attempt_result`/`command_sent` 独立保留；
- 只读记录、保留现场、报告；不自动 stop/restart/回滚。

#### 3.2.3 UNRECORDED 边界

- `start_result` 只表示实际成功持久化的结果：`exit_0`/`exit_nonzero`/`result_unknown`；
- 写入失败 → 进程内 `attempt_result=unrecorded`；
- 后续 resolution 可带 `attempt_result=unrecorded` 说明此前记录失败；
- resolution 也失败 → 保留现场与已有日志，不声称完整；
- 四个事实分开：启动意图、调用开始、命令结果、记录是否成功。

### 3.3 分支矩阵（全部经顶层事务，无自动重试）

| 分支 | 事务内动作 |
|---|---|
| 正常部署 | 备份 → 替换 → `start_verified(candidate)` |
| 备份失败 | 不启动；报告；可信 v14 恢复后才 `start_verified(v14)` |
| 备份校验不一致 | 不自动启动、不自动回滚；可信 v14 恢复后才 `start_verified(v14)`；否则停止 |
| 临时文件复制/校验失败 | 删临时文件；确认原文件可信后 `start_verified(v14)`；否则停止 |
| `mv` 失败 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败停止 |
| 回滚 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败停止 |
| **启动结果未知/非零** | **停止自动操作；不自动重试；报告主人；重试需独立人工授权事务，先核实容器状态/前次结果/磁盘** |
| 验证失败（测试 FAIL） | 不自动启动/回滚；报告，由主人决定 |

**删除** v13 的“启动失败后重试：仍 `start_verified`”条目；该条与 `result_unknown` 停止自动操作冲突。

### 3.4 restart 语义

```text
deploy_transaction("restart", target):
  ...（全局锁已持有）...
  docker stop
  检查容器实际状态
  start_verified(target)
```

禁止裸 `docker restart`。

### 3.5 启动日志（JSONL）

路径：`/opt/astrbot/shared/记忆/部署日志/start-attempt-<attempt_id>.jsonl`。

#### 3.5.1 日志目录与日志文件 fd 核验

**目录**：

1. 从可信根 `/` 逐级 `openat(parent_fd, name, O_DIRECTORY|O_NOFOLLOW)`；
2. 每级 `fstat` 核验：目录类型、属主（按 3.1.2）、不含 world/group write；
3. 保持目录 fd 链；取得日志目录 fd；
4. 创建/正式化/追加**只用 dirfd**，不重新解析完整路径。

**日志文件（创建）**：

1. `openat(logdir_fd, "....tmp", O_CREAT|O_EXCL|O_NOFOLLOW, 0600)`；
2. `fstat(fd)`：regular file、属主 root（或白名单）、mode 0600；
3. 记录 `dev/ino`。

**日志文件（正式化）**：

1. `linkat(logdir_fd, tmp, logdir_fd, final)` 或 `renameat2(RENAME_NOREPLACE)`；
2. `fstatat(logdir_fd, final, AT_SYMLINK_NOFOLLOW)` 核验目录项；
3. 与临时文件 `fstat` 比较 `dev/ino`；不一致 → 失败。

**日志文件（追加）**：

1. `openat(logdir_fd, name, O_RDWR|O_APPEND|O_NOFOLLOW)`；
2. `fstat(fd)`：regular、属主/权限符合；
3. `fstatat(logdir_fd, name, AT_SYMLINK_NOFOLLOW)` 比较 `dev/ino`；不一致 → 失败；
4. 失败 → 不追加、不启动。

日志目录与锁目录分别建立保证，不互相代表。

#### 3.5.2 事件 Schema（逐事件完整）

**字段类型/格式**：

| 字段 | 类型/格式 | 约束 |
|---|---|---|
| `event` | 枚举（见下） | 必需 |
| `attempt_id` | `^[a-f0-9]{32}$` | 必需 |
| `time` | `YYYY-MM-DDTHH:MM:SSZ`，须日历有效（月 01-12、日按月份/闰年、时 00-23、分/秒 00-59） | 必需 |
| `target` | 枚举：candidate/v14/recovered-v14 | attempt_created 必需 |
| `result` | precheck: pass/fail；start_result: exit_0/exit_nonzero/result_unknown | 按事件 |
| `reason` | 枚举：call_declined/operator_cancel/precondition_changed | start_not_sent 必需 |
| `attempt_result` | 枚举：exit_0/exit_nonzero/not_sent/result_unknown/unrecorded | resolution 必需 |
| `command_sent` | 枚举：yes/no/unknown | 仅 start_result/resolution 可选 |
| `container_state` | 枚举：running/stopped/unknown | resolution 必需 |
| `disk_verification` | 枚举：match/mismatch/check_failed | resolution 必需 |
| `expected_sha`/`actual_sha` | `^[0-9a-f]{64}$` | precheck 可选 |
| `owner` | `^[a-z_][a-z0-9_-]{0,31}:[a-z_][a-z0-9_-]{0,31}$` | precheck 可选 |
| `mode` | `^0?[0-7]{3}$` | precheck 可选 |
| `action` | 枚举：added_line_terminator | recovery 必需 |

**逐事件矩阵（必需/可选/禁止/前置/后继/重复）**：

| 事件 | 必需 | 可选 | 禁止 | 前置 | 后继 | 重复 |
|---|---|---|---|---|---|---|
| attempt_created | event, attempt_id, time, target | — | result, reason, attempt_result, command_sent, container_state, disk_verification | 无 | precheck | 否 |
| precheck | event, attempt_id, time, result | expected_sha, actual_sha, owner, mode | reason, attempt_result, command_sent, container_state, disk_verification | attempt_created | pass: start_invoked；fail: 结束 | 否 |
| start_invoked | event, attempt_id, time | — | result, reason, attempt_result, command_sent, container_state, disk_verification | precheck(pass) | start_not_sent 或 start_call_begin | 否 |
| start_not_sent | event, attempt_id, time, reason | — | result, attempt_result, container_state, disk_verification | start_invoked | resolution | 否 |
| start_call_begin | event, attempt_id, time | — | result, reason, attempt_result, command_sent, container_state, disk_verification | start_invoked | start_result | 否 |
| start_result | event, attempt_id, time, result | command_sent | reason, attempt_result, container_state, disk_verification | start_call_begin | resolution | 否 |
| resolution | event, attempt_id, time, attempt_result, container_state, disk_verification | command_sent | result, reason | start_not_sent 或 start_result | 结束 | 否 |
| recovery | event, attempt_id, time, action | — | 其它全部 | 任意合法事件之后、下一条事件之前 | 下一条合法事件 | 是（最多一次） |

**交叉约束**：

- `precheck=fail` → 不产生 `start_invoked`、`resolution`，attempt 结束；
- `start_not_sent` 的 `reason` 必填，且原子操作后必产生 `resolution`；
- `start_result.result=exit_0` 或 `exit_nonzero` → `command_sent` 若出现必须为 `yes`；
- `start_result.result=result_unknown` → `command_sent` 若出现必须为 `unknown`；
- `resolution.attempt_result=exit_0/exit_nonzero` → `command_sent=yes`；
- `resolution.attempt_result=not_sent` → `command_sent=no`；
- `resolution.attempt_result=result_unknown` → `command_sent=unknown`；
- `resolution.attempt_result=unrecorded` → `command_sent=unknown`；
- `container_state`/`disk_verification` 独立于 `attempt_result`，不得互相推断；
- `recovery` 不改变状态机，只标记行边界修复；位置必须在被修复行之后、下一事件之前；最多一次。

#### 3.5.3 严格 JSON 校验

- 只接受 JSON 对象；拒绝数组/标量；
- 拒绝重复键；拒绝 `NaN`/`Infinity`；
- 按 3.5.2 校验字段类型/格式/枚举/前置/后继/重复；
- 任一行不满足 → 非法行，按 3.5.4 处理。

#### 3.5.4 JSON 合法性处理

| 情况 | 处理 |
|---|---|
| 合法 + 有换行 | 可追加 |
| 合法 + 无换行 | 锁内 append `\n` → fsync → append `recovery` → fsync → 才允许后续 |
| 非法 + 无换行 | 原字节保留；停止追加、只读取证、不启动 |
| 非法 + 有换行 | 原字节保留；停止追加、只读取证、不启动 |
| 中间行非法 | 停止追加、只读取证、不启动 |
| 连续非法/无法定位 | 停止追加、只读取证、不启动 |

- 恢复任一步失败 → 停止后续追加与启动；不覆盖/截断历史。

#### 3.5.5 首次创建与追加（含身份核验失败矩阵）

**锁顺序**：全局锁 → attempt 锁；释放 attempt → 全局。

**A. 首次创建（precheck=pass）**

1. 全局锁已持有；获取 attempt 锁（失败 → 不创建、报告）；
2. 用已验证 logdir fd 创建临时文件（`O_CREAT|O_EXCL|O_NOFOLLOW`）；
3. 写 `attempt_created`；
4. 写 `precheck`；
5. 写 `start_invoked`；
6. 临时文件 `fsync`；
7. 不覆盖原子创建正式文件（`linkat`/`renameat2`）；目标已存在失败；
8. 删除临时文件；
9. 目录 `fsync`；
10. 全部成功才允许 `docker start`；
11. 释放 attempt 锁。

**B. 首次创建（precheck=fail）**

1. 写 `attempt_created`；
2. 写一条 `precheck(fail)`；
3. 临时文件 `fsync`；
4. 原子创建正式文件；
5. 删除临时文件；
6. 目录 `fsync`；
7. **直接返回，绝不 `docker start`**；不产生 `resolution`。

**C. 失败矩阵（含身份核验）**

| 失败步骤 | 可能状态 | 继续？ | 启动？ | 现场 |
|---|---|---|---|---|
| 临时文件创建失败 | 无文件 | 否 | 否 | 报告 |
| 临时文件 `fstat` 失败 | 文件存在但身份未证 | 否 | 否 | 保留，只读取证 |
| 事件写入失败 | 临时文件残缺 | 否 | 否 | 保留临时文件，只读取证 |
| 临时文件 `fsync` 失败 | 临时文件存在 | 否 | 否 | 保留 |
| 正式文件创建失败 | 临时文件存在、目标无 | 否 | 否 | 保留临时文件 |
| 正式化 `fstatat` 失败 | 目录项未证 | 否 | 否 | 保留，只读取证 |
| 正式化 `dev/ino` 不一致 | 身份不匹配 | 否 | 否 | 保留，只读取证 |
| 临时文件删除失败 | 正式文件已存在、临时文件残留 | 否 | 否 | 保留残留，报告 |
| 目录 `fsync` 失败 | 正式文件可能已存在 | 否 | 否 | 标记 `state_uncertain`，保留现场 |

**D. 追加（含身份核验）**

1. 全局锁已持有；获取 attempt 锁；
2. `openat` + `fstat` + `fstatat` 身份核验（3.5.1）；
3. 严格 JSON 校验；
4. append 一条完整事件；
5. 校验写入完整；文件 `fsync`；
6. 任一步失败（含 `fstat`/`fstatat` 失败、`dev/ino` 不一致）→ 不追加、不启动、保留现场、只读取证；
7. 释放 attempt 锁。

- 不得为清理临时文件而覆盖/截断已有正式日志。

#### 3.5.6 锁设计

**全局部署互斥锁**：

- 路径固定；目录链从 `/` 逐级 `openat` + `fstat`；
- `openat(lockdir_fd, "deploy.lock", O_RDWR|O_CREAT|O_NOFOLLOW, 0600)`；
- `fstat(fd)` 核验 regular/root/0600；
- `fstatat(lockdir_fd, "deploy.lock", AT_SYMLINK_NOFOLLOW)` 与 `fstat(fd)` 比较 `dev/ino`；
- `flock(LOCK_EX|LOCK_NB)`；
- 锁目录必须 root 且不可被外部替换；
- 获取失败 → 零改动、退出。

**attempt 日志锁**：同目录、同一套 fd/fstat/flock 规则。

#### 3.5.7 信号与异常

- 安装 SIGINT/SIGTERM 处理器，转事务中断，进入 `finally` 清理；
- 锁获取中 → 停止获取，不继续；
- 日志写入中 → 完成当前原子写或停止；不启动；
- Docker 调用中 → 等待返回或超时；无法取得结果记 `result_unknown`；**不自动重试**；
- 清理中再次信号 → 不再嵌套清理，保留现场后退出；
- SIGKILL/进程崩溃 → 无法执行清理，依赖内核释放 `flock`；日志按 3.5.4 恢复规则处理。

### 3.6 入口边界（内部/系统分层）

- 项目内部：`deploy.sh` 唯一入口；`lib/` 禁止独立执行；`start_verified` 不导出；
- 系统级：sudoers、Docker socket 权限、ACL 决定外部主体能否直接调用 Docker；
- 未实现系统级控制时，明确：**不保证拥有 Docker 权限的外部主体无法绕过 `deploy.sh`**；
- 负向测试：内部辅助脚本、内部调用链、系统外部直接 Docker（第三类不能仅靠脚本测试证明）。

### 3.7 测试矩阵

1. 配置初始信任根；解析；
2. 父目录逐级；非 root 判据；
3. 日志目录 fd 链；日志文件 fstat/fstatat 身份核验；替换 inode 失败；
4. 三维状态组合；
5. 事件 Schema：逐事件必需/可选/禁止/前置/后继/重复；交叉约束；未知字段；
6. JSON 严格：重复键/NaN/Infinity/非对象；时间日历有效性；owner 格式；
7. 首建：precheck fail 不启动且无 resolution；pass 才启动；失败矩阵各步骤（含身份核验失败）；
8. 追加：fstat/fstatat 失败、dev/ino 不一致 → 不追加不启动；
9. 锁顺序：全局→attempt；异常/信号 finally；事务失败仍持锁；

### 3.8 竞态

- 0777/0666 下检查到 Docker 加载之间文件可能被替换；
- 配置读取→使用竞态；日志/锁目录可被替换；
- `flock` 不阻止外部写入者；
- 不能宣称竞态消除；权限基线是根治前提。

## 四、现实约束

当前 0777 环境可能无法通过配置/日志/锁目录检查；设计通过后也不能直接施工/部署；先完成权限基线评估与整改；不得为让脚本跑起来放宽 fail-closed。

## 五、风险

1. 竞态未根治（依赖权限基线）；
2. 启动字节一致 ≠ 权限安全；
3. 日志/锁目录可能不满足前置条件，届时 fail-closed 不启动；
4. dry-run 与真实 Docker 差异；
5. 系统级 Docker 权限无法由脚本保证。

## 六、待复审

1. 自动重试删除与 `result_unknown` 停止自动操作；
2. 事件状态机与交叉约束；
3. 身份核验失败矩阵；
4. `recovery` 在状态机中的位置；
5. 时间/owner 格式与有效性。
