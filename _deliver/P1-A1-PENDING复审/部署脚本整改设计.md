# 部署脚本整改设计（start_verified 统一入口）v3

- **文档类型**：整改设计（不施工、不动线上）
- **任务**：解决部署脚本所有分支绕过 `start_verified()` 的问题
- **版本**：v3（v2 有条件通过；补 deploy.env 严格解析、重启后失败状态、invoked 遗留处理）
- **日期**：2026-11-22
- **更新时间**：2026-11-22 15:15（Asia/Shanghai）
- **当前状态**：**修订完成，待复审；未修改脚本、未改线上**

## 〇、v2 返修点

1. 预期值**唯一来源固定为 `deploy.env`**，删除“或脚本顶部常量”的替代方案；
2. `start_verified` 改为**单参数 `target`**，函数内部从目标映射取 SHA，拒绝任意 target/SHA 组合；
3. 明确**禁止裸 `docker restart`**，定义 `restart_verified(target)` 的“停止 → 核验 → 启动”受控流程；
4. 启动日志拆成**核验阶段**与**启动阶段**两条记录，覆盖启动失败/中断；
5. 新增**校验与启动竞态**分析：0777/0666 下无法仅靠一次 SHA 检查消除，列为未解决风险，与权限基线整改建立依赖；
6. 静态检查之外增加**分支测试矩阵**，证明失败路径无法绕过统一入口。

## 一、现状缺陷（已证实）

1. `p3_deploy_stepA.sh` 的 `BACKUP_MISMATCH` 分支裸 `sudo docker start astrbot`，未执行 3.3.1 三项核验；
2. 备份失败、复制失败、`mv` 失败等分支也有裸 `docker start`；
3. 预期 SHA 硬编码，且误写为 v6（`c4497e04…`），实际 v14（`2f180cf0…`）；
4. “启动完整性核验”与“权限安全基线”未分开；
5. 无统一启动日志（expected/actual）。

## 二、目标

1. **所有** `docker start` / `docker restart` 只能通过统一入口；
2. 启动前实际读取磁盘 `main.py`，核验 SHA、属主、权限；
3. 目标与 SHA 绑定，不接受任意组合；
4. 失败不启动、报告、人工恢复；
5. 启动尝试两阶段留痕；
6. 明确竞态未根治，依赖权限基线整改。

## 三、设计

### 3.1 唯一配置来源

`deploy.env`（**唯一来源**，不保留脚本顶部常量作为替代）：

```text
TARGET_CANDIDATE_SHA=bba95b712d6d0708ed23c34a97f55c2375ea66b4e2bab3b8995bd2fb26de627f
TARGET_V14_SHA=2f180cf0be727671a08ad98a5a15fd764bdc1bfe7867c939f6feeb12185550f0
EXPECTED_OWNER=root:root
EXPECTED_MODE=666
```

### 3.1.1 严格解析

- 只接受 `KEY=VALUE`，一行一对；
- 忽略空行与整行 `#` 注释；
- **白名单键**：`TARGET_CANDIDATE_SHA`、`TARGET_V14_SHA`、`EXPECTED_OWNER`、`EXPECTED_MODE`；
- 未知键、重复键、缺键 → 失败；
- 不允许引号、空格、续行、变量展开、`export`；
- 值类型校验：
  - SHA：`^[0-9a-f]{64}$`；
  - OWNER：必须为 `root:root`（或与部署前记录一致）；
  - MODE：`^0?[0-7]{3,4}$`，且必须与部署前记录一致；
- 文件权限：`deploy.env` 属主 `root`、权限不宽于 `0640`；否则失败（防止被改写）；
- 不读取 shell 环境变量覆盖，不读取脚本顶部常量；
- 解析失败 → 不启动、记录、报告。

### 3.1.2 交叉核对

- `TARGET_V14_SHA` 必须等于备份实际 SHA 与部署准备报告基线；
- `TARGET_CANDIDATE_SHA` 必须等于候选 snapshot SHA；
- 不一致 → 中止，不启动。

### 3.2 目标与 SHA 绑定

```text
TARGETS = {
  "candidate": TARGET_CANDIDATE_SHA,
  "v14":       TARGET_V14_SHA,
  "recovered-v14": TARGET_V14_SHA,
}

start_verified(target):
  expected_sha = TARGETS[target]        # target 未知 → 立即失败，不启动
  读取磁盘 main.py 的 SHA/属主/权限
  核验 SHA == expected_sha
  核验 属主 == EXPECTED_OWNER
  核验 权限 == EXPECTED_MODE
  写 precheck 日志（target/expected/actual/result）
  三项全过 → docker start
  写 start 日志（invoked/result）
  任一项失败 → 不启动；写 precheck fail；返回非零
```

- `start_verified` **只接受 target**，不接受调用方传 SHA；
- `TARGETS` 由 `deploy.env` 构建；未知 target 直接失败；
- 目标与 SHA 的映射在启动前打印一次，供人工核对。

### 3.3 分支矩阵（全部单参数）

| 分支 | 启动调用 |
|---|---|
| 正常部署（替换后） | `start_verified(candidate)` |
| 备份失败 | `start_verified(v14)` |
| 备份校验不一致 | 先确认/恢复原文件，`start_verified(v14)` |
| 临时文件复制/校验失败 | 删临时文件，`start_verified(v14)` |
| `mv` 失败 | 恢复备份，`start_verified(recovered-v14)` |
| 回滚 | 恢复备份，`start_verified(recovered-v14)` |
| 启动失败后重试 | 仍调用 `start_verified(当前 target)`，禁止裸 start/restart |
| 验证失败（测试 FAIL） | 不自动启动/不自动回滚；报告，由主人决定；回滚走 v14 分支 |

### 3.4 restart 语义

- **禁止裸 `docker restart`**；脚本静态检查同时禁止 `docker (start|restart)` 出现在统一入口之外；
- 确需重启时用 `restart_verified(target)`：
  1. `docker stop`（失败/仍运行 → 不继续，报告）；
  2. 核验磁盘 `main.py` 三项（同 `start_verified` 的检查）；
  3. 三项通过才 `docker start`；
  4. 写 precheck/start 两阶段日志；
- `restart_verified` 不接受“跳过核验直接 restart”的选项。

### 3.4.1 重启后核验失败：停止状态与人工恢复边界

场景：`restart_verified` 已完成 stop→核验→start，但启动后复核（inode/mtime/SHA）失败或容器异常。

状态定义：

- `STOPPED_UNVERIFIED`：容器停止且磁盘文件未通过核验；保持停止，不自动启动；保留现场；写日志；报告主人。
- `RUNNING_UNVERIFIED`：容器已运行但复核失败；**不自动 stop/restart**（避免掩盖现场/二次风险）；写日志；报告；由主人决定。

人工恢复边界：

- 不自动启动未验证文件；
- 不自动覆盖/删除文件；
- 不自动回滚（需主人批准后按 v14 恢复 + 三项校验）；
- dsh 只读取证 + 报告；恢复动作需主人明确批准。

### 3.5 启动日志（两阶段）

路径：`/opt/astrbot/shared/记忆/部署日志/start-attempt-<timestamp>.json`（每次尝试一个文件）。

记录两个阶段：

```json
{
  "time": "...",
  "target": "candidate",
  "expected_sha": "...",
  "actual_sha": "...",
  "owner": "root:root",
  "mode": "666",
  "precheck": "pass | fail",
  "start": "not_invoked | invoked | success | failed | interrupted"
}
```

- 先写 `precheck`（核验结果），再在 `docker start` 前后更新 `start`；
- 启动失败、进程中断、脚本异常退出都要留下可识别状态（例如 `start=failed` 或 `start=interrupted`）；
- 日志不写正文/敏感内容。

### 3.5.1 `invoked` 遗留状态

`start=invoked` 表示已调用 `docker start` 但未记录结果（脚本被杀、断电、中断）。

下次运行或巡检发现 `invoked` 时：

1. 读取容器实际状态 + 磁盘 `main.py` 三项；
2. 容器 Running 且三项与 expected 一致 → 追加 `resolution=recovered_success`；
3. 容器 Running 但三项不一致 → `resolution=success_unverified` / `postcheck=fail`，不自动操作，报告；
4. 容器 Stopped → `resolution=unknown_stopped`，不自动启动，报告；
5. **不允许把 `invoked` 当 success**；保留原记录，追加 `resolution` 字段，不覆盖历史；
6. 巡检为只读；部署脚本启动时扫描最近日志。

### 3.6 静态检查 + 分支测试

- **静态检查（基础）**：`grep -nE 'docker (start|restart)' deploy.sh`，除 `start_verified`/`restart_verified` 内部外出现即失败；
- **分支测试（必须）**：对每个失败分支（备份失败、备份校验失败、复制失败、`mv` 失败、回滚、启动失败重试）模拟执行，断言：
  1. 只调用统一入口；
  2. 核验失败时不启动；
  3. 日志写出 precheck/start 两阶段；
  4. 非零退出并报告；
- **dry-run**：`START_VERIFIED_DRY_RUN=1` 只核验不启动，覆盖全部 target；
- **映射测试**：未知 target、错误 target/SHA 组合必须失败；
- **静态检查不能替代分支测试**：grep 只能发现字面裸调用，不能证明控制流。

补充测试：

1. **`deploy.env` 解析**：缺键、多余键、重复键、非法 SHA、非法 MODE、权限宽于 0640、环境变量覆盖尝试 → 全部失败且不启动；
2. **重启后复核失败**：模拟启动后 SHA/inode 变化，断言进入 `STOPPED_UNVERIFIED` 或 `RUNNING_UNVERIFIED`，不自动 stop/restart/回滚，写日志并报告；
3. **`invoked` 遗留**：模拟脚本中断，下次运行能识别并追加 `resolution`（recovered_success / success_unverified / unknown_stopped），不把 `invoked` 当 success；
4. **target/SHA 映射**：未知 target、target 与 SHA 不匹配 → 失败且不启动。

### 3.7 校验与启动之间的竞态（未解决风险）

事实：目录 0777、文件 0666；`start_verified` 检查完 SHA 到 Docker 真正启动并加载文件之间，文件仍可能被其他进程/本地用户替换。

- 部署脚本内部 `flock` 只能防并发部署，**不能阻止不遵守该锁的其他写入者**；
- 因此在权限收紧前，**竞态无法仅靠一次 SHA 检查消除**；
- 缓解措施（不能根治）：
  1. 检查与启动窗口最小化；
  2. 启动后再次核验 `inode/mtime/SHA`，若与启动前不一致，记录并停止/告警；
  3. 启动后核验失败时，不能假设已加载的进程一定安全（可能已加载被替换文件），需回滚/人工处理；
- **依赖**：权限基线整改（目录 0755、文件 0644 等）是根治前提；在权限收紧前，本设计只能声明“竞态已缓解、未消除”，不能宣称绝对安全。

## 四、风险

1. 竞态未根治（依赖权限基线）；
2. `start_verified` 只保证“启动字节与目标一致”，若权限本身 0666，核验一致不代表权限安全；
3. 启动日志目录权限也需评估；
4. 分支测试若只 dry-run，仍可能与真实 Docker 行为有差异；
5. `deploy.env` 本身若被篡改（0777 环境），目标/SHA 也会被改；需权限基线配套。
