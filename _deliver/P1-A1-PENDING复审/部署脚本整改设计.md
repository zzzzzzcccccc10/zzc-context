- **版本**：v10（v9 返修；顶层事务锁、安全打开锁、状态改名、UNRECORDED 事件模型、账号组判定、JSONL 严格校验）

- **更新时间**：2026-11-22 16:30（Asia/Shanghai）

## 〇、v10 返修点

1. **唯一顶层部署事务**：所有分支（备份/替换/恢复/stop/start/resolution）只经 `deploy_transaction()`；全局锁在**任何文件/容器操作之前**获取，覆盖完整事务；`start_verified` 为内部函数，外部不可绕过。
2. **锁安全打开**：`O_NOFOLLOW` + 目录 fd + `openat` + `fstat` 核验实际打开对象；路径对象与 fd 不一致即失败；全局锁与 attempt 锁同一原则。
3. **状态改名**：`RUNNING_DISK_MATCH` / `RUNNING_DISK_MISMATCH` / `RUNNING_DISK_UNVERIFIED` / `STOPPED_UNVERIFIED` / `STATE_UNKNOWN_UNVERIFIED`；`attempt_result` 独立字段，不再有 `RUNNING_VERIFIED`。
4. **UNRECORDED 事件模型**：`start_result.result` 只表示实际持久化的 `exit_0`/`exit_nonzero`；写入失败时进程内 `attempt_result=unrecorded`；后续 resolution 可带该字段说明“先前记录失败”，不声称原始事件已写。
5. **非 root/组判定**：主 GID + 附加组、name/uid/gid 与白名单一致、专用账号可验证判据、提权组白名单维护、组信息不完整失败、`deploy.env` 引导顺序。
6. **JSONL 严格校验**：JSON 对象、拒绝重复键/NaN/Infinity、必需字段 schema；合法缺换行的恢复持久化顺序。

## 一、现状缺陷（已证实）

1. `p3_deploy_stepA.sh` 的 `BACKUP_MISMATCH` 分支裸 `sudo docker start astrbot`；
2. 备份失败、复制失败、`mv` 失败等分支也有裸 `docker start`；
3. 预期 SHA 硬编码，且误写为 v6（`c4497e04…`），实际 v14（`2f180cf0…`）；
4. “启动完整性核验”与“权限安全基线”未分开；
5. 无统一启动日志。

## 二、目标

1. 所有部署动作只经唯一顶层事务；
2. 全局锁覆盖完整事务，锁失败零改动；
3. 启动前核验 SHA、属主、权限；
4. 目标与 SHA 绑定；
5. 日志可靠、严格可解析、不可覆盖；
6. 状态记录拆三维，不互相推断；
7. 失败不启动、报告、人工恢复；
8. 竞态未根治，依赖权限基线。

## 三、设计

### 3.1 配置来源与保护

#### 3.1.1 唯一来源、严格解析与引导顺序

`deploy.env` 是唯一来源；不保留脚本顶部常量、不读 shell 环境变量覆盖。

- 只接受 `KEY=VALUE`，一行一对；忽略空行与整行 `#` 注释；
- 白名单键：`TARGET_CANDIDATE_SHA`、`TARGET_V14_SHA`、`EXPECTED_OWNER`、`EXPECTED_MODE`、`TRUSTED_OWNERS`、`PRIVILEGED_GROUPS`；
- 未知键、重复键、缺键 → 失败；
- 不允许引号、空格、续行、变量展开、`export`；
- SHA：`^[0-9a-f]{64}$`；OWNER：`root:root`；MODE：`^(?:[0-7]{3}|0[0-7]{3})$`；
- `TRUSTED_OWNERS`：`name:uid:gid` 逗号分隔；必须含 `root:0:0`；
- `PRIVILEGED_GROUPS`：组名逗号分隔；至少 `sudo,wheel,adm`，可追加；
- **引导顺序**：先验证 `deploy.env` 的绝对路径、父目录、属主、权限、无 symlink（3.1.2），**再**信任其中的白名单；不得先信任白名单再验证配置来源（避免循环信任）；
- 解析失败 → 不启动、记录、报告。

#### 3.1.2 路径、父目录与属主（可执行判据）

1. 绝对路径，拒绝相对路径；
2. 从 `/` 到直接父目录逐级 `lstat`（拒绝 symlink）；
3. **允许属主**：
   - `root:0:0`；或
   - 在 `TRUSTED_OWNERS` 内，且**同时满足**：
     a. passwd 记录 `name/uid/gid` 与白名单**三者完全一致**；
     b. 系统/服务账号：`100 <= uid <= 999`（或显式标注为服务账号），且 shell 为 `/usr/sbin/nologin` / `/bin/false`；
     c. 主 GID **和**附加组均不属于 `PRIVILEGED_GROUPS`；
     d. 只读读取 `/etc/passwd`、`/etc/group`、`getent group`；来源不完整/不可读 → 失败关闭；
   - 任一无法证明 → 失败关闭；权限位符合 ≠ 目录可信；
4. 任一级 world-writable → 不启动；
5. **group-writable**：读目录 gid → 同时核对**主 GID 成员**与 `getent group` 附加成员 → 存在不在 `TRUSTED_OWNERS` 的账号 → 失败；组信息不可完整取得 → 失败；
6. 文件 root、mode ≤0640、非 symlink；
7. 检查不能消除替换竞态；不宣称可靠防篡改。

#### 3.1.3 读取与使用竞态

- 读取后记录 `inode/mtime/SHA`，使用前再核验；
- 不能根治；依赖权限基线；
- 两次 stat 一致 ≠ 配置安全。

#### 3.1.4 交叉核对

- `TARGET_V14_SHA` = 备份实际 SHA = 部署准备报告基线；
- `TARGET_CANDIDATE_SHA` = 候选 snapshot SHA；
- 不一致 → 中止。

### 3.2 唯一顶层部署事务

```text
deploy_transaction(action, target):
  acquire_global_lock()          # 见 3.5.4；失败 → 零改动、退出
  ... 备份 / 替换 / 恢复 / stop / start_verified / resolution ...
  release_global_lock()
```

- **所有部署分支只能经由 `deploy_transaction()` 进入**；脚本对外只暴露该入口；
- 任何文件替换、恢复、`docker stop`、`docker start` 都必须在全局锁内；
- `start_verified(target)` 是**内部函数**，不得被顶层事务外的代码调用；
- 锁获取失败：不备份、不替换、不 stop、不 start、不改线上任何文件或容器状态；
- 分支矩阵中的每个分支都是 `deploy_transaction` 内部的一个 action。

#### 3.2.1 `start_verified`（内部）

```text
start_verified(target):
  expected_sha = TARGETS[target]
  读取磁盘 main.py 的 SHA/属主/权限
  核验三项
  追加 precheck（pass/fail）
  fail → 不启动（不写 start_invoked）
  持久化 start_invoked → 失败则不启动
  docker start
  attempt_result = exit_0 | exit_nonzero | unrecorded
  container_state = query() → running | stopped | unknown
  disk_verification = check() → match | mismatch | check_failed
  （见 3.2.3）
```

### 3.2.2 三维状态与对外映射

| 维度 | 取值 |
|---|---|
| `attempt_result` | `exit_0` / `exit_nonzero` / `unrecorded` |
| `container_state` | `running` / `stopped` / `unknown` |
| `disk_verification` | `match` / `mismatch` / `check_failed` |

| container_state | disk_verification | 对外状态 |
|---|---|---|
| running | match | `RUNNING_DISK_MATCH` |
| running | mismatch | `RUNNING_DISK_MISMATCH` |
| running | check_failed | `RUNNING_DISK_UNVERIFIED` |
| stopped | 任意 | `STOPPED_UNVERIFIED` |
| unknown | 任意 | `STATE_UNKNOWN_UNVERIFIED` |

- **不再使用 `RUNNING_VERIFIED`**：`RUNNING_DISK_MATCH` 只表示“Running 且磁盘相符”，不代表已加载目标代码；
- `attempt_result` 独立保留；容器/磁盘正常也不能掩盖“本次启动命令结果未记录”；
- 所有状态只读记录、保留现场、报告；不自动 stop/restart/回滚。

#### 3.2.3 UNRECORDED 与事件模型

- `start_result` 事件只表示**实际成功持久化**的命令结果：`exit_0` / `exit_nonzero`；
- `start_result` 写入失败 → 进程内 `attempt_result=unrecorded`；**不写一条“unrecorded 的 start_result”**（写不进去）；
- 后续 resolution 若写入成功，可带 `attempt_result=unrecorded` 字段，语义是“此前记录失败”，不是“原始事件已写入”；
- resolution 也写入失败 → 保留现场与已有日志，**不声称完整持久化**；
- 区分四个事实：Docker 返回码、命令执行异常、命令是否真正发出、日志是否写入成功。

### 3.3 分支矩阵（全部经顶层事务）

| 分支 | 事务内动作 |
|---|---|
| 正常部署 | 备份 → 替换 → `start_verified(candidate)` |
| 备份失败 | 不启动；报告；可信 v14 恢复后才 `start_verified(v14)` |
| 备份校验不一致 | 不自动启动、不自动回滚；只有可信 v14 恢复后才 `start_verified(v14)`；否则停止 |
| 临时文件复制/校验失败 | 删临时文件；确认原文件可信后 `start_verified(v14)`；否则停止 |
| `mv` 失败 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败停止 |
| 回滚 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败停止 |
| 启动失败后重试 | 仍 `start_verified(当前 target)`（事务内） |
| 验证失败（测试 FAIL） | 不自动启动/回滚；报告，由主人决定 |

### 3.4 restart 语义

```text
deploy_transaction("restart", target):
  ...（全局锁已持有）...
  docker stop
  检查容器实际状态
  start_verified(target)
```

禁止裸 `docker restart`；`restart_verified` 不再作为独立入口，改为事务内 action。

### 3.5 启动日志（JSONL）

路径：`/opt/astrbot/shared/记忆/部署日志/start-attempt-<attempt_id>.jsonl`。

#### 3.5.1 日志目录前置条件

1. 从 `/` 到日志目录逐级 `lstat`，拒绝 symlink；
2. 属主按 3.1.2；
3. 不 world-writable；group-writable 按 3.1.2 验证；
4. 日志文件（存在时）非 symlink、root、mode ≤0640；
5. 检查/创建/持久化失败 → 不启动。

#### 3.5.2 事件模型

```text
{"event":"attempt_created","attempt_id":"...","time":"...","target":"candidate"}
{"event":"precheck","attempt_id":"...","result":"pass|fail",...}
{"event":"start_invoked","attempt_id":"...","time":"..."}
{"event":"start_result","attempt_id":"...","result":"exit_0|exit_nonzero","time":"..."}
{"event":"resolution","attempt_id":"...","attempt_result":"exit_0|exit_nonzero|unrecorded","container_state":"...","disk_verification":"...","time":"..."}
{"event":"recovery","attempt_id":"...","action":"added_line_terminator","time":"..."}
```

- `start_result.result` **不含 unrecorded**；
- `resolution` 可带 `attempt_result=unrecorded` 说明先前记录失败；
- 严格 schema：必须含 `event`、`attempt_id`、`time`；按事件类型校验必需字段。

#### 3.5.3 严格 JSON 校验

- 只接受 JSON **对象**；拒绝数组/标量；
- 拒绝重复键（解析时检测）；
- 拒绝 `NaN`/`Infinity`；
- 校验必需字段与类型（schema）；
- 任一行不满足 → 非法行，按 3.5.4 处理。

#### 3.5.4 JSON 合法性处理

先判末行换行，再独立判 JSON：

| 情况 | 处理 |
|---|---|
| 合法 + 有换行 | 可追加 |
| **合法 + 无换行** | 锁内：append `\n` → `fsync` → append `recovery(added_line_terminator)` → `fsync` → 才允许后续事件 |
| 非法 + 无换行 | 原字节保留；停止追加、只读取证、不启动 |
| 非法 + 有换行 | 原字节保留；停止追加、只读取证、不启动 |
| 中间行非法 | 停止追加、只读取证、不启动 |
| 连续非法/无法定位 | 停止追加、只读取证、不启动 |

- 恢复流程任一步写入/持久化失败 → 停止后续追加与启动；
- 不覆盖/截断/重写历史。

#### 3.5.5 创建与追加

**A. 首次创建**

1. 受保护目录 `O_CREAT|O_EXCL|O_NOFOLLOW` 临时文件；
2. 写 `attempt_created`、`precheck`；precheck fail 只写 fail，不写 `start_invoked`；
3. precheck pass 写 `start_invoked`；
4. 临时文件 `fsync`；
5. 不覆盖目标的原子创建（`link` / `renameat2(RENAME_NOREPLACE)`）；目标已存在 → 失败；
6. 删临时文件；父目录 `fsync`；
7. 全成功才允许 `docker start`。

**B. 已有文件追加**

1. 获取 attempt 锁；
2. 严格 JSON 校验（3.5.3/3.5.4）；
3. append 一条完整事件；
4. 校验写入完整；
5. 文件 `fsync`；
6. 任一步失败 → 不启动。

**C. 目录 fsync 失败**

- 正式文件已创建但目录 fsync 失败：可能留下含 `start_invoked` 的文件；
- 不启动；标记 `state_uncertain`；不假设 Docker 已执行。

#### 3.5.6 锁设计（两级，安全打开）

**全局部署互斥锁**：

- 路径固定：`/opt/astrbot/shared/记忆/部署锁/deploy.lock`；
- 打开方式：
  1. `open(dir, O_DIRECTORY|O_NOFOLLOW)` 取得受保护目录 fd；
  2. 首次：`openat(dirfd, "deploy.lock", O_RDWR|O_CREAT|O_EXCL|O_NOFOLLOW, 0600)`；
  3. 后续：`openat(dirfd, "deploy.lock", O_RDWR|O_NOFOLLOW)`；
  4. `fstat(fd)` 核验：regular file、属主 root、mode 0600、inode 与预期一致；
  5. `flock(fd, LOCK_EX|LOCK_NB)`；
- 路径对象与已打开 fd 不一致（如被 rename 替换）→ 失败；
- 锁文件长期保留；异常退出由 `flock` 自动释放；
- 获取失败 → 零改动、退出；
- 覆盖完整事务（备份→替换→stop→start→resolution）；
- 只防并发部署，不阻止不遵守锁的外部写入者；不能替代权限基线。

**attempt 日志锁**：

- 每 attempt 一个锁文件；同一套 `O_NOFOLLOW`/`openat`/`fstat`/`flock` 原则；
- 只防同一 attempt 并发写；
- 失败 → 不写、不启动。

### 3.6 静态检查与完整调用链

`grep` 只是基础检查：审查所有脚本/辅助脚本/实际 Docker 调用路径；负向测试；人工调用链复核；grep 无命中不能宣称无绕过。

### 3.7 测试矩阵

1. deploy.env 解析（含白名单键、引导顺序、缺/非法）；
2. 父目录逐级；非 root 判据（name/uid/gid 一致、主 GID+附加组、提权组、组来源不可读）；
3. 读取与使用间替换；
4. 三维状态组合（attempt_result × container_state × disk_verification）；
5. 对外映射：RUNNING_DISK_MATCH/MISMATCH/UNVERIFIED、STOPPED、STATE_UNKNOWN；
6. JSON 严格校验：重复键/NaN/Infinity/非对象/字段缺失/空文件/部分写入；
7. JSON 合法性：合法无换行恢复（append `\n`→fsync→recovery→fsync）、非法（无/有换行/中间/连续）；
8. 首建：O_EXCL|O_NOFOLLOW、不覆盖原子创建、目标已存在失败、目录 fsync 失败；
9. 全局锁：所有分支只经顶层事务；两个部署尝试互斥；锁失败零改动；锁文件 symlink/rename 替换/openat+fstat 失败；
10. attempt 锁并发拒绝；
11. precheck fail 不写 invoked；
12. 日志目录/创建/持久化失败 → 不启动；
13. 备份校验不一致不自动启动/回滚；
14. Docker 非零但容器异常；
15. 负向测试：顶层事务外调用 `start_verified` 被拒绝；
16. target/SHA 映射。

### 3.8 竞态

- 0777/0666 下检查到 Docker 加载之间文件可能被替换；
- 配置读取→使用竞态；日志文件/目录可被替换；
- `flock` 不阻止外部写入者；
- 不能宣称竞态消除；权限基线是根治前提。
