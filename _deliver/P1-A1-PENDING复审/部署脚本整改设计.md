## 〇、v7 返修点

1. **日志不可覆盖**：正式日志文件用“排他创建 + 不覆盖目标的原子创建”（`O_CREAT|O_EXCL` 临时文件、`link` 或 `renameat2(RENAME_NOREPLACE)`）；目标已存在 → 失败，不替换；不能用“先检查再 rename”。
2. **残缺尾行恢复**：检测不完整尾行；原字节保留、不覆盖/不截断；追加前建立行边界（仅补 `\n`）、追加 `corrupt_line`/`recovery` 事件；无法确认边界 → 停止写入、报告、不启动。
3. **状态机失败分支**：新增 `container_state_unknown`、`disk_check_failed`、`resolution_unrecorded`；明确“无法读取 ≠ 不匹配”；不自动 stop/restart/回滚；Docker 已启动后日志失败仍须只读核查并记录“无法持久化”。
4. **父目录属主范围**：明确允许 root；非 root 需证明可信主体；无法证明失败关闭；权限位符合 ≠ 目录可信。
5. 细节：JSONL 单写者、首建事件条件（precheck fail 不写 start_invoked）、目录 fsync 失败的 `state_uncertain`、状态核验失败分类。

## 一、现状缺陷（已证实）

1. `p3_deploy_stepA.sh` 的 `BACKUP_MISMATCH` 分支裸 `sudo docker start astrbot`，未执行三项核验；
2. 备份失败、复制失败、`mv` 失败等分支也有裸 `docker start`；
3. 预期 SHA 硬编码，且误写为 v6（`c4497e04…`），实际 v14（`2f180cf0…`）；
4. “启动完整性核验”与“权限安全基线”未分开；
5. 无统一启动日志（expected/actual）。

## 二、目标

1. **所有** `docker start` / `docker restart` 只能通过统一入口；
2. 启动前实际读取磁盘 `main.py`，核验 SHA、属主、权限；
3. 目标与 SHA 绑定，不接受任意组合；
4. 启动日志必须可靠落盘、不可覆盖、可解析，否则不启动；
5. 启动后记录容器状态与磁盘复核，区分“不匹配”与“无法读取”；
6. 失败不启动、报告、人工恢复；
7. 明确竞态未根治，依赖权限基线整改。

## 三、设计

### 3.1 配置来源与保护

#### 3.1.1 唯一来源与严格解析

`deploy.env` 是**唯一来源**；不保留脚本顶部常量、不读 shell 环境变量覆盖。

- 只接受 `KEY=VALUE`，一行一对；忽略空行与整行 `#` 注释；
- **白名单键**：`TARGET_CANDIDATE_SHA`、`TARGET_V14_SHA`、`EXPECTED_OWNER`、`EXPECTED_MODE`；
- 未知键、重复键、缺键 → 失败；
- 不允许引号、空格、续行、变量展开、`export`；
- 值类型校验：
  - SHA：`^[0-9a-f]{64}$`；
  - OWNER：唯一判定来源 `root:root`；部署前记录仅用于核对，不一致即失败；
  - MODE：`^(?:[0-7]{3}|0[0-7]{3})$`；
- 解析失败 → 不启动、记录、报告。

#### 3.1.2 路径、父目录与属主

1. `deploy.env` 使用**绝对路径**，拒绝相对路径；
2. **从 `/` 到直接父目录逐级检查**：`lstat` 拒绝 symlink，核验属主、权限；
3. **属主范围**：
   - 允许 `root`；
   - 非 root 属主必须能证明属于可信主体（例如专用系统账号、受控组）；**无法证明 → 失败关闭**；
   - 权限位符合要求 **不等于** 目录可信；属主不可信时，即使不是 world/group-writable 也失败；
4. **world-writable**：任一级 others 有 `w` → 不启动；
5. **group-writable**：任一级 group 有 `w` 时，仅当该组可证明只含 root/可信主体才可接受；否则失败；
6. 文件本身：属主 `root`、mode 不宽于 `0640`、非 symlink；
7. 上述检查不能消除“检查后被替换”的竞态；权限基线完成前，**不宣称可靠防篡改**。

#### 3.1.3 读取与使用竞态

- 读取后记录 `inode/mtime/SHA`，使用前再次核验；不一致 → 中止；
- 仍不能根治；与权限基线整改建立依赖；
- 不能把“两次 stat 一致”写成“配置文件安全”。

#### 3.1.4 交叉核对

- `TARGET_V14_SHA` 必须等于备份实际 SHA 与部署准备报告基线；
- `TARGET_CANDIDATE_SHA` 必须等于候选 snapshot SHA；
- 不一致 → 中止，不启动。

### 3.2 唯一启动入口与启动后状态机

```text
TARGETS = {
  "candidate": TARGET_CANDIDATE_SHA,
  "v14":       TARGET_V14_SHA,
  "recovered-v14": TARGET_V14_SHA,
}

start_verified(target):
  expected_sha = TARGETS[target]        # target 未知 → 立即失败
  读取磁盘 main.py 的 SHA/属主/权限
  核验 SHA == expected_sha
  核验 属主 == EXPECTED_OWNER
  核验 权限 == EXPECTED_MODE
  追加 precheck 事件（pass/fail）
  若 fail → 不启动、返回非零（不写 start_invoked）
  持久化 start_invoked（见 3.5.3）→ 失败则不启动
  docker start
  追加 start_result（docker_start_exit_0 / docker_start_exit_nonzero）
  读取容器实际状态
  再次读取磁盘 inode/mtime/SHA
  按 3.2.1 判定并追加 resolution
```

- **只有 `start_verified()` 内部允许实际执行 `docker start`**；
- `restart_verified(target)` 只 `docker stop` + 状态检查 + 委托 `start_verified(target)`；
- `running_disk_match` 只证明“巡检时容器 Running 且磁盘相符”，**不证明容器已加载目标代码字节**。

#### 3.2.1 resolution 判定（区分“不匹配”与“无法读取”）

| 容器状态 | 磁盘核验 | resolution |
|---|---|---|
| Running | 三项符合 | `running_disk_match` |
| Running | 三项不符 | `running_disk_mismatch` |
| Running | 读取失败/inode/mtime/SHA 不可得 | `disk_check_failed` |
| Docker 状态查询失败/无法识别 | 任意 | `container_state_unknown` |
| Stopped | 任意（未验证） | `stopped_unknown` |
| 任意 | resolution 写入失败 | `resolution_unrecorded` |

规则：

- **不得把“无法读取/查询失败”转成 `running_disk_match`**；
- 不得将核验失败转换为“成功”；
- 不自动 stop/restart/回滚；保留现场、报告；
- Docker 已启动后日志写入失败，不能假装启动未发生；仍应尽可能只读核查，并记录“无法持久化”事实。

#### 3.2.2 与 RUNNING_UNVERIFIED / STOPPED_UNVERIFIED 的映射

- `RUNNING_UNVERIFIED` = 容器 Running 且 resolution 为
  `running_disk_mismatch` / `container_state_unknown` / `disk_check_failed` / `resolution_unrecorded`；
- `STOPPED_UNVERIFIED` = 容器 Stopped 且 resolution 为 `stopped_unknown`；
- 两套状态机不并存：内部用 resolution，对外报告用 UNVERIFIED 标签；映射固定，不得各路径自行解释。

### 3.3 分支矩阵

| 分支 | 启动调用 |
|---|---|
| 正常部署（替换后） | `start_verified(candidate)` |
| 备份失败 | 不自动启动；保留现场、报告；确认可信 v14 后才 `start_verified(v14)` |
| 备份校验不一致 | **不自动启动、不自动回滚**；只有找到可信、SHA 符合 `TARGET_V14_SHA` 的 v14 文件并恢复后，才 `start_verified(v14)`；无法确认则保持停止 |
| 临时文件复制/校验失败 | 删临时文件；确认原文件可信后 `start_verified(v14)`；否则停止、报告 |
| `mv` 失败 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败则停止、报告 |
| 回滚 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败则停止、报告 |
| 启动失败后重试 | 仍调用 `start_verified(当前 target)` |
| 验证失败（测试 FAIL） | 不自动启动/回滚；报告，由主人决定 |

### 3.4 restart 语义

- **禁止裸 `docker restart`**；
- `restart_verified(target)`：

```text
restart_verified(target):
  docker stop
  检查容器实际状态（失败/仍运行 → 不继续，报告）
  start_verified(target)      # 唯一启动入口
```

### 3.5 启动日志（JSONL 事件流）

路径：`/opt/astrbot/shared/记忆/部署日志/start-attempt-<attempt_id>.jsonl`。

#### 3.5.1 日志目录安全前置条件

1. 从 `/` 到日志目录逐级 `lstat`，拒绝 symlink；
2. 属主为 `root`（非 root 需证明可信主体，否则失败）；
3. 不 world-writable；group-writable 需证明组内仅 root/可信主体；
4. 日志文件（若已存在）非 symlink、属主 `root`、mode 不宽于 `0640`；
5. 检查失败、创建失败、持久化失败 → **不得执行 `docker start`**；
6. 日志路径权限基线纳入单独的权限安全评估。

#### 3.5.2 事件模型

```text
{"event":"attempt_created","attempt_id":"...","time":"...","target":"candidate"}
{"event":"precheck","attempt_id":"...","result":"pass|fail","expected_sha":"...","actual_sha":"...","owner":"...","mode":"..."}
{"event":"start_invoked","attempt_id":"...","time":"..."}
{"event":"start_result","attempt_id":"...","result":"docker_start_exit_0|docker_start_exit_nonzero","time":"..."}
{"event":"resolution","attempt_id":"...","result":"running_disk_match|running_disk_mismatch|container_state_unknown|disk_check_failed|stopped_unknown|resolution_unrecorded","time":"..."}
{"event":"corrupt_line","attempt_id":"...","reason":"incomplete_tail","time":"..."}
{"event":"recovery","attempt_id":"...","action":"added_line_terminator","time":"..."}
```

- 每个事件独立追加；`attempt_id` 关联；每行完整合法 JSON；
- **单写者约束**：同一 attempt 只允许一个写入者；追加前获取尝试级锁（如 `flock`），锁失败 → 不写、不启动；
- 不允许并发多写者造成事件交错。

#### 3.5.3 创建与追加流程

**A. 首次创建（attempt 不存在）**

1. 在受保护目录用 **`O_CREAT|O_EXCL`** 创建临时文件（拒绝 symlink）；
2. 写入 `attempt_created`、`precheck`；**precheck 失败只写 fail，不写 `start_invoked`**；
3. precheck 通过后写入 `start_invoked`；
4. 对临时文件 `fsync`；
5. 用**不覆盖目标的原子创建**（`link` 或 `renameat2(RENAME_NOREPLACE)`）生成正式文件名；**目标已存在 → 失败，不替换**；
6. 删除临时文件；
7. 对父目录 `fsync`；
8. 全部成功后才允许 `docker start`；任一步失败 → 不启动、报告。

**B. 已有文件追加**

1. 获取尝试级锁；
2. 检查文件末尾是否完整行（以 `\n` 结尾）；
3. 以 append 写入一条完整 JSONL 事件（一次写完整行）；
4. 检查写入完整性（字节数/行完整）；
5. 对文件 `fsync`；
6. 任一步失败 → 不得执行后续启动动作。

**C. 残缺尾行恢复（v7 新增）**

1. 若文件非空且最后一行不以 `\n` 结尾：
   - 原残缺字节**保留**，禁止覆盖/截断；
   - 追加一个 `\n`，使残缺内容独立成一行（仅补行结束符，不修改原字节内容）；
   - `fsync`；
2. 追加 `corrupt_line` 事件（`reason=incomplete_tail`）与 `recovery` 事件（`action=added_line_terminator`）；
3. 建立明确行边界后，才允许追加新事件；
4. **无法确认恢复后的行边界时，停止写入、报告、不得启动**；
5. 不得通过覆盖原文件修复历史。

**D. 目录 fsync 失败（v7 新增）**

- 正式文件已 rename/link，但父目录 `fsync` 失败：可能留下含 `start_invoked` 的文件；
- **不启动**；标记 `state_uncertain`；
- 不能假设 Docker 已经执行；交后续只读取证/人工处理。

#### 3.5.4 `invoked` 遗留与 `resolution`

- 发现 `start_invoked` 遗留：读容器状态与磁盘三项，按 3.2.1 追加 `resolution`；
- 原事件保留；不把 `invoked` 当 success；
- 无法完成核验时用 `container_state_unknown` / `disk_check_failed` / `resolution_unrecorded`，不归入 match。

### 3.6 静态检查与完整调用链

`grep` **只是基础检查**：

1. 审查所有部署脚本及辅助脚本；
2. 检查所有实际执行 Docker 命令的代码路径（子进程、Python 调用、其它脚本）；
3. 对统一入口外的启动调用做负向测试；
4. 人工调用链复核；
5. grep 无命中不能宣称“不存在绕过路径”。

### 3.7 测试矩阵

1. `deploy.env` 解析（缺/多/重复/非法值/权限宽/父目录 world-writable/group-writable/非 root 属主/symlink）；
2. 父目录从 `/` 逐级检查；
3. 读取与使用间替换；
4. 重启后失败：`STOPPED_UNVERIFIED` / `RUNNING_UNVERIFIED`；
5. 状态机：match / mismatch / container_state_unknown / disk_check_failed / stopped_unknown / resolution_unrecorded；
6. JSONL 首建：`O_EXCL` 临时文件、不覆盖目标的原子创建、目标已存在失败、目录 fsync 失败 `state_uncertain`；
7. JSONL 追加：完整行/部分写入/中断；残缺尾行补 `\n`、`corrupt_line`/`recovery` 事件、无法确认边界不启动；
8. 单写者锁：并发写入被拒绝；
9. precheck fail 不写 `start_invoked`；
10. 日志目录权限/文件创建/持久化失败 → 不启动；
11. 备份校验不一致：不自动启动、不自动回滚；
12. Docker 非零但容器异常 → `docker_start_exit_nonzero` + 实际状态；
13. 负向测试：统一入口外启动调用被捕获；
14. target/SHA 映射。

### 3.8 竞态（配置 + 主文件 + 日志）

- 0777/0666 环境下，检查到 Docker 加载之间文件仍可能被替换；
- `deploy.env` 有“读取→使用”竞态；
- 日志文件/目录同样可能被替换/篡改；
- `flock` 只防并发部署，不阻止其他写入者；
- 不能宣称竞态已消除；权限基线整改是根治前提。

## 四、现实约束

当前 0777 环境可能无法通过 v6/v7 的日志/配置路径检查：

- 设计通过后也不能直接施工/部署；
- 先独立完成权限基线评估与必要整改；
- 不得为让脚本跑起来放宽 fail-closed。

## 五、风险

1. 竞态未根治（依赖权限基线）；
2. `start_verified` 只保证启动字节一致，权限 0666 下不代表安全；
3. 日志目录当前可能不满足前置条件，届时 fail-closed 不启动；
4. dry-run 与真实 Docker 行为可能有差异；
5. grep 不能单独证明无绕过。
