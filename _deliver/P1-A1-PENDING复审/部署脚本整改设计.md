# 部署脚本整改设计（start_verified 统一入口）v6

- **文档类型**：整改设计（不施工、不动线上）
- **任务**：解决部署脚本所有分支绕过 `start_verified()` 的问题
- **版本**：v6（v5 有条件通过；补 JSONL 创建/追加、启动后状态机、grep 边界）
- **日期**：2026-11-22
- **更新时间**：2026-11-22 15:45（Asia/Shanghai）
- **当前状态**：**修订完成，待复审；未修改脚本、未改线上**

## 〇、v6 返修点

1. **JSONL 创建与追加分开定义**：首次创建用“临时文件 → 写入 → fsync → 原子 rename → 目录 fsync”；已有文件用“追加一条完整事件 → 校验完整 → fsync”；部分写入不当作有效事件、不覆盖历史。
2. **启动后状态机**：`docker start` 返回后记录 `start_result` → 读容器实际状态 → 再读磁盘 inode/mtime/SHA → 追加 `resolution`；明确 `running_disk_match` / `running_disk_mismatch` / `stopped_unknown` 的转换与“不自动停/回滚”。
3. **grep 只是基础检查**：补“审查所有部署脚本/辅助脚本/实际 Docker 调用路径 + 负向测试 + 人工调用链复核”；不能凭 grep 无命中宣称无绕过。
4. **现实约束**：当前 0777 日志目录可能无法通过 v6 前置检查；**不得为让脚本跑起来放宽 fail-closed**；先独立完成权限基线评估/整改，再决定是否进入脚本施工。

## 一、现状缺陷（已证实）

1. `p3_deploy_stepA.sh` 的 `BACKUP_MISMATCH` 分支裸 `sudo docker start astrbot`，未执行三项核验；
2. 备份失败、复制失败、`mv` 失败等分支也有裸 `docker start`；
3. 预期 SHA 硬编码，且误写为 v6（`c4497e04…`），实际 v14（`2f180cf0…`）；
4. “启动完整性核验”与“权限安全基线”未分开；
5. 无统一启动日志（expected/actual）。

## 二、目标

1. **所有** `docker start` / `docker restart` 只能通过统一入口；
2. 启动前实际读取磁盘 `main.py`，核验 SHA、属主、权限；
3. 目标与 SHA 绑定，不接受任意组合；
4. 启动日志必须可靠落盘，否则不启动；
5. 启动后记录容器状态与磁盘复核，不把“exit 0”当“已加载目标代码”；
6. 失败不启动、报告、人工恢复；
7. 明确竞态未根治，依赖权限基线整改。

## 三、设计

### 3.1 配置来源与保护

#### 3.1.1 唯一来源与严格解析

`deploy.env` 是**唯一来源**；不保留脚本顶部常量、不读 shell 环境变量覆盖。

- 只接受 `KEY=VALUE`，一行一对；忽略空行与整行 `#` 注释；
- **白名单键**：`TARGET_CANDIDATE_SHA`、`TARGET_V14_SHA`、`EXPECTED_OWNER`、`EXPECTED_MODE`；
- 未知键、重复键、缺键 → 失败；
- 不允许引号、空格、续行、变量展开、`export`；
- 值类型校验：
  - SHA：`^[0-9a-f]{64}$`；
  - OWNER：唯一判定来源 `root:root`；部署前记录仅用于核对，不一致即失败；
  - MODE：`^(?:[0-7]{3}|0[0-7]{3})$`（严格三位或四位八进制）；
- 解析失败 → 不启动、记录、报告。

#### 3.1.2 路径与父目录保护

1. `deploy.env` 使用**绝对路径**，拒绝相对路径；
2. **从 `/` 到直接父目录逐级检查**：每级 `lstat`（拒绝 symlink），核验属主、权限；
3. **world-writable**：任一级 others 有 `w` → 不启动；
4. **group-writable**：任一级 group 有 `w` 时，仅当该组可证明只含 root/可信主体才可接受；无法证明 → 不启动；
5. 文件本身：属主 `root`、mode 不宽于 `0640`、非符号链接；
6. 上述检查不能消除“检查后被替换”的竞态；权限基线完成前，**不宣称可靠防篡改**。

#### 3.1.3 读取与使用竞态

- 读取后记录文件 `inode/mtime/SHA`，使用前再次核验；不一致 → 中止；
- 仍不能根治；与权限基线整改建立依赖；
- 不能把“两次 stat 一致”写成“配置文件安全”。

#### 3.1.4 交叉核对

- `TARGET_V14_SHA` 必须等于备份实际 SHA 与部署准备报告基线；
- `TARGET_CANDIDATE_SHA` 必须等于候选 snapshot SHA；
- 不一致 → 中止，不启动。

### 3.2 唯一启动入口与启动后状态机

```text
TARGETS = {
  "candidate": TARGET_CANDIDATE_SHA,
  "v14":       TARGET_V14_SHA,
  "recovered-v14": TARGET_V14_SHA,
}

start_verified(target):
  expected_sha = TARGETS[target]        # target 未知 → 立即失败
  读取磁盘 main.py 的 SHA/属主/权限
  核验 SHA == expected_sha
  核验 属主 == EXPECTED_OWNER
  核验 权限 == EXPECTED_MODE
  追加 precheck 事件（pass/fail）
  若 fail → 不启动、返回非零
  持久化 start_invoked（见 3.5.3）→ 失败则不启动
  docker start
  追加 start_result（docker_start_exit_0 / docker_start_exit_nonzero）
  读取容器实际状态（Running/Stopped）
  再次读取磁盘 inode/mtime/SHA
  追加 resolution：
    Running + 磁盘三项符合 expected → running_disk_match
    Running + 磁盘不一致          → running_disk_mismatch
    Stopped                       → stopped_unknown
  返回
```

- **只有 `start_verified()` 内部允许实际执行 `docker start`**；
- `restart_verified(target)` 只 `docker stop` + 状态检查 + 委托 `start_verified(target)`；
- `running_disk_match` 只证明“巡检时容器 Running 且磁盘相符”，**不证明容器已加载目标代码字节**；
- `stopped_unknown` 下不得把 `docker_start_exit_0` 当“启动成功”。

### 3.3 分支矩阵

| 分支 | 启动调用 |
|---|---|
| 正常部署（替换后） | `start_verified(candidate)` |
| 备份失败 | 不自动启动；保留现场、报告；确认可信 v14 后才 `start_verified(v14)` |
| 备份校验不一致 | **不自动启动、不自动回滚**；只有找到可信、SHA 符合 `TARGET_V14_SHA` 的 v14 文件并恢复后，才 `start_verified(v14)`；无法确认则保持停止 |
| 临时文件复制/校验失败 | 删临时文件；确认原文件可信后 `start_verified(v14)`；否则停止、报告 |
| `mv` 失败 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败则停止、报告 |
| 回滚 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败则停止、报告 |
| 启动失败后重试 | 仍调用 `start_verified(当前 target)` |
| 验证失败（测试 FAIL） | 不自动启动/回滚；报告，由主人决定 |

### 3.4 restart 语义

- **禁止裸 `docker restart`**；
- `restart_verified(target)`：

```text
restart_verified(target):
  docker stop
  检查容器实际状态（失败/仍运行 → 不继续，报告）
  start_verified(target)      # 唯一启动入口
```

#### 3.4.1 重启后核验失败：统一状态

- `STOPPED_UNVERIFIED`：容器停止且磁盘未通过核验；保持停止，不自动启动；保留现场；写日志；报告。
- `RUNNING_UNVERIFIED`：容器已运行但复核失败；保持运行，**不自动 stop/restart/回滚**；保留现场；写日志；报告；是否停止由主人决定。
- 两种状态都只读记录；dsh 不自动执行恢复动作。

### 3.5 启动日志（JSONL 事件流）

路径：`/opt/astrbot/shared/记忆/部署日志/start-attempt-<attempt_id>.jsonl`。

#### 3.5.1 日志目录安全前置条件

1. 从 `/` 到日志目录逐级 `lstat`，拒绝 symlink；
2. 属主为 `root`；
3. 不 world-writable；group-writable 需证明组内仅 root/可信主体，否则失败；
4. 日志文件（若已存在）非 symlink、属主 `root`、mode 不宽于 `0640`；
5. 检查失败、创建失败、持久化失败 → **不得执行 `docker start`**；
6. 日志路径权限基线纳入单独的权限安全评估。

#### 3.5.2 事件模型

每次尝试一个 `attempt_id`，JSON Lines 追加：

```text
{"event":"attempt_created","attempt_id":"...","time":"...","target":"candidate"}
{"event":"precheck","attempt_id":"...","result":"pass|fail","expected_sha":"...","actual_sha":"...","owner":"...","mode":"..."}
{"event":"start_invoked","attempt_id":"...","time":"..."}
{"event":"start_result","attempt_id":"...","result":"docker_start_exit_0|docker_start_exit_nonzero","time":"..."}
{"event":"resolution","attempt_id":"...","result":"running_disk_match|running_disk_mismatch|stopped_unknown","time":"..."}
```

- 每个事件独立追加，不重写已有事件；`attempt_id` 关联；
- `start_result` 只代表 Docker 命令返回，不代表应用就绪或已加载目标代码；
- 每行必须是完整合法 JSON。

#### 3.5.3 创建与追加流程（v6 分开定义）

**A. 首次创建文件（attempt 尚未存在）**

1. 在受保护目录创建临时文件（同目录，非 symlink）；
2. 写入 `attempt_created`、`precheck`、`start_invoked`（需要先行的全部事件）；
3. 对临时文件执行 `fsync`；
4. 原子 `rename` 为正式日志文件；
5. 对父目录执行 `fsync`（确保目录项持久化）；
6. 全部成功后才允许 `docker start`；任一步失败 → 不启动、报告。

**B. 已有文件追加**

1. 以 append 方式写入一条完整 JSONL 事件（一次写完整行，含换行）；
2. 检查写入完整性（写入字节数/行完整）；
3. 对文件执行 `fsync`；
4. 任一步失败 → 不得执行后续启动动作。

**C. 部分写入/中断**

- 残缺 JSON 行**不得视为有效事件**；
- **不得通过覆盖/重写原文件来修复历史**；
- 只能：追加新事件、或将残缺行标记为 `corrupt_line`（追加记录），原始字节保留；
- 若 `start_invoked` 未完整持久化 → **不得启动**；
- 进程中断后保留现场，交后续只读取证。

#### 3.5.4 `invoked` 遗留与 `resolution`

- 发现 `start_invoked` 遗留：读容器状态与磁盘三项，追加 `resolution`（running_disk_match / running_disk_mismatch / stopped_unknown）；
- 原事件保留；不把 `invoked` 当 success。

### 3.6 静态检查与完整调用链（v6 边界）

`grep` **只是基础检查，不是唯一启动入口的完整证明**。

1. 审查所有部署脚本及其调用的辅助脚本；
2. 检查所有实际执行 Docker 命令的代码路径（含子进程、Python 调用、其它脚本）；
3. 对统一入口外的启动调用做**负向测试**（断言会被捕获/拒绝）；
4. 对最终脚本做**人工调用链复核**；
5. `grep` 无命中不能宣称“不存在绕过路径”。

### 3.7 测试矩阵

1. `deploy.env` 解析（缺/多/重复/非法值/权限宽/父目录 world-writable/group-writable/symlink）；
2. 父目录从 `/` 逐级检查；
3. 读取与使用间替换（两次 inode/mtime 不一致）；
4. 重启后失败：`STOPPED_UNVERIFIED` / `RUNNING_UNVERIFIED`，断言不自动 stop/restart/回滚；
5. 启动后状态机：`docker_start_exit_0` + 容器 Running/Stopped、磁盘一致/不一致，断言 `resolution` 正确；
6. JSONL 首次创建：临时文件/fsync/rename/目录 fsync；任一步失败不启动；
7. JSONL 追加：完整行/部分写入/中断；残缺行不当作有效事件；不覆盖历史；
8. `start_invoked` 未持久化 → 不启动；
9. 日志目录权限不合格/文件创建失败/持久化失败 → 不启动；
10. 备份校验不一致：不自动启动、不自动回滚；
11. Docker 非零返回但容器状态异常（如 Running）→ 记录 `docker_start_exit_nonzero` + 实际状态，不自动处理；
12. 负向测试：统一入口外的启动调用被捕获；
13. target/SHA 映射：未知 target/不匹配 → 失败。

### 3.8 竞态（配置 + 主文件 + 日志）

- 目录 0777、文件 0666；检查到 Docker 加载之间文件仍可能被替换；
- `deploy.env` 也有“读取→使用”竞态；
- 日志文件/目录同样可能被替换或篡改；
- `flock` 只防并发部署，不阻止其他写入者；
- 缓解不等于根治；**不能宣称竞态已消除**；权限基线整改是根治前提。

## 四、现实约束（v6 新增）

当前 `/opt/astrbot`、`data`、`plugins`、插件目录均为 0777（专项评估记录）。按 v6 自己的规则：

- 日志目录前置检查很可能**无法通过**；
- `deploy.env` 父目录检查同样可能无法通过；
- 因此 **v6 设计通过后也不能直接施工/部署**；
- 必须先独立完成权限基线评估与必要整改，确认日志目录、配置目录、部署路径符合要求；
- **不得为了让脚本跑起来而放宽 fail-closed 条件**。

## 五、风险

1. 竞态未根治（依赖权限基线）；
2. `start_verified` 只保证启动字节与目标一致，权限 0666 下不代表权限安全；
3. 日志目录当前可能不满足前置条件，届时 fail-closed 不启动；
4. 分支测试若只 dry-run，可能与真实 Docker 行为有差异；
5. `grep` 不能单独证明无绕过路径。
