## 〇、v12 返修点

1. **日志目录安全操作**：从可信根逐级 `openat` + `O_NOFOLLOW` + `fstat`，创建/追加全部使用已验证的目录 fd；不再依赖检查后重新解析完整路径；日志目录与锁目录分别建立保证。
2. **入口边界分层**：明确“项目内部脚本只经 `deploy.sh`”与“系统级 Docker 权限控制”是两层；本项目未提供系统级控制时，明确写“不保证拥有 Docker 权限的外部主体无法绕过 `deploy.sh`”。
3. **`start_invoked` 语义**：=`启动意图已持久化`，**不代表 Docker 命令已发出**；补 `command_sent`（yes/no/unknown）与 `result_unknown`/`not_sent` 状态。
4. **事件矩阵**：逐事件列出必需/可选/禁止字段；`precheck=fail` 只写一条，不重复。
5. **锁释放**：事务级统一清理；异常/信号/分支失败不自行释放；区分正常释放、进程退出内核释放、事务失败仍持锁。

## 一、现状缺陷（已证实）

1. `p3_deploy_stepA.sh` 的 `BACKUP_MISMATCH` 分支裸 `sudo docker start astrbot`；
2. 备份失败、复制失败、`mv` 失败等分支也有裸 `docker start`；
3. 预期 SHA 硬编码，且误写为 v6（`c4497e04…`），实际 v14（`2f180cf0…`）；
4. “启动完整性核验”与“权限安全基线”未分开；
5. 无统一启动日志。

## 二、目标

1. 所有部署动作只经唯一顶层事务；
2. 全局锁覆盖完整事务，锁失败零改动；
3. 启动前核验 SHA、属主、权限；
4. 日志与锁目录使用安全目录 fd；
5. 启动意图、命令发出、命令结果、记录结果四层分开；
6. 失败不启动、报告、人工恢复；
7. 竞态未根治，依赖权限基线。

## 三、设计

### 3.1 配置来源与保护

#### 3.1.1 唯一来源与初始信任根

`deploy.env` 是唯一来源；不保留脚本顶部常量、不读 shell 环境变量覆盖。

**初始信任根**：

1. `deploy.env` 必须 `root:root`、mode `0640`、非 symlink；
2. 从 `/` 到直接父目录逐级 `lstat`：每级 `root` 属主、非 symlink、不含 world/group write；
3. 任一级不满足 → 失败，**不读取配置内容**；
4. 通过后才读取 `TRUSTED_OWNERS`、`PRIVILEGED_GROUPS`；
5. 不得用配置内白名单证明配置自身路径可信。

**解析**：

- `KEY=VALUE` 一行一对；忽略空行/整行 `#`；
- 白名单键：`TARGET_CANDIDATE_SHA`、`TARGET_V14_SHA`、`EXPECTED_OWNER`、`EXPECTED_MODE`、`TRUSTED_OWNERS`、`PRIVILEGED_GROUPS`；
- 未知/重复/缺键 → 失败；不允许引号/空格/续行/变量展开/`export`；
- SHA `^[0-9a-f]{64}$`；OWNER `root:root`；MODE `^(?:[0-7]{3}|0[0-7]{3})$`；
- `TRUSTED_OWNERS`：`name:uid:gid` 逗号分隔，含 `root:0:0`；
- `PRIVILEGED_GROUPS`：组名逗号分隔，至少 `sudo,wheel,adm`；
- 解析失败 → 不启动、记录、报告。

#### 3.1.2 路径、父目录与属主

1. 绝对路径；
2. 配置路径按 3.1.1（仅 root）；
3. 其它路径允许：`root:0:0`；或白名单内且 passwd `name/uid/gid` 一致、系统账号（`100<=uid<=999` 或显式标注）、`nologin`/`false`、主 GID 与附加组均不在 `PRIVILEGED_GROUPS`；组来源可读；否则失败；
4. 任一级 world-writable → 不启动；
5. group-writable：主 GID 成员 + `getent group` 附加成员，存在非白名单 → 失败；组信息不完整 → 失败；
6. 文件 root、mode ≤0640、非 symlink；
7. 不宣称防篡改。

#### 3.1.3 读取与使用竞态

- 读取后记录 `inode/mtime/SHA`，使用前再核验；
- 不能根治；依赖权限基线。

#### 3.1.4 交叉核对

- `TARGET_V14_SHA` = 备份实际 SHA = 部署准备报告基线；
- `TARGET_CANDIDATE_SHA` = 候选 snapshot SHA；
- 不一致 → 中止。

### 3.2 唯一顶层事务与入口边界

```text
deploy.sh <action> [target]        # 唯一项目入口
  deploy_transaction(action, target):
    acquire_global_lock()          # 失败 → 零改动、退出
    try:
      ... 备份 / 替换 / 恢复 / stop / start_verified / resolution ...
    finally:
      release_attempt_lock()       # 若持有
      release_global_lock()
```

- 项目内部约束：所有项目自有脚本只经 `deploy.sh`；`lib/` 禁止独立执行；`start_verified` 不导出；
- **系统级边界**：能否阻止拥有 Docker socket/sudo 权限的外部主体直接调用 Docker，由 sudoers、socket 权限等系统控制决定；本项目未提供这些控制时，**不保证外部主体无法绕过 `deploy.sh`**；本设计只保证“项目内部受控入口统一经过事务”；
- 负向测试分三类：项目内部辅助脚本直接执行；项目内部调用链绕过事务；系统外部直接 Docker（第三类不能仅靠脚本测试证明）。

#### 3.2.1 `start_verified`（内部）

```text
start_verified(target):
  expected_sha = TARGETS[target]
  读取磁盘 main.py 的 SHA/属主/权限
  核验三项
  追加 precheck（pass/fail）
  fail → 不启动（不写 start_invoked）
  持久化 start_invoked            # 仅表示“启动意图已记录”
  （命令尚未发出）
  command_sent = no → 发出 docker start → command_sent = yes
  attempt_result = exit_0 | exit_nonzero | not_sent | result_unknown | unrecorded
  container_state = query() → running | stopped | unknown
  disk_verification = check() → match | mismatch | check_failed
```

- `start_invoked` 语义：**启动意图已持久化**，不代表 Docker 命令已发出；
- `command_sent`：`yes`（已发出）/ `no`（进程中断在发出前）/ `unknown`（无法确定）；
- `not_sent`：明确未发出；`result_unknown`：已发出但结果无法取得；`unrecorded`：结果存在但日志写入失败（进程内）；
- 后续只读取证不得仅凭 `start_invoked` 认定命令已执行。

#### 3.2.2 三维状态与对外映射

| 维度 | 取值 |
|---|---|
| `attempt_result` | `exit_0` / `exit_nonzero` / `not_sent` / `result_unknown` / `unrecorded` |
| `command_sent` | `yes` / `no` / `unknown` |
| `container_state` | `running` / `stopped` / `unknown` |
| `disk_verification` | `match` / `mismatch` / `check_failed` |

| container_state | disk_verification | 对外状态 |
|---|---|---|
| running | match | `RUNNING_DISK_MATCH` |
| running | mismatch | `RUNNING_DISK_MISMATCH` |
| running | check_failed | `RUNNING_DISK_UNVERIFIED` |
| stopped | 任意 | `STOPPED_UNVERIFIED` |
| unknown | 任意 | `STATE_UNKNOWN_UNVERIFIED` |

- `RUNNING_DISK_MATCH` 不代表已加载目标代码；
- `attempt_result`/`command_sent` 独立保留；
- 只读记录、保留现场、报告；不自动 stop/restart/回滚。

#### 3.2.3 UNRECORDED 边界

- `start_result` 只表示实际成功持久化的结果：`exit_0`/`exit_nonzero`/`not_sent`/`result_unknown`；
- 写入失败 → 进程内 `attempt_result=unrecorded`；
- 后续 resolution 可带 `attempt_result=unrecorded` 说明此前记录失败；
- resolution 也失败 → 保留现场与已有日志，不声称完整；
- 四个事实分开：启动意图、命令是否发出、命令结果、记录是否成功。

### 3.3 分支矩阵（全部经顶层事务）

| 分支 | 事务内动作 |
|---|---|
| 正常部署 | 备份 → 替换 → `start_verified(candidate)` |
| 备份失败 | 不启动；报告；可信 v14 恢复后才 `start_verified(v14)` |
| 备份校验不一致 | 不自动启动、不自动回滚；可信 v14 恢复后才 `start_verified(v14)`；否则停止 |
| 临时文件复制/校验失败 | 删临时文件；确认原文件可信后 `start_verified(v14)`；否则停止 |
| `mv` 失败 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败停止 |
| 回滚 | 恢复备份并核验；通过后 `start_verified(recovered-v14)`；失败停止 |
| 启动失败后重试 | 仍 `start_verified(当前 target)`（事务内） |
| 验证失败（测试 FAIL） | 不自动启动/回滚；报告，由主人决定 |

### 3.4 restart 语义

```text
deploy_transaction("restart", target):
  ...（全局锁已持有）...
  docker stop
  检查容器实际状态
  start_verified(target)
```

禁止裸 `docker restart`。

### 3.5 启动日志（JSONL）

路径：`/opt/astrbot/shared/记忆/部署日志/start-attempt-<attempt_id>.jsonl`。

#### 3.5.1 日志目录安全（目录 fd）

1. 从可信根 `/` 开始，逐级 `openat(parent_fd, name, O_DIRECTORY|O_NOFOLLOW)`；
2. 每级 `fstat` 核验：目录类型、属主（按 3.1.2）、不含 world/group write；
3. 保持目录 fd 链；取得日志目录 fd；
4. 创建临时文件：`openat(logdir_fd, "....tmp", O_CREAT|O_EXCL|O_NOFOLLOW, 0600)`；
5. 正式文件：`linkat(logdir_fd, tmp, logdir_fd, final)` 或 `renameat2(RENAME_NOREPLACE)`；
6. 追加：`openat(logdir_fd, name, O_RDWR|O_APPEND|O_NOFOLLOW)`；
7. **不再用完整路径创建/追加**；目录 fd 持有到事务结束，文件 fd 每次操作后关闭；
8. 日志目录与锁目录分别建立保证，不互相代表。

#### 3.5.2 事件矩阵（每事件 schema）

| 事件 | 必需字段 | 可选字段 | 禁止字段 |
|---|---|---|---|
| `attempt_created` | event, attempt_id, time, target | — | result, attempt_result, container_state, disk_verification |
| `precheck` | event, attempt_id, time, result(pass/fail) | expected_sha, actual_sha, owner, mode | attempt_result, container_state, disk_verification |
| `start_invoked` | event, attempt_id, time | command_sent(no/unknown) | result, attempt_result, container_state, disk_verification |
| `start_result` | event, attempt_id, time, result(exit_0/exit_nonzero/not_sent/result_unknown) | command_sent | container_state, disk_verification |
| `resolution` | event, attempt_id, time, attempt_result, container_state, disk_verification | command_sent | result |
| `recovery` | event, attempt_id, time, action(added_line_terminator) | — | result, attempt_result |

- `additional_properties=false`，按上表拒绝未列字段；
- `attempt_created` 的 `target` 必需；`precheck` 的 `result` 必需；
- `start_invoked` 只表示意图，禁止携带 `result`；
- `precheck=fail` 只写一条 `precheck`，不重复写 fail 事件。

#### 3.5.3 严格 JSON 校验

- 只接受 JSON 对象；拒绝数组/标量；
- 拒绝重复键；拒绝 `NaN`/`Infinity`；
- 按 3.5.2 逐事件校验必需/可选/禁止字段；
- 任一行不满足 → 非法行，按 3.5.4 处理。

#### 3.5.4 JSON 合法性处理

| 情况 | 处理 |
|---|---|
| 合法 + 有换行 | 可追加 |
| 合法 + 无换行 | 锁内 append `\n` → fsync → append `recovery` → fsync → 才允许后续 |
| 非法 + 无换行 | 原字节保留；停止追加、只读取证、不启动 |
| 非法 + 有换行 | 原字节保留；停止追加、只读取证、不启动 |
| 中间行非法 | 停止追加、只读取证、不启动 |
| 连续非法/无法定位 | 停止追加、只读取证、不启动 |

- 恢复任一步失败 → 停止后续追加与启动；不覆盖/截断历史。

#### 3.5.5 创建与追加（锁顺序统一）

**锁顺序**：全局锁 → attempt 锁；释放 attempt → 全局。

**A. 首次创建**

1. 全局锁已持有；获取 attempt 锁（失败 → 不创建、报告）；
2. 用已验证 logdir fd 创建临时文件（`O_CREAT|O_EXCL|O_NOFOLLOW`）；
3. 写 `attempt_created`；
4. 写 `precheck`；
5. **若 precheck=fail**：写这一条 fail → `fsync` → 原子创建正式文件 → 目录 `fsync` → **直接返回，绝不 `docker start`**（不再重复写 fail）；
6. 若 pass：写 `start_invoked` → 临时文件 `fsync` → 不覆盖原子创建（目标已存在失败）→ 删临时文件 → 目录 `fsync`；
7. 只有 pass + `start_invoked` 已持久化 + 原子创建 + 目录 fsync 全成功，才允许 `docker start`；
8. 释放 attempt 锁。

**B. 已有文件追加**

1. 全局锁已持有；获取 attempt 锁；
2. 严格 JSON 校验；
3. append 一条完整事件；
4. 校验写入完整；文件 `fsync`；
5. 任一步失败 → 不启动；
6. 释放 attempt 锁。

**C. 目录 fsync 失败**

- 正式文件已创建但目录 fsync 失败：可能留下含 `start_invoked` 的文件；
- 不启动；标记 `state_uncertain`；不假设 Docker 已执行。

#### 3.5.6 锁设计

**全局部署互斥锁**：

- 路径固定；目录链从 `/` 逐级 `openat` + `fstat`（同 3.5.1 原则）；
- `openat(lockdir_fd, "deploy.lock", O_RDWR|O_CREAT|O_NOFOLLOW, 0600)`；
- `fstat(fd)` 核验 regular/root/0600；
- `fstatat(lockdir_fd, "deploy.lock", AT_SYMLINK_NOFOLLOW)` 与 `fstat(fd)` 比较 `dev/ino`，不一致失败；
- `flock(LOCK_EX|LOCK_NB)`；
- 锁目录必须 root 且不可被外部替换，否则两进程可能锁不同 inode；
- 获取失败 → 零改动、退出。

**attempt 日志锁**：同目录、同一套 fd/fstat/flock 规则；只防同 attempt 并发写。

#### 3.5.7 锁释放与异常

- **事务级统一清理**：`try/finally` 中释放 attempt 锁、全局锁；业务分支不得自行释放；
- 正常结束：finally 释放；
- 异常/信号（SIGINT/SIGTERM）：保留现场（日志、文件状态）后退出；锁由 finally 或进程退出由内核释放；
- 进程存活但事务失败：**继续持有锁直到事务结束**，不提前释放暴露未完成状态；
- 不可恢复错误：记录后退出，不为了尽快释放锁而掩盖未完成状态；
- attempt 锁同理。

### 3.6 入口边界（内部/系统分层）

- 项目内部：`deploy.sh` 唯一入口；`lib/` 禁止独立执行；`start_verified` 不导出；
- 系统级：sudoers、Docker socket 权限、其他 ACL 决定外部主体能否直接调用 Docker；
- 本项目未实现系统级控制时，明确：**不保证拥有 Docker 权限的外部主体无法绕过 `deploy.sh`**；本设计只保证项目内部受控入口统一经过事务；
- 负向测试：内部辅助脚本、内部调用链、系统外部直接 Docker（第三类不能仅靠脚本测试证明）。

### 3.7 测试矩阵

1. 配置初始信任根（非 root/权限宽/symlink → 不读取内容）；解析；
2. 父目录逐级；非 root 判据；
3. 日志目录 fd 链：逐级 openat/fstat；symlink/非 root/权限宽失败；创建/追加只用 dirfd；
4. 三维状态组合（attempt_result × command_sent × container_state × disk_verification）；
5. 事件矩阵：必需/可选/禁止字段；未知字段；类型错；precheck=fail 只一条；
6. JSON 严格：重复键/NaN/Infinity/非对象；合法无换行恢复；非法（无/有换行/中间/连续）；
7. 首建：precheck=fail 不启动；pass 才启动；并发首建失败；
8. 锁顺序：全局→attempt；异常/信号下 finally 释放；事务失败仍持锁；
9. 锁目录链与 inode 一致性；
10. 全局锁覆盖所有分支；锁失败零改动；
11. attempt 锁并发拒绝；
12. 日志目录/创建/持久化失败 → 不启动；
13. 备份校验不一致不自动启动/回滚；
14. Docker 非零但容器异常；
15. 入口负向测试：内部辅助脚本/内部调用链/系统外部（第三类标记为“不能仅靠脚本证明”）；
16. target/SHA 映射。

### 3.8 竞态

- 0777/0666 下检查到 Docker 加载之间文件可能被替换；
- 配置读取→使用竞态；日志/锁目录可被替换；
- `flock` 不阻止外部写入者；
- 不能宣称竞态消除；权限基线是根治前提。

## 四、现实约束

当前 0777 环境可能无法通过配置/日志/锁目录检查；设计通过后也不能直接施工/部署；先完成权限基线评估与整改；不得为让脚本跑起来放宽 fail-closed。

## 五、风险

1. 竞态未根治（依赖权限基线）；
2. 启动字节一致 ≠ 权限安全；
3. 日志/锁目录可能不满足前置条件，届时 fail-closed 不启动；
4. dry-run 与真实 Docker 差异；
5. 系统级 Docker 权限无法由脚本保证。
