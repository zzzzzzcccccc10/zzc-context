## 二、四个队友独立一致确认的阻断问题

### 一致项 1：`SOCK_STREAM` 方向正确，但 §4.5.7 的 `SCM_RIGHTS`/分帧合同不成立（A 主发现，B 交叉印证）

- A：内核语义是 fd 关联在 `sendmsg` 数据流的**第一个字节**，不关联应用层“帧字段”；Linux 允许 fd 随**部分读**交付。v35 断言“length 前缀本身不携带 fd；SCM_RIGHTS 只出现在 pidfd 帧的 recvmsg 控制消息”**不是内核保证**。
- 反例：先 `read(4)` 长度、再读 32B 头且长度读取未带控制缓冲 → 内核在消费 pidfd 帧首字节时 detach fds，因控制空间不足置 `MSG_CTRUNC` 并关闭 fd → pidfd 丢失（fail-closed，但按文无法实现）；若长度读取带控制缓冲，fd 会随长度前缀那次 `recvmsg` 返回，与设计不符。
- B 独立指出同类“I/O 合同未定义”：未规定部分写/EINTR/EPIPE/SIGPIPE、`read()` 与 `recvmsg` 混用、`MSG_CTRUNC` 时已收 fd 的关闭；混用 `read()` 会拿不到 cmsg。
- **证据**：Linux v6.12 `net/unix/af_unix.c` `unix_stream_read_generic`/`unix_stream_sendmsg`；`net/core/scm.c` `scm_detach_fds`；2019 年 af_unix 补丁讨论；A 已给行号链接。目标环境实验未执行。

### 一致项 2：`execve` 结果不可观测， `execve_failure` 证据不可证明（B 主发现，C 独立、D 测试不可判定）

- B：supervisor 没有独立渠道得知 CLI 的 `execve` 是否成功；退出码无法区分“execve 失败”“docker 正常执行后非零（含 127）”“被信号杀死”。若 Docker CLI 返回 127，会把“可能已发送”误记为 `not_sent(cli_exec_failed)`，诱发重复启动。
- C：同样把 F1 列为 P1；`cli_exec=failed` 不可证明；可能把已发送误记未发送，或把 exec 失败误记 `exit_nonzero`。
- D：测试矩阵无法判定 exec 成败，D11/D14 等场景无观测点；正向对照缺失，永不放行的实现可通过全部负向用例。
- **证据**：v35 §4.2.1 L182、§4.5.2 L326/L403；无 exec 结果通道/errno 上报设计。

### 一致项 3：放行字节写出不是显式、可审计的状态转移（B 主发现，C F2、D D5 呼应）

- B：正文只在 L466/L468 写“才允许迁移/放行”，§4.2.1 流程没有“写放行字节 + 校验写成功”步骤，成功路径没有“放行已授权”事件；实现把放行提前写在日志上与合规运行无法区分（B2）。
- C：F2 指出放行前后失败路径（supervisor 写放行字节失败 EPIPE、CLI 读到字节后 execve 前被杀、CLI 等待放行时死亡）没有 kind/reason，只能“保持锁、人工”或错误归类。
- D：D5/D14 指出 FIN 后额外帧、release 写失败等场景无判据，evidence 期望自相矛盾。
- **一致**：放行时序需要显式事件/字段（如 `gate_authorized` 或 `release_phase=after_eof`）与失败 kind。

### 一致项 4：端点继承顺序/`CLOEXEC` 处理有自授权与残留面（B B3，A P2-D 时序矛盾）

- B：L155/L422 在主进程 fork 前清除 supervisor 端 CLOEXEC；CLOEXEC 只对 execve 生效、对 fork 无效，supervisor 又不 exec，该步骤无收益；反而让 CLI 若未及时关闭 supervisor 端，端点跨 exec 存活进 Docker。L159+L161 的“先 fork CLI、后关继承的主进程端”使 CLI 在 fork 瞬间同时继承授权端与 supervisor 端，与 §1.2“CLI 不持有任何 socket 端点”不符。
- 反例 C2：若 CLI 漏关主进程端且主进程崩溃/卡住，CLI 可从 P 读 done/取得 X，自己发 ACK+FIN+shutdown，supervisor 看到合法 ACK+FIN+EOF → 迁移放行；放行不再依赖主进程。
- A 独立指出 §4.2.1 与 §4.5.7 的关闭顺序表述矛盾（一个说 fork CLI 前关、一个说 fork CLI 后关），若按后者 EOF 延迟到 CLI 关闭，最坏死锁/超时。
- **一致修订**：supervisor 在 fork CLI **之前**关闭主进程端；两端保持 `SOCK_CLOEXEC`；CLI fork 后第一动作关 supervisor 端；`/proc/self/fd` 核验。

### 一致项 5：Evidence 全路径/`gate` 组合与崩溃恢复未闭合（C 主发现，B C3、D D5 交叉）

- C：F1 execve 不可判定；F2 放行前后失败无 kind/reason；F3 崩溃恢复规则忽略 evidence（evidence 已落盘、not_sent 未写是合法崩溃态，却被判 `result_unknown`；evidence(gate=released) 无 start_result 同样）；F4 evidence→not_sent 缺 fsync 契约（§4.5.1 追加无 fsync）；F5 写入者/日志 fd/attempt 锁归属未定义，与 §4.2.1 矛盾（supervisor 写 not_sent 后退出，主进程却判“人工”）；F6 v34 的 reaped/reap_method/reap_result 组合约束在 v35 丢失；F7 `call_declined/operator_cancel/precondition_changed` 无 evidence 映射；F9 ACK/FIN 失败四处规则不一致且“条件满足”未定义。
- B：C3 done 发送失败窗口两套终态（supervisor 写 not_sent / 主进程保持锁人工），无单一终态裁决者；锁释放未定义。
- D：D5 evidence 期望冲突；D24“保持锁、人工”无挂起点定义，进程退出则 flock 自动释放，“保持锁”不成立。
- **一致**：evidence 需要重写为“日志重放算法 + 单一终态写者 + fsync 契约 + 组合校验”，不能靠措辞。

### 一致项 6：测试矩阵缺判据、正向对照与 seam（D 主发现，C F15 呼应）

## 五、v36 修订方向（Lead 汇总，供设计返修）

1. **I/O 合同**：每帧一次 `sendmsg`（返回 36、`MSG_NOSIGNAL`、fd 帧禁止重试）；每次 `recvmsg` 带控制缓冲 + `MSG_CMSG_CLOEXEC`；fd 按帧累计；`MSG_CTRUNC/MSG_TRUNC` 关闭 fd + 协议错误；禁止 0 长度 read/recv；EOF 仅在“请求≥1 + 返回 0 + 帧边界”判定。
2. **SCM_RIGHTS 与分帧**：删除“length 前缀不携带 fd”；明确 fd 关联在首字节；或改固定 36B 单次 recvmsg；补目标环境实验设计（A E1–E8）。
3. **exec 结果通道**：CLOEXEC error pipe（execve 失败写 errno 后 `_exit`；成功自动关闭）；只有明确 execve 失败才允许 `execve_failure + not_sent`；其余放行后异常一律 `result_unknown`/`exit_nonzero` + `command_sent=yes/unknown`，禁止把可能已发送记成 not_sent。
4. **放行事件**：新增 `gate_authorized`（ACK+FIN+EOF 验证后、写放行前持久化）或 `release_phase=after_eof`；交叉约束 gate=released ⇔ release=yes、gate=closed ⇒ release=no ∧ cli_exec=false。
5. **端点顺序**：fork CLI 前关主进程端；两端保持 CLOEXEC；CLI fork 后关两端；`/proc/self/fd` 断言；统一 §4.2.1/§4.5.7 表述。
6. **evidence 重写**：日志重放算法与优先级（start_result > start_not_sent > evidence 派生 > result_unknown）；单一终态写者；fsync 契约；恢复 reason↔kind；补 release 失败/CLI 放行前后死亡 kind；补 reaped/reap_method/reap_result 组合校验；删除或定义 call_declined/operator_cancel/precondition_changed；补人工中止事件。
7. **测试**：新增 §4.7.0 判据/观测点（canary、放行字节、JSONL evidence 期望、三维状态、锁持有、进程去向）；正向对照；补 D 的 D1–D25 与 C 的 F15；补 seam（纯函数库/test-only peer/canary）。
8. **目标环境**：固定内核版本/配置；A 的 E1–E8 实验设计作为授权后验证项；超时/时钟/上限数值写死。
