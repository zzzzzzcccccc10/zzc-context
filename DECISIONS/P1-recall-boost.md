# 决策记录 · P1-recall_boost（按问句检索）

日期：2026-11-15 至 2026-11-17　状态：**封版并部署**

## 背景

旧版一次问多个问题时，livingmemory 只做一次整体召回，向量被稀释，导致"明明在库里却想不起来"（实测 15 问有 33% 漏）。同时旧版在 `on_llm_request` 里同步算全部文档向量，实测注入阶段 **281 秒**。

## 已批准

1. **按问句分别检索**：≥2 问句才拆，每句单独算 query 向量，取最相关几条。
2. **持久向量缓存**：`recall_boost_vectors.json`，按 `doc_id` / 内容 hash 存，文档与原子用命名空间隔离，`CACHE_VERSION=2`；预热在后台线程，钩子里只算 query 向量（5s 网络超时、整轮 15s 预算）。
3. **快照只当索引，权限每次现查**：
   - 原子：每次读 `原子.jsonl`（读前/读后 stat 一致才用，否则跳过原子注入）；
   - 文档：每次查 `documents` 的 `text`+`metadata`，正文 hash 不一致不注入旧正文；
   - `vis` 严格匹配 `"public"`（主人私聊允许 `"private"`）。
4. **所有 await 结束后才做权限判断与排序**（防止 await 期间权限收紧）。
5. **query 调度有界**：2 线程池 + 非阻塞槽位，满载立刻降级；LRU 5 秒 / 64 条；同 query 去重。
6. **R1 共享范围**：用 livingmemory 正式 `resolve_memory_scope`；因历史 session 平台段是 `aiocqhttp`、现 platform 名是 `大肥鱼`，按同身份后缀匹配而非整串等值。

## 已否决

- 在钩子里同步算全部文档向量（否决：281 秒的根因）。
- 用 mtime 判断记忆库变化（否决：WAL 模式下 mtime 不可靠，已实测）。
- 依赖 600 秒刷新来保证权限正确（否决：TOCTOU）。
- 有外部工具就整体禁用插件（否决：public 原子与本会话文档仍应可用）。
